## 3. R26-01｜规则发布诊断覆盖豁免过宽（P0，SC+PX）

位置：
- `services/api/app/monitoring_protocol_rules.py::expression_requires_diagnostic_coverage`
- `services/api/app/monitoring_protocol_rule_repository.py::_validate_release_shadow_evidence/_assert_release_coverage`
- `services/api/app/monitoring_protocol_rule_service.py::_evaluate_predicate_with_trace`

新增 walker 只要表达式树没有 `changed` 或 `no_corresponding_record`，就返回“不要求 diagnostic_indeterminate 覆盖”。但求值器明确对下列输入返回 indeterminate：

- eq/ne/in/not_in 的缺失值、不合法值或非有限值；
- gt/gte/lt/lte 的非数值操作数；
- regex 的缺失值或非法正则；
- date_compare/date_delta_days 的无效、部分日期或配置。

PX：gt、eq、date_compare、regex 表达式均被 walker 豁免。引擎对应分支来自源码交叉核对，本轮未全引擎执行。这证明**豁免范围超出了已描述的“纯 exists/missing”决策**，不证明已发布的两条 missing 规则本身必然有错误。

修复：基于已知算子能力的保守分类。仅对可证明总可判定的纯行级 exists/missing 及其合规组合豁免该特定样本要求；未知算子默认需诊断验证。前提/触发/排除所有树都纳入。算子逻辑的总可判定不等于整条链的权限、映射、适用性和来源永不未知。共享算子能力注册，并为发布分类与真实求值器建立对照测试。

禁止：完全删除诊断门、为不可达状态伪造金标准、仅再添几个当前案例关键词、批量回填过去发布资格。

## 4. R26-02｜自动化检查、医学核验与授权须分开（P0 边界，SC+HD）

`w04_s2_all_topics.py::_candidate_usability` 只检查类型在允许集合、证据存在且 locator/quote/source 对应、required_actions 非空。其 `step3_adjudicate` 随后自动写“医学经理复核（W04-S2 批量裁决）”原因并调用用户 decision 接口。

结构与来源绑定验证有价值，却不能独立证明“从原文到规则的含义正确”，也不能证明独立第二模型或医学经理实际审阅了规则。应核对具体执行证据；不能因脚本运行在本地用户身份下，就将技术校验描述成人类医学确认。

详细 W04 台账还写明本地 medical_director 映射在“用户问询未答复后按推荐方案执行”；最新 closeout 则称授权决策。可见材料不能将未答复变成明确授权。当前不删除历史审计、不擅自撤销既有记录，也不继续扩大权限或替用户追加签名。补齐真实授权范围与执行主体类型，不能补造历史。

产品建议：规则治理可以保留为可选管理模式；普通监查仍直接呈现风险和 Query 草稿，不增设风险逐条确认或外部流转。不要全仓库删除审批功能，也不要将新规则治理面板变成原始资料阅读或既有可靠结果的必经门。

## 5. R26-03｜历史结果不应因为代码升级而不可读（P0，SC+HD）

`result_context_service.load_public_result_context` 在读历史 token 时调用当前 `_build_r5_publication_packet`，然后比较发布时冻结 digest。HD 已实际记录：severity 语义更新后旧 token 的 digest 不匹配、无法打开，处理方式为新 prepare-and-start + 新发布。

拒绝错误 digest 是正确保护；**必须使用当前代码重建旧 packet、因而无法保留历史阅读能力，是尚未关闭的实现缺口**。不能将两者一起标“不是回归”。重新发布可以产生新结果，但不恢复旧结果身份。

应冻结发布时可读取的 Finding/事件/风险/来源关联模型，或者保存可验证且兼容的旧投影 recipe。版本升级形成新 revision；旧结果可历史只读并标策略已更新。确有不安全旧结论可撤回医学使用资格，但应保留真实历史与理由，不静默覆盖。禁止降低 digest 检查、直接改旧 publication.digest 或用 active 补造旧内容。

## 6. R26-04｜Finding 与 QueryDraft 的冻结阅读模型仍未分开（P1，SC+HD）

`ResolvedResultContext.public_findings_envelope()` 在 payload.findings 缺失时直接返回 payload.query_drafts，并将其命名 findings。两者不是同一个对象合同。HD 也承认草稿卡无 subject_ref、旅程按钮 disabled，只能从另外的风险列表进入。

要求：冻结不同类型的对象，公开 API 由明示 adapter 做完整映射；Finding 保留 finding_id、subject/site、事件/时间窗、逐条证据和状态。QueryDraft 有自己的 ID，引用 Finding，不替代 Finding。合法0发现完整输出空集合，不用 truthy 条件保留另一组旧值。

每个问题必须能走“问题→该受试者→对应事件/时间窗→准确来源→回到原问题列表”，不是“别的入口能打开同一个人”就视为通过。

## 7. R26-05｜Journey 默认适配有进步，但几何/渲染/交互尚未贯通（P1，SC+PX）

### 7.1 fit、密度和空间

默认zoom0使用容器宽度，PX宽1000时输出1000，修复有效。但仍强制 `Math.max(640, containerWidth)`；实际绘图区500时输出640，宽屏中的窄主栏仍可溢出。

“全程/更密/更疏”只是同一 zoomLevel 的新文案。该变量仍同时影响 px/day、聚合和标签，没有独立 timeViewport/detailDensity。默认 full fit 仍无全程缩略+局部聚焦机制。不要把 comment 或按钮名称当作解耦实现。

### 7.2 时间语义与无损显示

- `2025-09-UK` 已拒绝；`2025-09` 仍补成09-01，`2025-09-01-99`仍按合法前缀接受。
- pending 检查只识别 date_precision='partial'，不完整消费现有 dateState/date_state='partial'。
- 无日期时 hasValidDates=false 是正确元数据，但返回的日期仍是2026-01-01至01-31，DomainTracks仍无条件使用它画日期窗/刻度。
- xFor 窗内返回number、窗外返回object；普通marks做了解包，aggregates没有。窗外聚合最终形成 `[object Object]px`。
- beyond标志没有贯通可视符号/读屏文案，结束越界也没有完整保留；仍有边界同日误读风险。
- ongoing/end_unknown 新增了几何标签，但布局只给 interval 非零width，渲染只对 interval 使用条形；其余仍走点分支。
- 非空无效访视日期会进入 positionedVisits，随后被filter掉；没有进入pendingVisits。PX再现输入1条、轴上0条、待确认0条。
- 仅pending事件的域，lane.eventCount=0，却显示“无记录”；应区分无记录与有未定位记录。

### 7.3 聚合与返回

可展开和键盘路径已有进步；但 `expanded = containsSelected || expandedSet.has(key)` 导致当前选中成员所在组无法显式收起，焦点目标也可能不挂载。成员内容仍主要为内部event_ref。应显示日期/事件名称/记录号，ID留作稳定身份。

返回按钮和scroll锚点恢复应保留；补筛选/排序/时间域/密度/选中/焦点恢复。不要只用replaceState再加一个固定返回按钮代替正常浏览历史语义。是否采用pushState应与既有路由白名单/站内返回同时验证，不强行改整个路由系统。

## 8. R26-06｜命题比较加否决有效，但集合不能表达归属（P0 医学质量，SC+PX）

简单“ALT升高 vs ALT降低”已被新极性否决拒绝，同义升高/上升仍可配对，应保留。

PX仍得到agrees=True：
- ALT升高、AST降低 vs ALT降低、AST升高；
- 本次3级、既往1级 vs 本次1级、既往3级；
- 事件A给药前、B给药后 vs A给药后、B给药前。

原因是对象、属性、时间和比较方向被拆成集合，只检查有交集。单侧没有方向/时序信息也不自动意味着支持。继续添加当前句子的词表不会解决归属问题。

实施：匹配“同一问题”与判断“同一主张是否被支持”分两步；使用实体/事件ID、属性、数值单位、基线、比较时间、否定与条件绑定的命题。缺一侧资料保留核验不足，不默认同意；不把系统无法解析的情况强制变为医学经理签名任务。无发现是合法终态。

## 9. R26-07｜计量 finally 修复伴随 heartbeat 失租约错误被忽略（P1 并发，SC+PX）

`_run_with_heartbeat` 的线程仍收集 heartbeat_error，但新增 finally记账后原先的heartbeat_error检查和结束heartbeat不在该路径中。PX令初始心跳成功、后台心跳抛异常、provider返回合法对象：函数仍正常返回输出。
