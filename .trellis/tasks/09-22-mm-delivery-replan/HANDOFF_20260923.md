## 1. 这项工作要解决什么

目标不是做一套能展示的医学监查看板，而是交付可由资深医学监察员实际使用的完整本地产品。用户添加 Excel、PDF、Word 后，系统应自己理解研究身份、表和字段、方案、研究者手册及标准版本；明确内容自动处理，只把少量真正会改变医学判断、且系统无法从证据中排除的歧义交给用户。用户不应逐列确认，也不应看到模型、候选、正式事实、只读等工程术语。

完整目标包括：

- 日常定期增量监查；
- 锁库前全量及多轮修订增量监查；
- 锁库后至 CFDI 核查前的固定全量报告、中心和个例自查包；
- AE、MH、CM、试验药物、PD、入排、疗效、安全性、实验室等适用医学域的深度核查；
- 研究与中心看板，含“知情同意→筛选→治疗→研究状态”的流向和表格；
- 受试者全宽真实时间访视轴、八类临床轨道、真实数值趋势、风险定位、原始来源下钻和 Query 草稿闭环；
- 五个真实项目各至少一次真实全量；存在兼容双快照时完成真实增量；
- 三种监查模式、报告、备份恢复、一键启动、性能基线和用户验收全部完成后，整个目标才可标记 complete。

产品不得把特定疾病、药物、量表、风险或某一种表格格式硬编码进临床逻辑。真实资料用于打磨通用 harness 和提示框架。医学写作业务和 assets 不属于本任务修改范围。原始临床文件只读，处理结果进入隔离目录。

## 6. 踩过的坑和已采取的处理

### 坑一：配置界面保存会丢模型能力参数

之前用户修改连接后，输出预算、分片大小和额外请求头可能被 API/UI 省略，造成设置被擦除。现已把这些字段纳入 profile API 和界面，保存后不会丢失。

### 坑二：盲核错误读取主分析的输出预算

原实现从全局主角色解析预算，导致 DeepSeek 即使 profile 写了更大预算也没有生效。现改为从当前精确绑定的 service runtime 读取，主分析和盲核各用自己的预算。

### 坑三：DeepSeek 高推理会只返回思考过程

12 字段分片即使给 131072 输出预算，仍多次只返回 reasoning，最后 `finish_reason=length`，没有最终 JSON；4 字段明显改善但仍有随机残差。系统的正确行为是 fail closed：思考过程永不作为医学内容，失败保留为覆盖缺口。

当前第二轮失败分类：GLM 22 个 `invalid_ai_output`、4 个 `provider_runtime_error`；DeepSeek 2 个 `invalid_ai_output`、20 个 `provider_runtime_error`。DeepSeek 的主要具体原因是 reasoning-only。不要把这些失败改写成两模型一致。

### 坑四：重复代际和大分片遗留会浪费调用

已退休 77 个未开始的大分片 DeepSeek 作业和 87 个意外创建的 CMS 默认命名空间作业，均保留不可变退休标记。另有一个 12 字段诊断作业已经耗尽，不要再次恢复。恢复时只处理当前两个 digest：

- CMS：`8614ec804eb5fbb59beb`
- DeepSeek：`b5d8bf9c442618b57c75`

### 坑五：暂停时不能直接杀服务

本次先通过产品 API 把队列置为 paused，再等待 8 个在途调用自然降为 0，最后停止 8920。这样未开始作业保持排队，已开始作业完成或失败后正常写入，没有 running lease 残留。
