# 医学监查子系统国内成熟产品批判性借鉴 - 2026-07-08

## 目的与边界

本记录回应用户对医学监查子系统的补充要求：参考国内成熟产品，例如杉云平台，但不直接等同于改功能或加模块。

本记录只作为产品与架构参考，不作为商业宣称，不代表当前工作台已经具备相同能力。所有采纳项必须回到本项目的真实输入边界：当前日常医学监查以用户手动上传 EDC 导出 data listing 为主，RUX-03-002 试点必须从原始 listing 和研究方案重新构建风险、事件和可视化，不能使用既有 skill 成品或已解构结果替代。

## 产品事实层抽象

1. 杉云 iMRDP 的外部可见定位（基于官网搜索摘要和页面标题，未访问产品演示、试用账号或完整产品文档）接近“医学监查数据平台”，关键词集中在 Patient Profile、可视化图表/报表、数据信号和风险识别。
2. 国内大型临床数字化平台更常见的是一体化临床研究平台定位：CTMS、EDC、远程监查、eTMF、RBQM、数据管理等整合，而不是单纯医学经理工作站。
3. 国内公开讨论中的 RBQM 更偏“质量管理/数据管理/运营监查”共同场景，医学经理视角需要从这些系统里抽取医学复核、受试者级数据解释和方案规则闭环，而不是复制运营平台。
4. 从有限公开信息推断，这类成熟产品的共性可能不是炫酷大屏，而是多源数据聚合、异常/风险队列、受试者级 drill-down、审计留痕、角色协同和问题关闭证据。

## 可批判性借鉴

### 1. 借鉴：医学监查入口应是风险队列 + 受试者 drill-down 双入口

杉云 iMRDP 这类产品将 Patient Profile、数据信号和风险识别放在同一医学监查语境下，这是值得借鉴的。我们的医学监查首页不应只有项目风险卡，也必须保留两个稳定入口：

- 风险队列入口：按风险项、严重程度、规则来源、受试者、中心、未读/待处理状态进入。
- 受试者入口：直接进入 Subject Timeline 和 Patient Profile，查看事件时间轴、疗效/安全性历时趋势和相关风险提示。

当前工作台已朝这个方向走，后续应把“进入 Subject Timeline / Patient Profile”从演示按钮升级为与风险项绑定的正式跳转对象。

### 2. 借鉴：Patient Profile 是医学监查主界面的一等对象

杉云对 PP/可视化图表的强调，和既有 Veeva/JMP/开源 patient profile 参考一致。我们的 Patient Profile 不应只是图表集合，而应成为“个例医学解释界面”：

- 基本信息、分组/访视、入组状态。
- 疗效指标历时变化。
- 安全性指标历时变化。
- AE、CM、MH、PD/Query、试验药物变更与实验室结果联动。
- 来源行号、规则、医学解释、待确认项。

已经明确的边界：CM 只代表非试验用合并用药/治疗；`dose_adjustment` 和其他试验药物相关变更应单列在 Subject Timeline/Patient Profile 的试验药物变更语义中。

### 3. 借鉴：RBQM/风险监查要以可关闭的问题闭环为中心

成熟平台和监管文件都强调基于风险、成比例、可沟通、可处置。我们不能只做“风险热力图”，而应为每个医学关注项提供：

- 风险类型和规则来源。
- 源数据定位。
- 触发证据。
- 推荐复核动作。
- 责任角色。
- 未读/已读/处理中/已关闭状态。
- 关闭依据和审计记录。

这也支持用户此前要求：不要把“自上次查看以来”做成进入后自动消失，而应做成未读项，只有点击进入或明确标记后才变为已读。

### 4. 借鉴：多系统整合能力要体现在接口，不要在 P0 硬接大平台

太美、泰临研这类一体化平台覆盖 CTMS/EDC/eTMF/RBQM 等，说明未来公司内网私有化或多端部署需要保留系统集成能力。但本项目 P0 不能假装已经直连 EDC/CTMS。

当前正确做法：

- P0：手动上传定期 data listing，记录批次、字段映射、diff 和规则输出。
- P1：支持文件登记、来源注册和半自动批次更新。
- P2：若临床运营系统或 EDC 可接入，再做 API/数据库/消息队列自动触发。

### 5. 借鉴：平台级视角和医学经理视角要分层

国内成熟平台多面向申办方、CRO、数据管理、运营、中心、PV 等多角色。我们的首版用户统一为医学经理身份，因此不应把 CTMS 任务、CRA 访视执行、中心启动、招募运营直接放进医学监查。

可保留的底层设计：

- `owner_role`
- `target_page`
- `source_type`
- `handoff`
- `approval_gate`
- `audit_event`

但首版可见界面应聚焦医学经理：医学风险识别、医学复核、个例解释、锁库前医学核查、写作/TFL/PV交接。

## 不应照搬

1. 不照搬通用 CTMS/EDC 首页。医学经理工作台不是运营项目管理系统，不能让医学监查首页被启动、招募、中心访视执行等信息淹没。
2. 不照搬“平台能力大而全”的宣传逻辑。功能必须由真实 raw source 测试通过后才在系统中宣称。
3. 不把 RBQM 简化成热力图。热力图只能做导航，医学监查真正价值在风险解释、证据定位、处置闭环和审计留痕。
4. 不把 AI 建议变成自动医学结论。系统可以生成“待医学批准的正式内容”，但必须保留来源、模型、验证、人工确认状态。
5. 不把合并用药和试验药物调整混用。CM 是非试验用药/治疗；研究药物暂停、恢复、剂量调整和其他研究治疗变更必须单列。

## 对当前医学监查子系统的设计影响

### 已确认需要坚持

- 医学监查首页：风险队列优先，右侧/下钻显示风险详情，不再让详情缩在不重要区域。
- Subject Timeline：以访视为轴，事件按 study day/date 定位；图中只放紧凑编号块，详情放在明细区。
- Patient Profile：展示疗效、安全性指标历时变化，不只是静态表格。
- RUX：从原始 listing + 原始方案重新解析，不能复用 SAR/MG-K10 skill 成品或既有解构结果。
- 项目总看板：风险项使用未读状态，不使用进入后自动消失的“自上次查看以来”。

### 新增到后续产品 backlog 的候选，不立即实现

1. 医学监查“信号/规则目录”页：展示规则版本、适用方案章节、启用状态、受试者命中数、最近一次批次命中差异。
2. 项目级医学监查矩阵：按中心、受试者、风险域、访视窗、规则组汇总，支持从矩阵跳到个例时间线。
3. 数据批次差异视图：同一受试者同一事件在两个 listing 批次中的新增/删除/变更。
4. 医学处置闭环：风险项进入“待医学确认 -> 处理中 -> 待补充证据/已关闭/升级PV/写作引用候选”的状态机。
5. 平台集成适配层：未来 EDC/CTMS/eTMF/PV 接入时只替换 ingestion adapter，不改变前端业务对象。

## 当前优先级判断

这些国内产品参考不改变当前短期优先级。优先级仍然是：

1. 医学监查：RUX-03-002 真实 listing + 方案的端到端风险、Subject Timeline、Patient Profile 和 inbox 路由。
2. 入排审核：D001 原始入排资料从零开始进入统一接口。
3. 医学写作：研究方案优先，富文本编辑、证据绑定、AI交互修订和审批留痕。

参考成熟产品后的主要调整不是立即增加页面，而是提高验收标准：每个风险和每个受试者视图都必须证明其来源、状态、处置路径和审计闭环。
