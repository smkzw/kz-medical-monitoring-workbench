# 医学监查子系统 PRD 审阅与差距矩阵

**文档性质：** 内部审阅、实施决策与交接依据  
**审阅对象：** 《医学监查子系统说明书》V1.0  
**审阅结论：** 原说明书已经形成较完整的目标能力框架，但仍需把“目标态、当前实现、正式验收”分开，修正若干审批与 AI 语义，并补齐真实增量、独立 AI、总系统集成、并行开发隔离和发布门。  
**使用方式：** 本文用于解释为什么修改 PRD、下一阶段先做什么以及什么证据才可视为完成；不作为面向最终用户的页面内容。

---

## 1. 审阅目标与判断原则

本轮审阅不推翻既有架构，而是解决四类问题：

1. **医学工作流是否真实：** 是否符合医学经理拿到方案和定期 EDC data listing 后的实际工作顺序。
2. **目标与现状是否分开：** 文档描述的是应达到的能力，还是已经由两个真实项目、多个批次和完整交互验证过的能力。
3. **跨项目是否可泛化：** 是否依赖某一项目的表名、访视、阈值、适应症术语或预先解构产物。
4. **是否能无冲突接入总系统：** 项目、来源、方案事实、风险、处置、未读和审计是否只有一个权威数据对象，并与并行开发的医学写作子系统明确读写边界。

审阅采用以下证据优先级：

| 优先级 | 证据 | 用途 |
|---|---|---|
| 1 | 用户较新的明确要求 | 业务边界和产品决策 |
| 2 | 当前原始方案、原始 listing 与真实运行结果 | 功能和科学性验证 |
| 3 | 当前代码、接口契约和自动化测试 | 判断已实现范围 |
| 4 | 系统及子系统任务记录、踩坑记录 | 解释历史决策和恢复边界 |
| 5 | 监管指南、官方产品资料与成熟产品模式 | 校正目标方案，不代替本地验证 |
| 6 | 其他模型或代理的意见 | 独立挑战意见，不作为完成证据 |

## 2. 不可退让的业务合同

### 2.1 输入与运行时点

- 日常医学监查的主要输入是医学人员手动上传的、EDC 定期导出的**最新全量 data listing**。
- 日常监查不得假定已有 SDTM 或 ADaM；标准化数据集主要在锁库后才可能获得。
- 自动接入 EDC 或临床运营系统是未来能力，本地首版不得用“未来自动接入”掩盖当前手动流程缺口。
- 每个真实项目必须从**原始方案与原始 listing**开始，不得把既有时间线、患者概览、已解构方案或风险结果当作工作流起点。

### 2.2 三种运行策略，一套底层事实

| 运行策略 | 输入特点 | 核心差异 | 共用底座 |
|---|---|---|---|
| 日常医学监查 | 定期最新全量 listing | 以上一已确认批次为基线，突出新增、变化、重开和未读 | 方案事实、规范化事件、规则、风险对象、证据和处置 |
| 锁库前整体医学监查 | 候选冻结数据 | 全量重算、覆盖核对、开放项和关闭依据 | 同上 |
| 核查前总结性自查 | 当前冻结数据及历史处置 | 受试者、中心、试验三级聚集和证据包 | 同上 |

不得为三种运行策略复制三套规则或风险台账。

### 2.3 关键医学边界

- CM 仅指非试验用药或治疗。
- 试验药物给药、漏服、多服、暂停、减量、加量、停药、重启和其他剂量调整进入独立数据域、独立风险类别和独立时间线泳道。
- 系统只能生成疑似 AE 漏报、疑似 MH 漏报、潜在 PD、CS/NCS 评价需复核等**候选风险**，不能自动确认医学事实。
- 用户作为医学经理确认、修改或采纳某项候选后，该项在当前医学监查工作中即为已确认结论，不得再次泛化显示“待医学批准”。
- 正式向 EDC 发出 Query、升级为组织级 Finding、需要医学总监或其他角色批准的情形，按项目配置进入后续组织流程；系统不得默认所有医学操作都需二次审批。

### 2.4 用户界面

- 所有子系统按桌面端设计，移动端不是验收目标，不能为了移动端删减桌面功能。
- 模块名称只写“医学监查”，不出现“第几环节”。
- 风险清单默认只保留七列：受试者编号、中心编号、风险级别、风险类别、具体风险项、当前处置、更新时间。每列可排序、筛选。
- 详情中必须先显示“原始事实是什么”，再显示文件、工作表、行号或段落定位。
- 风险详情是主要工作区，不得压缩在次要窄栏。
- Checklist、Subject Timeline、Patient Profile、AE/MH 核查、PD/用药规则和来源证据应在同一叠加工作区互相打开，并保留当前风险、受试者、筛选和滚动位置。
- “未读”表示用户尚未查看，不等于风险消失；打开风险后仅更新已读状态，不删除或隐藏风险。

### 2.5 Subject Timeline 与 Patient Profile

**Subject Timeline：**

- 以方案访视和实际日期构成时间轴，事件按时间位置分布在轴下方的泳道中。
- 不得退化为按访视排列的一组卡片，也不得使用低信息密度的瓷砖式布局。
- AE、MH、CM、试验药物/剂量调整、实验室/检查、疗效、访视/PD 等事件类别使用不同颜色。
- 颜色首先编码事件类别；风险严重程度使用边框、图标或标记编码，避免一套颜色同时表达两种含义。
- 试验药物/剂量调整必须与 CM 分开。

**Patient Profile：**

- 同时支持疗效和安全性指标的历时变化。
- 显示实际日期、访视、基线、参考范围、正常上下限、单位、计划外访视、重要治疗事件和风险锚点。
- 点击数据点能够看到原始值、访视、日期、参考范围、CS/NCS、来源正文及关联风险。
- 个体层面保留计划外访视；中心和试验层面的按访视汇总默认不混入计划外访视，除非项目规则明确指定。

## 3. 当前实现真值表

状态定义：

- **已验证：** 已有代码、自动化测试和真实运行证据支持，但仍需纳入最终发布回归。
- **部分实现：** 存在界面或服务，但完整业务链、跨项目泛化或正式验收未闭环。
- **目标设计：** PRD 已描述，但当前不能对外承诺为可用能力。

| 能力 | 当前状态 | 已有证据 | 主要缺口 |
|---|---|---|---|
| 两个真实研究的原始来源登记与项目目录 | 已验证 | 真实方案/listing 目录、受试者和中心下钻、来源修订记录 | 仍需第三个结构差异明显的项目验证泛化 |
| 内容基本信息与内容适配校验 | 已验证 | 项目/适应症/文件类型/版本检查、可覆盖提醒和不可覆盖技术失败 | 覆盖理由、批次基线选择需纳入统一 UX 回归 |
| 方案/来源内容修订与并发控制 | 已验证 | 修订号、来源变化失效保护、过期写入拒绝 | 需与总系统统一 Source Registry 契约 |
| 统一医学风险对象和处置 | 已验证 | 风险标识、七列清单、状态/处置、批次历史、跨视图入口 | 风险语义键与批次实例的迁移规则需固化 |
| 受试者时间线 | 部分实现 | 真实项目受试者级入口、访视轴和事件下钻 | 泳道信息密度、类别颜色、稀疏数据、精确风险聚焦仍需逐项回归 |
| 患者概览 | 部分实现 | 真实项目疗效/安全性趋势入口 | 项目级指标自动配置、计划外访视、中心/试验汇总和盲态策略需完善 |
| Safety/PV 风险投影 | 已验证其只读投影边界 | 共享风险标识、Safety/PV 标签、独立文档审阅边界 | 需在总系统导航和权限层正式接线 |
| 独立 AI 语义辅助 | 部分实现/待正式验收 | 已有接口和提示词框架 | 必须证明不依赖开发代理；需真实运行、超时/失败/低置信度降级和提示词回归 |
| 真实增量批次导入与差异执行 | 部分实现 | 不可变来源修订、差异服务雏形、真实项目多文件研究 | 真实文件存在结构漂移且无 CHANGE_FLAG；当前生产入口尚未完成项目中立的逐行/逐字段差异闭环 |
| 锁库前全量医学监查 | 目标设计 | PRD 流程和规则复用设计 | 未完成冻结版本、全域覆盖、开放项和关闭依据的完整演练 |
| 核查前三级总结性自查 | 目标设计 | 统一风险和三级汇总设计 | 未完成受试者/中心/试验级可回溯的一致性演练 |
| Query 正式发送与回复闭环 | 目标设计 | Query 候选草稿和处置接口 | 当前只应承诺候选与内部记录；外部发送、回复、重开需后续接入 |
| 身份、RBAC、电子签名 | 目标设计 | 本地持久化和审计基础 | 首版统一医学经理身份；多角色、组织目录和适用电子签名留作私有化部署能力 |
| EDC 自动接入 | 未来能力 | 接口边界预留 | 当前不在首版范围 |

## 4. 主要差距与优先级

### P0：不解决则不能进入正式产品 LOOP

| 编号 | 差距 | 风险 | 要求 |
|---|---|---|---|
| P0-01 | 目标态与已实现态混写 | 对外误报已上线能力 | 主 PRD 新增实现真值和发布门；任何状态以正式验收记录为准 |
| P0-02 | 独立 AI 尚未形成可重复的产品内证据 | 开发代理能力被误当成产品能力 | 用产品配置的独立 AI 从原始文件执行语义映射、证据摘要和候选分析；开发代理仅评测 |
| P0-03 | 真实增量流程未闭环 | 日常监查核心价值无法成立 | 建立不可变批次、基线、项目级业务键、结构漂移门、行/字段差异和风险迁移 |
| P0-04 | 风险身份语义不够清晰 | 旧处置错误继承到新事实 | 区分稳定 `risk_key` 与来源/批次绑定的 `risk_instance_id`；定义 continuation、reopen、supersede |
| P0-05 | 并行子系统仍共享大型前端文件 | 与医学写作并行开发冲突 | 先建立文件所有权和模块挂载点，再拆分医学监查功能目录；共享契约只做兼容扩展 |
| P0-06 | 医学确认与组织审批混用 | 用户重复审批、状态含义错误 | AI 候选由医学经理确认后即生效；仅配置的外部流程进入额外审批 |
| P0-07 | 当前仅两个真实项目 | 项目硬编码或隐性过拟合难发现 | 正式门至少纳入三个结构差异明显的真实研究，从原始文件开始 |

### P1：核心体验和医学可用性

| 编号 | 差距 | 风险 | 要求 |
|---|---|---|---|
| P1-01 | Timeline 仍可能退化为低密度卡片或元素冲突 | 医学人员无法快速理解事件链 | 固定访视轴、类别泳道、颜色规范、碰撞消解和密度分级 |
| P1-02 | Patient Profile 项目指标配置仍偏项目适配器 | 新适应症趋势图不完整 | 从方案终点、安全性计划和 listing 字段联合生成指标集候选，经医学经理确认 |
| P1-03 | 证据面板可能优先显示定位而非事实 | 复核成本高 | 统一“事实正文→方案依据→规则理由→定位折叠”的顺序 |
| P1-04 | 清单和详情的筛选/定位状态可能丢失 | 来回切换效率低 | 统一路由上下文和 exact-focus 参数，返回时恢复筛选、滚动和选中风险 |
| P1-05 | 大项目首轮加载和全清单查询慢 | 用户误以为卡死 | 预计算风险索引、异步进度、可取消/可重试、缓存和明确空态 |
| P1-06 | 稀疏受试者数据曾导致白屏 | 边缘病例不可用 | 所有集合返回完整空结构，前端逐域降级，不伪造数据 |

### P2：私有化部署和组织协作

| 编号 | 差距 | 要求 |
|---|---|---|
| P2-01 | 多角色权限未开放 | 首版只开放统一医学经理；保留角色、动作和项目范围字段 |
| P2-02 | Query/PD/Finding 外部系统未接入 | 先提供候选、关联和导出契约，未来接入时不复制风险对象 |
| P2-03 | EDC/运营系统自动触发未实现 | 保留事件接口和幂等键，当前明确用户手动上传 |
| P2-04 | 内网多节点部署未验证 | 保持存储、任务队列、文件对象和 AI 网关可替换，不在本地首版硬绑定 |

## 5. 历史踩坑及制度化修正

| 踩坑 | 根因 | 制度化修正 |
|---|---|---|
| Timeline 与参考成品视觉差异大 | 只模仿“有时间轴”，未理解访视轴、泳道和信息密度 | 以业务语义和原始构建逻辑为合同，截图仅作视觉验收 |
| CM 与试验药物混淆 | 事件模型边界不清 | 数据域、规则类别、颜色、泳道和筛选标签全链路分开 |
| 风险详情缩在右侧小区域 | 页面按卡片均分而非按医学任务优先级设计 | 风险列表为导航，详情为主工作区；采用底部/侧边大叠加层 |
| 来源只显示行号 | 把技术溯源当成医学证据 | 强制生成可读事实句，定位放在次级折叠区 |
| “自上次查看以来”进入页面即消失 | 未读与风险存在性混为一谈 | 已读只更新阅读状态，不改变风险或筛选结果 |
| 稀疏受试者白屏 | 后端缺失域返回形状不稳定 | 契约化空集合和缺失原因；前端按域显示空态 |
| 选择器/筛选恢复竞态 | 路由、筛选和异步数据分别管理 | 单一页面上下文对象，加载顺序和回退状态可测试 |
| 中心筛选残留到 Patient Profile | 跨视图隐式复用筛选 | 明确受试者级、中心级和试验级上下文，不自动继承不适用筛选 |
| 真实文件没有 CHANGE_FLAG | 沿用演示数据假设 | 对完整快照自行计算差异，不依赖来源额外标记 |
| 多批真实 listing 结构漂移 | 默认表名和列结构稳定 | 每批先做结构差异门；映射迁移由配置和 AI 候选共同完成 |
| 同一源文件更新后旧处置仍显示 | 处置未绑定来源修订 | 风险实例绑定来源、方案、规则和映射修订；变化触发重新复核 |
| 截图受试者与验收目标不一致 | 只验证页面“有内容” | E2E 合同必须声明项目、受试者、风险和预期焦点 |
| 版本号和技术状态占据用户页面 | 把运行日志当作产品信息 | 版本与审计进入详情/系统页；主工作区只展示影响任务推进的信息 |
| 大型 `App.jsx` 造成并行冲突 | 子系统未形成清晰挂载边界 | 先拆分路由和模块壳层，再由各子系统独立迭代 |
| API 修改后仍看到旧行为 | 服务未重启或前端缓存 | 每轮验证记录运行版本、进程、构建哈希和重启证据 |
| 测试误收集备份文件 | 备份落在测试发现路径 | 快照和临时文件放入专用归档目录，不进入测试收集范围 |

## 6. 对原 PRD 的具体修订决定

| 原位置 | 原问题 | 修订决定 |
|---|---|---|
| §1.3、§38 | 目标、能力和待验证有定义，但缺现状清单 | 增加“当前实现真值与剩余缺口”章节 |
| §3.3 | “待批准的数据质疑草稿”易被理解为医学选择仍未生效 | 改为“数据质疑候选草稿”；是否正式发送由项目流程决定 |
| §5、§26 | 多角色和审批链被写成首版默认流程 | 明确首版统一医学经理身份；目标角色保留但默认不开放 |
| §6.3 | “医学总监/经理批准”范围过宽 | 改为医学经理完成处置；高风险升级或外部动作按项目配置 |
| §6.2 | 只有 `risk_instance_id`，缺稳定语义键 | 增加 `risk_key`、来源绑定和实例迁移规则 |
| §7 | 内容校验与技术安全校验边界不够突出 | 明确只做技术可读性和内容适配，不设置重型文件安全流程 |
| §10 | 差异机制目标正确，但未突出真实文件无标记 | 增加不可依赖 CHANGE_FLAG、不可变批次、删除完整性证明和结构漂移门 |
| §22–25 | 交互原则已覆盖，但需固化颜色和 exact-focus | 增加类别颜色、严重度第二编码、路由焦点和事实正文格式 |
| §26 | AI 边界未明确开发代理不能替代产品 AI | 增加产品内独立 AI、提示词治理、失败保护和真实运行验收 |
| §27–29 | 总系统共享边界缺失 | 增加项目、来源、方案事实、风险、未读、审批和模块挂载契约 |
| §30、附录D | 多项目验证数量和全功能 LOOP 不够具体 | 发布门至少三个真实项目、每个按钮/隐含逻辑、三种运行策略和独立 AI |

## 7. 总系统与并行子系统集成风险

### 7.1 权威对象和写入所有权

| 对象 | 权威所有者 | 医学监查权限 | 其他子系统权限 |
|---|---|---|---|
| 项目主数据 | 总系统项目服务 | 读取；创建监查配置 | 读取；各自创建模块配置 |
| 来源文件与内容修订 | 共享来源登记服务 | 登记 listing、方案和补充材料的模块用途 | 可登记自身来源；不得覆盖他模块绑定 |
| 方案事实/规则条款 | 共享方案事实服务 | 读取并创建监查规则绑定；医学确认后写回事实修订 | 入排和写作可创建候选或读取确认事实；不得直接改监查处置 |
| 医学风险 | 医学监查风险库 | 唯一写入所有者 | 总看板和 Safety/PV 只读投影；其他模块通过关联而非复制 |
| 医学处置与未读 | 医学监查风险库 | 唯一写入所有者 | 总看板只读统计；审批中心仅对配置动作写审批结果 |
| 写作文档 | 医学写作子系统 | 只读项目事实，不修改文档 | 医学写作唯一写入 |
| Safety/PV 文档审阅 | Safety/PV 协作模块 | 只读关联风险；可建立关联 | PV 文档模块写入其审阅对象，不复制风险事实 |

### 7.2 并行开发约束

1. 在修改共享文件前建立“文件—会话—所有者—预计完成点”清单。
2. 工作区无版本控制时，修改前记录哈希并创建可恢复快照；不得用覆盖式拷贝合并。
3. 医学监查和医学写作分别挂载独立前端模块，避免两条会话同时大幅修改同一根组件。
4. 共享接口采用版本化、向后兼容和消费者契约测试；新增字段默认可选。
5. 共享设计令牌、导航壳层、项目选择器和通知样式统一；业务页面的信息架构由各子系统独立负责。
6. 总看板只读取子系统摘要和未读计数，不维护第二套风险状态。
7. 发生冲突时先以数据所有权和当前运行契约判定，不以任一会话的较新文件时间直接覆盖另一会话。

## 8. 发布判定建议

医学监查子系统只有同时满足以下条件才可进入“可上线”状态：

1. 至少三个结构明显不同的真实临床研究，从原始方案和原始 listing 开始完成全流程。
2. 至少一个研究使用两个以上真实连续批次完成新增、变化、持续、条件不再满足、重开、来源修订和结构漂移验证。
3. 日常医学监查、锁库前全量重算、核查前三级汇总各完成一次完整演练。
4. 规则覆盖 AE/MH、CS/NCS、试验药物/剂量调整、CM 禁限用药、访视/时间窗、入排持续合格性、AE/SAE/AESI、疗效/量表、跨表逻辑。
5. 产品内独立 AI 能在不依赖开发代理的情况下完成字段语义候选、方案条款结构化候选、风险证据摘要和用户追问；失败时确定性流程仍可用。
6. 每个页面按钮、筛选、排序、导出、详情、叠加页签、处置、冲突、空态、失败和重试均实际点击测试。
7. Timeline 与 Patient Profile 通过医学语义、视觉、稀疏数据和跨项目回归。
8. 原始事实正文、方案依据、系统规则、计算过程和次级定位能够逐条回溯。
9. 与总看板、项目主数据、来源登记、方案事实、Safety/PV 和审批中心的消费者契约通过；不修改医学写作文档。
10. 真实桌面浏览器验收、API 契约、持久化重启、并发冲突、性能和审计证据完整。

在任一 P0 项未通过时，只能标记为“开发/验证中”，不能用“页面可打开”或“演示数据无报错”替代上线判定。

## 9. 独立会商复核后的处理

独立临床工作流审阅、数据/系统契约审阅和综合裁决完成后，接受以下文档修订：

| 修订 | 处理 |
|---|---|
| 字段映射候选虽已描述，但日常流程缺少用户确认门 | 已在主 PRD §9.1–§9.2 明确批量确认、`mapping_revision`、关键域阻断和非技术用户路径 |
| “来源完整性待确认”未明确是否可成为下一基线 | 已在主 PRD §9.2 明确：可保存/限定查看，不得成为完整 diff 基线 |
| §13.3 把内部审批画成必然直接正式发送，与 §26.3 项目配置冲突 | 已改为条件路由；审批只覆盖草稿文本和发送建议，正式发送另行确认 |
| “文件角色”可能混淆来源内在类型与模块用途 | 已在主 PRD §28.4 分离 `source_content_revision`、`parse_revision` 和 module binding |
| 七列 Checklist 缺少本批次变化的扫描信号 | 保持七列不变，在具体风险项/更新时间内显示紧凑变化标记 |

以下意见不作为当前缺陷扩大范围：

- 正确执行的试验药物剂量调整应显示在 Timeline/Profile，但不另造“合规风险”。
- 不增加第八个默认 Checklist 列。
- 不设置跨项目固定中心样本量；按项目批准方法判断是否只做描述性分析。
- 不以固定点击次数或固定用时替代真实医学可用性验收。

会商同时确认，当前最高优先级实施阻断仍是：产品内独立 AI 未完成真实验收、真实增量 diff 未闭环、风险实例迁移路径未全覆盖、第三个真实项目未纳入、结构漂移/删除完整性未验证和前端大型共享组件未拆分。这些已在本文 P0/P1 和主 PRD 当前实现真值表中标为未完成，不属于文档已夸大为上线能力。
