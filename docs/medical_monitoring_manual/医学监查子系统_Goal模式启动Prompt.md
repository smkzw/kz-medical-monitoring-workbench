# 医学监查子系统 Goal 模式启动 Prompt 与使用说明

## 1. 使用说明

本文件用于下一次以 Goal 模式持续推进医学监查子系统。启动前：

1. 确认医学写作子系统的并行会话仍在运行时，不要让两个会话同时修改同一共享文件。
2. 不预先指定固定模型路由；每次执行/会商前重新读取当前全局 `AGENTS.md`，以最新路由、夜间规则、OCR/翻译并发和接受要求为准。
3. Goal 只在目标真正完成、用户明确暂停，或连续多轮遇到同一不可解阻塞并达到 Goal 阻塞条件时结束。不要阶段性自行暂停。
4. 不设置 token 预算，除非用户另行明确指定。
5. 把下方“Goal Objective”作为 Goal 的目标，把“完整启动 Prompt”作为第一条工作指令。

### Goal Objective

> 将医学监查子系统从当前已验证基础推进至可上线状态：以真实方案和定期全量 EDC data listing 为输入，完成日常增量医学监查、锁库前全量监查、核查前三级总结性自查、统一医学风险 Checklist、Subject Timeline、Patient Profile、产品内独立 AI、医学处置和审计闭环，并无冲突接入医学经理工作台总系统，不回归或覆盖并行开发的医学写作子系统。

二、Goal 和完成定义

目标是交付一个能由资深医学经理真实使用的桌面端医学监查子系统，而不是演示页面。

必须完成：
1. 用户手动上传当前有效方案和定期 EDC 导出的最新全量 data listing。
2. 技术可读性和内容适配校验、来源登记、项目/版本绑定和可覆盖提醒。
3. 对连续完整快照自行计算结构、行、字段和医学语义差异，不依赖 CHANGE_FLAG 或人工预处理。
4. 方案事实和规则配置，包括 AE/MH、CS/NCS、试验药物/剂量调整、CM 禁限用药、访视/时间窗、入排持续合格性、AE/SAE/AESI、疗效/量表和跨表逻辑。
5. 七列医学风险 Checklist、可读证据、医学处置、未读、批次历史和审计。
6. 以访视/实际日期为轴的高密度 Subject Timeline；事件类别使用不同颜色，试验药物/剂量调整与 CM 严格分泳道。
7. 包含疗效和安全性历时变化、基线、参考范围、计划外访视、风险锚点和原始数据下钻的 Patient Profile。
8. 日常增量医学监查、锁库前全量医学监查、核查前受试者/中心/试验三级总结性自查。
9. 产品内独立 AI 能脱离 Codex、执行模型和会商模型独立完成字段语义候选、方案条款候选、跨表线索、证据摘要和用户追问。
10. 无冲突接入项目总看板、共享项目/来源/方案事实、Safety/PV 和配置的审批中心；不修改医学写作拥有的文档。

只有主 PRD §40 的发布门全部通过才能标记可上线。

三、不可退让的医学和产品边界

1. 日常医学监查使用最新全量 EDC listing；SDTM/ADaM 只在锁库后可能提供，不能作为日常前提。
2. 所有真实项目必须从原始方案和原始 listing 开始。禁止把既有 Timeline、Patient Profile、已解构方案、已生成风险或 skill 中间文件作为工作流起点。
3. CM 只指非试验用药/治疗。试验药物给药、漏服、多服、暂停、减量、加量、停药、重启和剂量调整必须独立数据域、独立风险类别、独立泳道和独立颜色。
4. AI/规则只能生成疑似 AE 漏报、疑似 MH 漏报、潜在 PD、CS/NCS 需复核等候选。不得自动确认医学事实。
5. 医学经理采纳、修改或确认 AI 候选后，该项即成为当前医学工作记录，不再重复显示“待医学批准”。只有正式发送 Query、高风险升级或其他项目明确配置的组织动作进入额外流程。
6. 风险详情优先展示事实本身，例如“日期—访视—检验—数值—单位—参考范围—异常方向—风险”，来源文件、工作表、行号、段落放次级溯源区。
7. 风险清单默认只有七列：受试者编号、中心编号、风险级别、风险类别、具体风险项、当前处置、更新时间。每列可排序、筛选。
8. “已读”只更新阅读状态，不让风险消失。
9. 桌面端是唯一首版体验目标。不要为了移动端删减功能。
10. 前端清爽、直观、重点突出、信息密度中等偏高。日志、技术版本、冗余警告和不影响任务推进的信息不常驻主工作区。
11. 模块名称只写“医学监查”，不出现“第几环节”。
12. 文件导入不做重型安全检查，只做技术可读性和内容适配校验；可覆盖项在充分提醒后允许资深医学人员说明理由继续，技术失败不可覆盖。
13. 首次导入或结构变化时，系统先给出字段映射候选，医学经理批量确认或修订关键域后再运行依赖规则；不要求用户编写映射文件，不允许未映射关键域静默产生空风险清单。
14. 无法证明为完整全量快照的批次可以保存和限定范围查看，但不得确认成下一轮完整差异分析基线。

四、产品内独立 AI

1. 先把独立 AI 运行时做到真实可用；若独立 AI 不可用，不得用你自己、subAgent、执行/会商模型代替产品结果继续宣称功能通过。
2. 开发代理负责架构、提示词设计、评测、问题复现和修复；产品内 AI 执行真实的字段映射、方案条款、证据摘要和交互任务。
3. 每次 AI 调用绑定 project_id、任务类型、来源修订、允许引用范围、稳定输出结构、超时和重试。
4. 提示词强制区分源事实、推断、建议和证据缺口；每项事实有可打开引用。找不到时写“未在当前授权来源中找到”，不能把“未检出”写成“没有”。
5. 禁止跨项目复用阈值、表名、访视、适应症表达或医学结论。
6. AI 超时、限流、低置信度或结构化输出无效时显示明确失败与重试；确定性规则、原始证据和人工处置仍可使用。
7. 提示词和模型升级必须使用固定跨项目回归集，并增加一个未见项目检查过拟合。
8. 如果不引入 Agent/harness 时独立 AI 确实无法可靠完成查询、文件操作或多步分析，先广泛调研成熟开源实现和最小工作流。若出现几条证据相当但架构完全不同的路径，再停在该决策点向用户汇报选择；不要暗中换路线。

五、总系统和并行开发契约

1. 一个 project_id 贯穿所有子系统。
2. 来源可多模块引用但按用途绑定，任何子系统不得覆盖另一模块的绑定。
3. 医学风险、证据、处置和未读由医学监查唯一写入；总看板和 Safety/PV 只读投影。
4. 共享方案事实包含来源、状态、适用版本和消费者。医学监查可创建候选，医学确认后形成新修订；不得覆盖医学写作文档。
5. 医学监查和医学写作必须独立路由、业务组件、状态和样式作用域；共享项目选择器、壳层和设计令牌通过稳定接口复用。
6. 共享契约新增字段默认可选并保持向后兼容。修改前列出全部消费者，修改后同时回归项目总看板、医学监查和医学写作。
7. 不得让两个会话同时大范围修改同一根组件。若发现共享文件已变化，先 diff，再迁移到独立模块或协调兼容扩展。

六、分阶段推进

严格按《医学监查子系统_分阶段实施与LOOP计划.md》的 P0–P10 推进：
P0 现状冻结与契约；
P1 模块边界与共享接线；
P2 来源/批次/真实差异；
P3 方案事实与确定性规则；
P4 产品内独立 AI；
P5 统一风险工作台；
P6 Timeline/Profile；
P7 日常监查闭环；
P8 锁库前/核查前；
P9 总系统接入；
P10 多项目全功能发布 LOOP。

阶段不按时间结束，只按退出门结束。可并行的独立工作流可以并行，但共享契约、风险身份、来源修订和前端根壳层必须串行确认。

七、真实项目和全功能 LOOP

1. 至少三个结构明显不同的真实非肿瘤临床研究，从原始方案和原始 listing 开始。
2. 覆盖不同适应症、分期、研究设计、给药方式、访视密度、listing 结构、疗效量表和安全性计划。
3. 至少一个项目具有两个以上真实连续全量批次。
4. 每个项目选择 3–5 名不同数据完整性和风险模式的受试者做逐功能下钻，同时运行全项目规则和三级汇总。
5. 每个按钮、筛选、排序、列、页签、弹层、Timeline 事件、Profile 数据点、处置、导出、冲突、空态、失败和重试都要实际操作。
6. 测试角色同时覆盖：
   - 工程师视角；
   - 懒惰但专业、视觉要求高的资深医学经理视角；
   - 医学科学性视角；
   - 桌面视觉与交互视角。
7. 每个问题执行“复现→分析根因→最小修复→原场景重测→另一项目回归→总系统/写作消费者回归”。
8. 禁止用 demo 无报错、页面有内容、测试数据已预处理或模型口头声称通过作为完成证据。

八、执行/会商方法

1. 对超过三个步骤、临床/监管高风险、外部调研、多文件代码、浏览器视觉或生产写入的工作，按当前全局 AGENTS.md 使用工作流守卫建立受跟踪任务。
2. 执行用于有边界的实现、文件修改和产物生产；会商用于独立挑战、医学边界、方案取舍和接受审阅。不要让会商重复实现同一产物。
3. 分派前写明来源、目标、范围、允许写入路径、禁止修改对象、成功标准、风险、超时和返回格式。
4. 执行者返回：来源、实际工作、观察、失败路径、证据、不确定性、下一建议。
5. 只针对执行/会商后的冲突点、风险点和缺少证据的地方复核，不重新完整遍历已经有充分证据的无问题范围。
6. 慢响应不等于失败。按当前 AGENTS.md 的硬等待、同会话续问、回退和夜间路由执行。
7. Codex 保留最终真实文件、浏览器、医学、监管、生产和用户接受权。其他模型的信心不是证据。
8. 普通中文标签和句子可直接处理；高风险医学结论需来源级验证。

九、外部调研

在采用新的重要库、解析器、Timeline 组件、图表引擎、任务框架或 AI 工作流前，按当前 AGENTS.md 做两轮外部发现：
1. 景观扫描：官方标准、官方文档、成熟产品、开源仓库和临床数据审阅实践。
2. 候选核验：许可证、维护、兼容性、数据外发、私有化、可逆性和真实集成约束。

只采用具有明确可用开源许可证且后续无需额外付费的组件。外部产品用于批判性借鉴，不照搬其云优先、移动优先、SDTM 前置或 AI 自动结论。

扫描版方案或补充资料确需 OCR 时，按当前全局 AGENTS.md 的共享资源租约、默认 OCR 路由和并发上限执行；图表页采用足以可靠识别表格结构和脚注的渲染分辨率。OCR 文本保留页码、表格/段落定位和原图入口，医学规则不得只引用无法回到原页的整理文本。医学监查通常不需要翻译；若项目资料确需翻译，同样遵循当前全局翻译路由和来源追溯要求。

十、LOOP 和记录

每轮至少记录：
- 目标、原始输入与修订；
- 本轮唯一问题；
- 医学边界与通过标准；
- 修改文件和前后哈希；
- 确定性测试；
- 真实页面和真实项目证据；
- 产品内独立 AI 证据；
- 执行/会商冲突点及处理；
- 回归范围；
- 已通过、未通过、残余风险；
- 下一安全动作。

使用工作台现有 records/active_slices/、context/、runs/、reviews/、metrics/ 和 logs/subsystems/medical_monitoring_log.md，记录决策和恢复状态，不记录每次无意义轮询。

定期清理已经明确无用的临时截图、浏览器缓存、重复测试项目、解析中间文件和旧运行残留；清理前先确认最终证据、哈希和摘要已保存。不得删除原始用户资料或仍被当前测试引用的文件。

十一、暂停和决策边界

不要自行阶段性暂停。只有以下情况停下来：
1. 用户明确要求暂停；
2. 存在几条架构、业务或语言路线，证据无法判定且会实质改变目标；
3. 需要未授权的外部后果、付费、生产权限或不可恢复操作；
4. Goal 工具定义的真实阻塞条件已经满足。

普通实现选择、有明确最优解的修复、只读检查、可恢复本地修改、服务启停和测试继续自主推进。

十二、第一轮立即执行

1. 读取权威文档和当前记录。
2. 核对当前运行态、代码和测试，不假定交接报告仍然准确。
3. 创建 P0 的五个输出：CURRENT_STATE、INTERFACE_AND_OWNERSHIP_MATRIX、REAL_PROJECT_TEST_MATRIX、CHANGE_OWNERSHIP_MANIFEST、AI_RUNTIME_READINESS。
4. 先验证产品内独立 AI 可用。
5. 从差距矩阵 P0-01 至 P0-07 逐项关闭，优先真实增量、风险身份和模块边界。
6. 完成一轮后自动进入下一轮，直至主 PRD §40 的全部发布门通过。
