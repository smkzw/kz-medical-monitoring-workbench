# 医学监查子系统分阶段实施与 LOOP 计划

**文档性质：** 产品实施、任务编排、验证与恢复计划  
**适用范围：** 医学监查子系统从当前基础能力推进至可接入医学经理工作台总系统并具备上线条件  
**实施原则：** 不按页面数量判断进度，以真实医学任务是否能从原始文件完成闭环判断进度；不限定固定工期，各阶段达到退出门后连续进入下一阶段。

---

## 1. 最终目标

交付一个能够由医学经理独立使用的桌面端医学监查子系统：

1. 用户选择项目，上传当前有效方案和定期导出的最新全量 EDC data listing。
2. 系统完成文件基本信息和内容适配校验、来源登记、字段语义映射和方案规则候选提取。
3. 日常模式自动比较上一已确认批次，突出新增、变化、重开、持续和需重新复核事项。
4. 规则引擎和独立 AI 共同形成来源可追溯的候选风险；医学经理查看证据、Timeline、Patient Profile 后完成确认和处置。
5. 同一底座支持锁库前全量医学监查和核查前受试者/中心/试验三级总结性自查。
6. 总看板读取稳定摘要，Safety/PV 读取安全性投影，其他子系统通过共享项目、来源和方案事实协作，但不复制医学风险。
7. 系统与并行开发的医学写作子系统在前端、后端、共享契约和数据所有权上无冲突。

---

## 2. 完成定义

必须同时满足：

- 至少三个结构差异明显的真实研究从原始方案和原始 listing 完成全流程。
- 至少一个真实研究使用两个以上连续全量批次完成真实 diff 和风险迁移。
- 日常、锁库前、核查前三种模式分别完成完整 LOOP。
- 产品内独立 AI 脱离开发代理独立运行，失败时确定性流程可继续。
- 所有按钮、筛选、排序、页签、弹层、处置、导出、冲突、空态、失败和重试均实际操作验证。
- Timeline 和 Patient Profile 的医学语义、数据完整性、视觉密度、交互和跨项目泛化通过。
- 总系统项目、来源、方案事实、风险摘要、未读、Safety/PV、审批中心和深链契约通过。
- 医学写作子系统的文件、路由、状态和文档所有权未被医学监查开发覆盖。
- 真实桌面浏览器、服务重启、并发冲突、持久化、性能和审计验证通过。
- 需求追溯、变更记录、测试证据、遗留项和下一安全动作完整。

## 3. 工作流和文件所有权

### 3.1 总体工作流

```mermaid
flowchart LR
    P0["P0 现状冻结与契约"] --> P1["P1 模块边界与共享接线"]
    P1 --> P2["P2 来源/批次/真实差异"]
    P2 --> P3["P3 方案事实与规则引擎"]
    P3 --> P4["P4 产品内独立AI"]
    P4 --> P5["P5 统一风险工作台"]
    P5 --> P6["P6 Timeline / Profile"]
    P6 --> P7["P7 日常监查闭环"]
    P7 --> P8["P8 锁库前 / 核查前"]
    P8 --> P9["P9 总系统集成"]
    P9 --> P10["P10 多项目发布LOOP"]
```

### 3.2 并行开发边界

| 工作面 | 本任务可修改 | 与医学写作会话的边界 |
|---|---|---|
| 医学监查业务服务 | 可修改 | 独立目录；不改写作服务 |
| 医学监查前端页面 | 可修改 | 先建立独立路由/模块；不大范围重写共享根组件 |
| 共享项目/来源契约 | 可兼容扩展 | 修改前列出消费者；新增字段默认可选 |
| 共享设计令牌/壳层 | 可提出小范围兼容变更 | 合并前同时跑写作与监查视觉回归 |
| 医学写作文档、编辑器、AI 写作状态 | 禁止修改 | 只读项目事实接口 |
| 医学风险与处置 | 医学监查唯一写入 | 写作、总看板和 Safety/PV 只读 |

### 3.3 无版本控制工作区的必备保护

每轮代码修改前必须：

1. 记录目标文件路径、SHA-256、大小和修改时间。
2. 记录当前会话拥有的文件和可能被另一会话修改的共享文件。
3. 对将修改的共享文件创建任务级可恢复快照，不放入测试收集目录。
4. 修改完成后输出逐文件变更摘要和新哈希。
5. 合并时逐块比较，不使用目录覆盖。

## 4. 阶段 P0：现状冻结与可执行合同

### 目标

把“以为实现”“局部实现”“真实已验证”和“目标设计”分开，形成后续所有开发的唯一入口。

### 工作项

1. 读取主 PRD、差距矩阵、系统/子系统日志、真实项目 LOOP、当前代码、测试和运行配置。
2. 建立能力真值表，逐项关联代码、测试、真实运行证据和剩余缺口。
3. 建立共享对象所有权矩阵：项目、来源、方案事实、批次、风险、处置、未读、写作文档、Safety/PV 文档。
4. 建立当前接口快照和消费者清单。
5. 建立文件所有权清单，避开医学写作会话正在修改的文件。
6. 建立三个真实研究测试矩阵，确认每个项目的原始方案、原始 listing、连续批次和可用受试者。
7. 建立产品内独立 AI 测试配置与最小连通性证据。

### 输出

- `CURRENT_STATE.md`
- `INTERFACE_AND_OWNERSHIP_MATRIX.md`
- `REAL_PROJECT_TEST_MATRIX.md`
- `CHANGE_OWNERSHIP_MANIFEST.md`
- `AI_RUNTIME_READINESS.md`

### 退出门

- 所有 P0 缺口有负责人、输入、通过标准和验证数据。
- 没有共享文件所有权冲突。
- 产品内独立 AI 至少完成一次真实请求并返回可验证响应；如失败，先修复独立 AI，不进入依赖 AI 的功能开发。

---

## 5. 阶段 P1：模块边界与总系统共享接线

### 目标

让医学监查成为可独立迭代、可被总系统挂载的模块，消除大型共享根组件导致的并行冲突。

### 工作项

1. 建立医学监查独立路由、页面壳层、状态容器、API 客户端、样式作用域和测试目录。
2. 复用总系统项目选择器、导航、品牌和设计令牌，不复制项目主数据。
3. 定义模块摘要接口、深链接口和路由焦点参数。
4. 为总看板提供只读的未读、高风险、待行动和最新批次摘要。
5. 建立共享契约消费者测试，证明医学写作不受影响。
6. 保持模块名称为“医学监查”，不展示“第几环节”。

### 验证

- 直接打开、总看板进入、受试者/风险深链进入三条路径均正确。
- 关闭监查页面后不污染写作页面的项目、筛选和编辑状态。
- 共享壳层视觉一致，业务工作区不被统一卡片模板限制。

### 退出门

- 医学监查页面和医学写作页面可以在同一构建中独立工作。
- 共享契约为兼容扩展，无破坏性消费者失败。

---

## 6. 阶段 P2：来源、不可变批次与真实差异

### 目标

完成日常医学监查的核心数据链，不依赖演示 `CHANGE_FLAG` 或人工整理后的差异。

### 工作项

1. 统一来源登记：文件角色、项目、内容修订、解析器版本和模块绑定。
2. 建立不可变业务批次：上传、校验、登记、运行、确认、冻结。
3. 实现技术可读性与内容适配校验；允许医学人员覆盖可覆盖项，技术失败不可覆盖。
4. 逐数据域配置稳定业务键和候选匹配逻辑。
5. 计算结构差异、行级差异、字段差异和医学语义差异。
6. 对删除/撤回先证明当前输入是完整全量快照，否则标记来源完整性待确认。
7. 处理表名、列名、类型、访视编码和事件键漂移。
8. 实现幂等、并发冲突、断点恢复、失败重试和批次确认。
9. 批次只有在关键域映射确认、完整全量快照证明和来源覆盖通过后才能成为比较基线；不完整来源只允许保存为草稿或限定范围查看。

### 真实 LOOP

每个连续批次至少覆盖：

- 新增记录；
- 原值改值；
- 迟发补录；
- 记录缺失但无法确认删除；
- 明确撤回；
- 业务键变化；
- 新增/缺失/改名字段；
- 单位或参考范围变化；
- 完全相同重传；
- 处理途中来源变化。

### 退出门

- 至少一个真实项目的两个以上完整批次从上传到差异摘要无人工预处理。
- 差异结果逐条能回到旧/新原始值和定位。
- 结构漂移不被静默跳过，规则不会在关键域缺失时输出“无风险”。

---

## 7. 阶段 P3：方案事实、规则配置与确定性规则

### 目标

从当前有效方案中形成可复用、可版本化、可医学确认的监查规则，不把项目阈值写入代码。

### 工作项

1. 从方案及修正案提取访视、时间窗、入排、给药、剂量调整、依从性、禁限用药、洗脱、疗效、安全性、AESI、提前退出和 PD 口径候选。
2. 建立方案事实状态：AI 候选、医学已确认、已替代、待补资料。
3. 每条规则绑定方案原文、适用日期、前置条件、触发、排除、严重度、置信度、证据模板和版本。
4. CM 与试验药物/剂量调整在方案事实、字段映射、规则、事件和风险中全链路分域。
5. 建立规则包版本、影子运行、回溯策略和金标准病例。
6. 实现核心规则族：
   - AE/MH 漏报候选；
   - CS/NCS 评价需复核；
   - 试验药物暂停、减量、停药、重启和依从性；
   - CM 禁限用药、洗脱和救援药；
   - 访视、时间窗、关键评估错序；
   - 入排持续合格性；
   - AE/SAE/AESI 一致性；
   - 疗效、量表和终点完整性；
   - 跨表逻辑和数据质量。

### 退出门

- 每条启用规则有可打开的方案原文和确定性计算证据。
- 同一规则在三个真实项目中由配置适配，不存在项目硬编码。
- 方案或规则版本变化能正确触发受影响风险重新复核。

## 8. 阶段 P4：产品内独立 AI

### 目标

让系统真正脱离开发代理独立完成需要语义理解的任务。

### AI 任务

| 任务 | 产品输出 | 人工动作 |
|---|---|---|
| listing 字段语义映射 | 规范域/字段候选、依据、置信度、未映射项 | 批量确认或逐项修订 |
| 方案条款结构化 | 原文、条件、适用范围、歧义和定位 | 确认规则候选 |
| 跨表线索归纳 | 事实链、可能解释、冲突和缺口 | 选择处置方向 |
| 风险证据摘要 | 简短医学摘要和可打开引用 | 复核/修改 |
| 用户追问 | 基于当前风险的事实、推断、建议 | 继续对话或采纳 |
| Query/医学说明候选 | 2–3 个不同侧重文本 | 选择、编辑、导出 |

### 提示词 LOOP

1. 固定输入合同与稳定 JSON 输出。
2. 明确只使用当前项目授权来源。
3. 强制区分事实、推断、建议和缺失。
4. 强制提供可验证引用；没有证据时明确未找到。
5. 禁止跨项目阈值、禁止把未检出写成不存在、禁止自动确认 AE/MH/PD。
6. 用三个真实项目分别测试字段、条款、风险和追问。
7. 医学人员按正确性、可读性、引用准确性、遗漏、过拟合和行动价值评分。
8. 修订提示词后重跑同一固定集和一个未见项目。

字段映射确认界面必须以医学数据域分组，默认接受高置信度候选，集中呈现低置信度和关键未映射项；资深医学经理不需要编辑代码、表名规则或技术字典。确认后的映射绑定当前来源并形成独立 `mapping_revision`。

### 退出门

- 产品内 AI 的成功由真实系统调用证明，不依赖开发代理手工完成。
- 失败、超时、低置信度和无效结构均有明确降级。
- 确定性规则和人工路径在 AI 不可用时仍完整。

## 9. 阶段 P5：统一医学风险工作台

### 目标

以七列 Checklist 为导航，以风险详情为主工作区，形成可追溯、可处置、可跨视图定位的闭环。

### 工作项

1. 固化 risk_key、risk_instance_id、来源修订和实例迁移。
2. 七列列表每列排序/筛选；额外字段只在列选择器中按需开启。
3. 未读与风险状态分离；打开只更新已读。
4. 风险详情采用大叠加工作区：
   - 风险处置；
   - Subject Timeline；
   - Patient Profile；
   - AE/MH 核查；
   - 来源证据；
   - 批次历史。
5. 证据顺序固定为：原始事实正文→方案依据原文→系统规则/计算→来源定位。
6. 医学经理可确认、驳回、调整、补资料、解释保留、关联 PD/Finding、转 Safety/PV、生成 Query 候选。
7. 用户已确认的选择不再显示“待医学批准”。
8. 列表、详情、Timeline 和 Profile 之间保持 exact-focus、筛选和滚动状态。

Query 候选是否进入内部审批由项目配置决定。内部审批仅覆盖草稿文本和发送建议，不等于正式发送，也不重复审批医学经理已经完成的医学判断；正式发送由数据管理或配置的组织流程确认。

### 退出门

- 每类风险至少有一个真实项目案例完成创建、阅读、处置、冲突、重开和历史回看。
- 任一风险在所有视图中身份、证据、状态和未读一致。

## 10. 阶段 P6：Subject Timeline 与 Patient Profile

### Subject Timeline

1. 横轴为实际日期，方案访视作为轴上锚点。
2. 事件在轴下按类别泳道和真实起止时间排列。
3. AE、MH、CM、试验药物/剂量调整、实验室/检查、疗效、访视/PD 使用不同颜色。
4. 风险严重度通过边框、图标或强调线第二编码。
5. 高密度区域提供错层、聚合展开和缩放，杜绝大卡片和元素冲突。
6. 从风险进入时只高亮关联事件，不过滤完整临床上下文。

### Patient Profile

1. 指标集由当前方案、医学监查计划和 listing 字段联合生成候选。
2. 展示实际日期、访视、基线、单位、参考范围、异常方向、CTCAE（适用时）、风险锚点和重要治疗事件。
3. 疗效、安全性、AE、试验药物和数据完整性互相联动。
4. 个体层面保留计划外访视；聚合默认排除，除非项目配置纳入。
5. 盲态研究不泄露治疗分组。
6. 缺失域返回稳定空结构，不白屏、不虚构。

### 退出门

- 与参考成品的业务语义一致，而非仅视觉相似。
- 三个真实项目、稀疏受试者、高密度受试者和不同视口通过视觉及交互验收。

## 11. 阶段 P7：日常医学监查闭环

### 用户主路径

选择项目 → 上传最新全量 listing → 内容校验 → 确认基线 → 查看差异摘要 → 运行规则/AI → 复核未读和变化风险 → 查看 Timeline/Profile → 处置 → 确认批次。

### 必测异常

- 文件类型错误；
- 适应症或项目不匹配并由用户覆盖；
- 关键域技术不可读；
- 上一批次选择错误；
- 结构漂移未确认；
- AI 超时；
- 规则部分失败；
- 来源处理中变化；
- 并发用户修改同一风险；
- 浏览器刷新、服务重启；
- 大项目首次加载与缓存后加载。

### 退出门

- 真实用户无需查看技术日志即可知道任务进度、失败位置和下一步。
- 本批次差异、风险和处置可成为下一批次可靠基线。

---

## 12. 阶段 P8：锁库前与核查前

### 锁库前

- 冻结来源、方案、映射、规则和字典版本。
- 对候选锁库数据全量重算。
- 核对关键域、计划评估和全体受试者覆盖。
- 汇总开放项、已关闭依据、责任人和锁库决定。
- 不用日常增量结果替代全量重算。

### 核查前

- 基于同一风险库形成受试者、中心、试验三级汇总。
- 识别重复模式、中心聚集、评价习惯和长期未闭环事项。
- 每个汇总数字可回到具体风险、原始事实和处置历史。
- 形成可导出的风险 listing、证据包和整改状态。

### 退出门

- 三层数字逐层一致。
- 不把统计偏离直接表述为中心违规。
- 所有关闭或解释项有可验证依据。

---

## 13. 阶段 P9：总系统接入

### 接入项

1. 总看板项目摘要和未读计数。
2. 项目选择、来源登记和方案事实共享。
3. 受试者、中心、风险和视图深链。
4. Safety/PV 只读风险投影及独立文档审阅关联。
5. 审批中心只处理配置的组织动作。
6. 统一品牌、导航、设计令牌、加载、空态和错误模式。
7. 与医学写作的消费者契约和回归。

共享来源的内容身份与模块用途绑定分离：同一文件跨模块共享 `source_content_revision`；解析器升级形成 `parse_revision`；医学监查/医学写作用途写入各自 binding，不改变来源内容修订号。

### 退出门

- 总系统只读取摘要，不维护第二套风险。
- 共享项目上下文切换时各模块正确重置自身状态。
- 医学写作文档、版本和编辑状态无回归。

## 14. 阶段 P10：多项目全功能发布 LOOP

### 测试角色

- 工程师视角：接口、状态机、并发、持久化、异常、性能和消费者契约。
- 懒惰但专业的资深医学经理视角：最少输入、默认最优、重点突出、事实可见、无需阅读日志、能快速确认和修订。
- 医学科学性视角：方案依据、时序、单位、基线、参考范围、CTCAE、AESI、盲态和跨域解释。
- 视觉与交互视角：桌面密度、层级、字体、对齐、颜色、碰撞、焦点和跨视图连续性。

### 每个项目的完整顺序

1. 清理上一测试项目的运行状态，保留归档证据但不复用配置。
2. 从项目创建和原始来源导入开始。
3. 完成方案事实和字段映射。
4. 执行日常批次、风险复核、Timeline、Profile 和处置。
5. 完成独立 AI 的真实调用。
6. 完成锁库前和核查前演练。
7. 验证总看板和 Safety/PV 投影。
8. 导出风险 listing 和证据。
9. 重启服务后恢复。
10. 汇总问题、修复、同项目重测，再用另一未见项目回归。

测试模型或执行角色发现问题后，Codex 只复现冲突点、风险点和关键证据，不重复遍历其已经提供完整证据的无问题范围。任何角色的“通过”必须附真实点击、接口、文件或渲染证据。

## 16. 执行与会商机制

1. 每轮开始读取当前全局 `AGENTS.md`，不复制可能过时的模型路由到产品文档。
2. 超过三个步骤、临床/监管高风险、外部调研、跨文件代码、浏览器视觉或生产写入时，通过当前工作流守卫初始化受跟踪任务。
3. 执行用于有边界的实现和产物修改；会商用于独立挑战、医学边界和接受审阅，不让会商重复生产同一产物。
4. 分派前写清来源、范围、成功标准、风险边界、允许写入路径、超时和返回格式。
5. 执行者返回来源、实际工作、观察、失败路径、证据、不确定性和下一建议。
6. Codex 只复核冲突点、风险点和接受证据，最终负责真实文件、浏览器、医学和生产判定。
7. 发生几条完全不同的架构路径且证据无法判定优劣，或独立 AI 无法在不引入代理框架的情况下达到任务要求时，暂停该决策点并提交用户选择；其余有明确最优解的实现继续推进。
