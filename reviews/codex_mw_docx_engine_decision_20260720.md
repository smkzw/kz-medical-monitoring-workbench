# 医学写作 DOCX 引擎技术决策

日期：2026-07-20

## 决策

生产主链保持分层实现，不切换为单一第三方“文档生成器”：

1. `python-docx` 继续负责常规段落、表格、分节和高层对象创建；
2. 直接 OOXML 变换继续负责公司模板保真、Word 样式、域、书签、目录、
   交叉引用、文献重排、页眉页脚、字体和无法由高层 API 完整表达的细节；
3. Microsoft Open XML SDK 3.5.1 继续作为结构与 schema 验证器；
4. LibreOffice 只作为可自动化的 PDF/页面渲染 QC 路径，不作为 OOXML
   生产事实源；
5. Microsoft Word 原生打开、更新域、保存、重开和视觉检查仍是上线前
   最终发布门。

该组合全部可本地、离线运行，不引入额外商业授权或按次付费。

## 外部候选复核

### docx4j

- Apache-2.0，支持打开、创建和修改完整 OpenXML package，也支持变量、
  content control、MERGEFIELD、字体处理等；
- 作为 Java 路线功能覆盖广，但引入 JVM/JAXB 和第二套 OOXML 对象模型；
- 当前系统已有 Python 高层对象、纯 OOXML 变换、Open XML SDK 校验和
  大量真实文档回归。迁移不能消除 Word 布局引擎依赖，反而会扩大回归面；
- 结论：保留为未来独立 Java 文档服务候选，不进入当前发布关键路径。

### Microsoft Open XML SDK

- MIT，紧贴 ISO 29500，支持 WordprocessingML 的生成、修改和验证；
- 官方明确它是低层框架，不提供完整的高层生产力抽象；
- 当前最适合作为强类型校验和特定 OOXML 变换的补强，而非整体替换
  Python 写作后端。

### Apache POI XWPF

- Apache 官方将 XWPF 描述为核心较稳定但 API 不完整，部分能力需要下沉
  到 XMLBeans；官方同时提示可能生成无效文件且错误检查并不完整；
- 与 docx4j 一样会引入 Java 运行时和第二套文档模型，却没有明显高于
  当前组合的模板与域保真收益；
- 结论：淘汰。

### python-docx

- MIT，适合 Python 后端内的常规 DOCX 创建与修改，并已在本项目形成稳定
  测试资产；
- 对 Word 域、复杂书签、部分列表和完整 OOXML story 的高层支持不足；
- 结论：不单独承担最终保真，但继续作为主链高层层次。

### LibreOffice

- 继续用于无界面批量转 PDF 和页面回归；
- 其排版结果不能替代 Microsoft Word 对 Word 域、字体回退、目录更新和
  最终分页的解释，因此不得把“LibreOffice 可打开/可导出”作为上线充分
  条件。

## 采用标准

任何未来替换或新增引擎必须同时证明：

- 开源许可证允许公司内网私有化和个人私有化部署；
- 无额外按文档、按页、按服务器或按用户付费；
- 在不少于两个真实项目上保留公司权威模板的文字、表格、图形、页眉页脚、
  样式、域、书签、目录、交叉引用和引用跳转；
- 导出前后 Open XML 无新增错误；
- Microsoft Word 更新域、保存、重开后无修复提示和不可接受的分页漂移；
- 迁移收益显著高于现有分层实现的回归与维护成本。

当前没有候选同时满足“明显更优”和“低迁移风险”，因此不进行引擎替换。
