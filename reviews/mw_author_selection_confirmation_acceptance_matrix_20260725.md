# 医学作者选择即确认：修复验收矩阵

日期：2026-07-25

## 原则

系统当前用户即医学经理。用户选择、修订后采用或明确确认某项内容时，该动作就是项目内作者确认；不得再制造第二次“待医学批准”。快照、交接、版本冻结属于技术动作，只负责可追溯性和下游数据一致性。

## 必须通过

### PICOS 单次确认

- 选择候选且已提供项目理由时，同一原子动作将该域置为作者已确认。
- 选择时尚无理由，可保留未完成状态；补充并保存理由后即作者已确认。
- UI 不再同时提供“选择”“保存理由”“确认当前域”三层重复动作。
- 全部域作者确认后，技术快照可生成，但不得显示为再次医学批准或再次作者确认。

### 历史 PICOS 迁移

- `in_medical_review` 历史绑定可通过当前 UI 一次迁移为作者确认，并从审批中心待办消失。
- `returned_for_revision` 历史快照要么完成真实状态迁移，要么返回明确冲突；不得无状态变化却提示成功。
- 迁移保留原快照、原审批绑定和追加式审计记录。

### 写作交接业务幂等

- 相同 `project_id + package_id + snapshot_id + target_document_type` 使用不同 idempotency key 重试时返回同一 handoff。
- 重复点击、页面刷新、并发请求不会产生唯一键错误。
- 新 snapshot/revision 不会被旧 handoff 状态阻挡。
- UI 的交接状态来自服务端当前 snapshot 投影，不以包级本地布尔值作为事实来源。

### 历史译文迁移与失效

- 历史 `approved + not_admitted` 在 UI 中有“一次作者确认并准入”的出口。
- 确认、准入、brief 建立和迁移审计在一个事务内完成，失败时整体回滚。
- 来源、提取、hash 或当前 revision 变化后，历史确认仍可追溯，但不再计入当前 `author_confirmed_count`。
- 单条 UI 明确显示“历史已确认、当前已失效”，不得同时投影为当前已确认。
- 针对非当前 translation revision 的退回或拒绝明确失败，不写假成功 review。

### 项目隔离

- 两个项目使用相同 batch/translation ID 时，读取、确认、准入、失效、批次汇总和审批待办互不影响。

## 验证层次

1. 后端单元与事务故障注入测试。
2. 前端组件/合同测试，覆盖按钮可达性和真实状态变化，不能只检查字符串。
3. 前端构建。
4. 统一重启后验证 5174/8911 构建号一致。
5. 浏览器真实路径验证：新状态、历史迁移、刷新、重复点击。
6. CRSwNP、D017、UC 真实项目数据重跑。

## 发布门

任何一项 P1 语义仍可复现，或前后端 build ID 不一致，均不得进入真实项目发布验收。
