## 五、复盘与策略

### 根因归类

1. **状态碎片化（双实证，当前第一优先根因）**：R8 与 R9 两轮、两个项目，预置 API 均返回 confirmed/ready/documents_ready 全绿，产品界面与运行门均读「未确认」。接入管线写入的状态与运行门读取的状态**不是同一份事实**。修不好它，开考位永远开不了考，引擎永远零运行——fail-fast 只是让失败变得诚实，没有让成功变得可能。
2. **「假出口」家族（承诺-实现脱节的最新样本）**：C 撞上的归属确认假出口与 R2-01（裁决文案无控件）、R6-08（或/且脱节）同族——**文案先行、控件缺位**的设计模式在异常分支上反复出现；R1-01 轮修过主路径（放行入口），异常分支的出口八轮后仍是空的。
3. **R3-01 家族的 CSU 固定终点**：60 字段/10 表→复核停滞已三次稳定复现；seed 题卡的「两侧逐字相同却判不一致」第二次目击——复核比较逻辑本身（比的是什么？revision 还是值？）仍是未解之谜，修复前该家族不可能收敛。
4. **识别吞吐是 MY008 的物理墙**：1600+ 字段全列枚举、单会话跑不完（三轮互证）；CSU 的 60 字段规模则稳定可完成——**开考位与植入对照应继续以 CSU 为载体**，MY008 留给吞吐修复（并行/断点续跑）之后。
5. **诚实性建设进入深水区**：fail-fast 拒绝、文案限定（「仅代表数据校验完成」）是正面里程碑；同时新暴露「拒绝零留痕」（R9-05）与「签核无原文可核」（R9-01）——诚实不只是不撒谎，还包括**让每个决定可追溯**。
6. **台账完整性问题进入第三代**：R1-06（关闭后八源复发）、R3-01（关闭后六机制复发）之后，R1-01 成为第三起「关闭与复发同轮并存」——**按「主路径走通」关闭、按「分支复发」延续的台账规则，已经无法表达这个系统的真实状态**。家族档案（复盘报告持续维护）事实上成为唯一完整的真相记录。
