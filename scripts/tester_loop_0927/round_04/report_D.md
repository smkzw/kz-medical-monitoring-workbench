## 发现清单

1. 【医学监查·数据接入向导 第3步】【研究文件交叉核对无限停滞，监查链路在此中断】
   - 严重度：critical；类别：product_bug
   - 证据：页面持续显示「系统正在完成最后一次核对」「无需操作，系统会自行处理两次判断中的差异。」「系统正在识别并交叉核对…」，按钮停在「正在核对研究文件…」（禁用）。该消息在 23:56:11 的瞥视中已出现，00:30:37 离开一小时回来未变，00:37:33、00:44:59 两轮复查仍未变；「方案事实与规则发布」区同步停在「字段核对尚未完成」。00:32:20 重传两份 docx 后向导跳过归属确认直接回到同一「最后一次核对」状态，说明不是前端展示问题而是核对任务本身无进展。
   - 复现：新建项目（启用医学监查）→ 开始数据接入 → 目录导入 xlsx → 下一步上传方案+eCRF docx → 「确认属于当前项目并继续」→ 等待「最后一次核对」，观察 >45 分钟。

2. 【医学监查·数据接入向导 第2步】【离开/刷新后前端丢失已上传文档的显示，与服务端状态自相矛盾】
   - 严重度：high；类别：product_bug（含语义不诚实）
   - 证据：界面明示「整理在后台进行时，可以离开页面，稍后再查看」，但刷新后重开向导，第 2 步显示「研究方案 尚未添加」「电子病例报告表 尚未添加」，且上传入口回到「一次选择研究文件」；然而重传后系统跳过归属确认、直接恢复到「最后一次核对」，证明服务端记得此前的归属裁决——「尚未添加」的显示与事实不符。同一时间「来源台账」显示 0 条当前登记来源。Returning user 无法从界面判断自己的文件到底在不在系统里。
   - 复现：上传两份 docx → 核对进行中刷新页面 → 重新打开向导 → 第 2 步显示「尚未添加」；再重传同一组文件 → 直接进入「最后一次核对」（无归属确认）。

## 界面评价

- **易用性**：主线动线本身设计得不错——三步向导有步骤条，进度文案有安抚性设计（「无需操作，系统会自行处理两次判断中的差异」），归属确认的文案甚至主动说明「当前项目可能尚未登记方案编号，因此系统缺少可比对的基准，并不代表文件缺少内容」，这是少见的语义诚实。但恢复性是短板：等待期间没有百分比、阶段序列或耗时提示，1 小时以上的「最后一次核对」让用户完全无法判断是慢还是死；刷新回来后界面显示「尚未添加」（发现2），用户无从自行恢复。
- **逻辑性**：阶段门禁清晰（「字段核对尚未完成，确认完成前不会启动医学监查」的前置提示明确、位置醒目；向导收起后工作条仍留有回入口）。但系统内部口径不一致：向导称已导入核对中、来源台账却是 0 条登记来源；建项成功提示与「无法安全打开」告警同屏出现（发现3），逻辑上自相矛盾。
- **美观性**：布局规范（左侧模块导航、顶部项目元数据条、卡片式分区），信息密度适中，「查看 10 张表的结构 仅在需要时展开」这类渐进披露做得克制。扣分项：显眼的 alert 承载失实内容（发现3）、顶栏时间戳长期冻结（发现5）直接损害界面的可信感；弹窗头部错挂「医学写作」标签（发现6）说明上下文标记维护不严。
