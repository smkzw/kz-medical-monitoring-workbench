## 二、总结论

**fail**。卡点：**数据接入向导 Step 3「本次未提供eCRF」出口逻辑死锁（F-01）**。

一线临床研究中，许多成熟项目或外包监查场景仅具备临床研究方案（Protocol）与数据 Listing，或仅有《eCRF 填写指南》（EDC 填报手册），无法提供作为原始空表的独立 eCRF。系统在界面上明确提供了「本次未提供电子病例报告表」这一人工裁决合法出口，然而当监查员实事求是选择该项后，后端校验引擎并未将 eCRF 降级为可跳过项，仍然判定 `ecrf.required_now: true`，致使 `ready: false`，主操作按钮永久被锁死在 disabled 态的「请先添加所需文件」，使得整个医学监查链路在「内容确认→字段映射」的分水岭前被彻底截断，下游事实准备、运行、发布及结果视图均无法触达。

## 三、发现清单

### F-01【critical / product_bug】「本次未提供eCRF」出口逻辑死锁，下游全链硬阻断
- **页面**：医学监查 → 数据接入向导 第 3 步（处理少量疑点 / 研究文档准备情况）
- **问题**：当真实研究仅具备方案而无单独空白 eCRF 时，监查员在系统询问「哪份是电子病例报告表？」时选定「本次未提供电子病例报告表」并确认。后端虽然记录了选择并将 `ecrf.status` 置为 `"missing"`，但内部规则引擎仍将 eCRF 锁定为必须文件（`required_now: true`），返回 `ready: false`。界面上的前进主按钮永久置灰为「请先添加所需文件」，没有任何推进或绕过机制，流程陷入终态死锁。
- **严重度**：critical
- **类别**：product_bug
- **证据**：
  1. 页面快照明确显示：`研究方案 已识别`，`电子病例报告表 尚未添加`，底部主按钮显示 `请先添加所需文件`（disabled=true）；
  2. 提取后端 `/study-documents` 接口载荷：
     ```json
     {
       "ready": false,
       "roles": [
         { "role": "protocol", "required_now": true, "status": "current", "status_text": "已识别" },
         { "role": "ecrf", "required_now": true, "status": "missing", "status_text": "尚未添加" }
       ]
     }
     ```
  3. 监查员在界面上无任何可操作入口打破该阻塞，整条医学监查旅程在此处强行中止。
- **复现步骤**：
  1. 新建项目「MX循R6C-RUX」，启用医学监查；
  2. 上传 `RUX-03-002_DataListing.xlsx` 完成数据表解析；
  3. 在第 3 步上传 `RUX-03-002_临床研究方案_V1.3.docx` 与 `RUX-03-002_eCRF填写指南_V1.0.pdf`；
  4. 系统识别提示文件角色无法自动判定时，在「哪份是电子病例报告表？」下选中单选框「本次未提供电子病例报告表」，点击保存；
  5. 确认方案文件内容差异并放行后，观察向导第 3 步主操作按钮状态。

### F-02【high / product_bug】内容确认提交后前端状态机假死，文案永久停留在「正在核对研究文件…」
- **页面**：数据接入向导 第 3 步「研究文档准备情况」
- **问题**：在监查员提交文件内容确认（「差异不影响本次监查，继续使用」）后，后端异步返回了新的状态载荷，但前端组件内部状态机 `documentState.phase` 遗留在 `"analyzing"`，而返回的 payload 中已无 `analysis_token`。根据前端组件内部 `useEffect` 守卫条件（必须同时存在 `analyzing` 等阶段且存在 `analysis_token` 才会启动轮询），导致轮询机制彻底失效，按钮文案永久挂起为「正在核对研究文件…」（disabled=true），界面失去响应与自愈能力，用户只能通过 F5 强制刷新页面才能看清最新静态状态。
- **严重度**：high
- **类别**：product_bug
- **证据**：
  检查 React 组件 Fiber 树：
  ```json
  {
    "phase": "analyzing",
    "payload": {
      "project_id": "proj_user_8c3da90600fe",
      "ready": false,
      "roles": [...]
    }
  }
  ```
  `payload.analysis_token` 为 `undefined`，轮询定时器停振，控制台再无后续请求发出，按钮长期处于不可点击的加载状态。
- **复现步骤**：
  1. 在第 3 步完成内容差异确认并点击「差异不影响本次监查，继续使用」；
  2. 不刷新页面，静置观察 5 分钟以上；
  3. 观察主操作按钮文案与 disabled 态，始终为「正在核对研究文件…」。

### F-04【medium / ux_issue】向导底部固定 Footer 遮挡页面操作按钮，常规鼠标点击被拦截

## 四、界面评价

### 1. 易用性（Usability）
向导式的三步接入（选择数据 → 查看概况 → 处理疑点）流程骨架非常清晰，对一线监查员而言不需要记忆复杂的前置操作，尤其是「选择单个数据文件」能直接支持多 Sheet 的大型 Excel，省去了人工拆表转 CSV 的巨大负担。但在**微交互细节上存在明显绊脚石**：Step 3 的固定页脚（Footer）直接漂浮在滚动内容上方，使得视口较矮时位于卡片底部的「保存选择并继续」「差异不影响本次监查」等关键操作按钮被拦截（必须盲猜滚动才能点到）；同时，在处理完确认后，主按钮陷入「正在核对研究文件…」假死而不给用户明确的前进状态指引，让习惯了即时操作反馈的临床人员产生“卡死了、不敢动”的心理压力。

### 2. 逻辑性（Logic & Flow）
系统的**后端校验逻辑与前端语义表达存在割裂**：
最突出的矛盾在于 Step 3 顶部大字写着「还需补充研究方案**或**电子病例报告表」，但代码底层却对两者都施加了 `required_now: true` 的硬性约束。即使监查员选了「本次未提供电子病例报告表」这一完全符合 GCP 现实情况的选项，系统依然把它当成“未满足必填”而拒绝前进。此外，在让用户指认 eCRF 时，单选列表中竟然提供了方案 docx，却隐去了指南 pdf，这种逻辑混乱完全违背了医学临床常理。

### 3. 美观性（Aesthetics & Professional Look）——「敢不敢给领导演示」
**整体色调专业内敛，但宽屏与极端态下不敢直接给业务领导演示**：
工作台采用了经典的医疗/企业级蓝白灰配色体系（深灰文字、柔和蓝色主调、清晰的状态徽标），在 1440px 笔记本常规分辨率下，来源台账、总看板的卡片层级和留白舒适，专业度较高。
然而，如果给部门领导或申办方做现场演示，有两个地方会立刻“露怯”：
一是**新建项目刚进去就会跳出猩红色的「暂时无法安全打开此项目，请保留原项目并联系支持」**，会让领导误以为系统崩盘或环境故障；
二是**在 1920px 宽屏会议室投影或大显示器上，向导容器无上限拉伸至 1708px**，左侧的表单文案与右侧的状态徽标之间出现数千像素的巨大鸿沟，显得非常空洞、缺乏排版设计感。若要用于高层演示或申办方汇报，必须限制容器最大宽度（如 `max-width: 1200px` 居中）并消除首屏误报错。
