## 二、总结论

### ❌ 验收结论：FAIL（阻断）

**核心卡点**：
真实 54 表大型临床数据集接入在第 3 步「研究文档差异确认」提交后，系统后台长时间执行 `study-documents/resolve` 与 `ai/queue`，未能在前端提供可感知的阶段性反馈；同时后台持续占用进程/数据库排他锁，导致前端所有 `/api/projects` 请求全面超过 20 秒超时阈值，工作台反复呈现「项目服务暂不可用」，且两个差异确认按钮长期灰显锁定在「正在记录确认…」，流程无法继续推进至字段映射与监查执行。

## 三、发现清单

### 发现 1：建项 120s 超时未复位 busy 状态导致弹窗死锁无法退出
- **【页面】** 「配置新研究项目」弹窗（`dialog "在医学监查配置新研究项目"`）
- **【问题】** 当服务器响应较慢触发 120 秒硬超时时，界面弹出提示：「创建请求超过120秒未返回，已停止等待。项目可能已在服务器创建，请先核实再重试。」然而，前端未在超时分支将 `busy` 状态复位为 `false`，导致：
  1. 提交按钮持续停留在「创建中」并被禁用；
  2. 左下角「取消」按钮依然为 `disabled: true`；
  3. 右上角「关闭新项目配置」X 按钮依然为 `disabled: true`。
  用户被强制死锁在弹窗内，既无法取消也无法关闭，除刷新整个浏览器页面外别无他法。
- **【严重度】** `high`
- **【类别】** `product_bug` / `ux_issue`
- **【证据】** DOM 检查确证数据：
  ```json
  {
    "closeBtn": { "disabled": true },
    "cancelBtn": { "disabled": true },
    "submitBtn": { "text": "创建中", "disabled": true }
  }
  ```
- **【复现步骤】** 打开医学监查新建项目弹窗 -> 填写项目参数并点击「创建项目」 -> 当后台在忙碌状态超过 120 秒 -> 弹窗出现超时提示 -> 尝试点击右上角 X 或点击「取消」按钮 -> 按钮全为 disabled，无法关闭弹窗。

### 发现 2：真实大数据集接入导致全局项目列表 `/api/projects` 接口反复超时（>20s），首页抛出「项目服务暂不可用」
- **【页面】** 全局顶部项目选择器及项目看板首页（`http://localhost:5178/`）
- **【问题】** 接入 18.8 MB 54 表数据后，前端所有依赖 `/api/projects` 的页面生命周期均出现严重阻塞。由于后端遍历项目目录及统计耗时极长（实际在后台耗时达 70s - 120s），前端设定的 20 秒硬超时触发，直接显示大面积错误告警「项目服务暂不可用 / 项目列表加载失败或超时（超过20秒未返回）」，导致顶部项目下拉框显示「读取失败」，各模块导航按钮置灰禁用。
- **【严重度】** `critical`
- **【类别】** `product_bug`
- **【证据】** `performance.getEntriesByType('resource')` 抓取到多次持续 20002ms 且被 AbortSignal 终止的 `/api/projects` 资源调用，随后界面呈现：
  - `项目总看板: 项目服务暂不可用`
  - `项目列表读取失败: 项目列表加载失败或超时（超过20秒未返回）。请点击重试；若持续失败请检查服务状态。`
  - 顶部导航模块按钮全部被 `disabled`。
- **【复现步骤】** 在包含真实 54 表数据集的项目中，直接访问 `http://localhost:5178/` 或刷新页面，等待 20 秒，页面直接红字报错「项目服务暂不可用」。

### 发现 3：数据接入第 3 步「内容差异确认」提交后界面无限停留在「正在记录确认…」，缺乏流式反馈与超时恢复

### 发现 4：1280px 分辨率下顶部全局导航栏严重折行（Wrap），挤压主要内容视区
- **【页面】** 顶部全局导航栏（`.workspace header nav`）
- **【问题】** 在 1280px 标准笔记本监查视口下，顶栏的 9 个一级导航按钮（「项目总看板」至「审批中心」）因为间距和文字宽度较大，发生强制折行成两行（`navWrapped: true`），使得导航头高度增加一倍，严重挤占工作台的纵向首屏空间，造成视觉层次紊乱。而在 1440px 与 1920px 宽度下排列正常（单行显示）。
- **【严重度】** `medium`
- **【类别】** `cosmetic` / `ux_issue`

  - 1280px: `navWrapped: true`（首个导航项 top 为 0px，第 9 个项 top 产生纵向位移偏移折行）
  - 1440px: `navWrapped: false`（单行整齐）
  - 1920px: `navWrapped: false`（宽屏空间充裕）
- **【复现步骤】** 将浏览器窗口宽度调整为 1280px，观察顶部 9 个模块导航按钮的排列。

## 四、界面评价（一线医学监查员视角）

### 1. 易用性（Usability）
向导式设计（第1步选数据 -> 第2步看概况 -> 第3步核对文件）对于监查员非常直观，无需记忆任何操作路径。特别是在第 1 步支持直接拖拽/选择本地数据文件夹或输入目录，以及第 2 步的 54 表概况卡片，都能给出清晰的即时反馈。然而，易用性的致命短板在于**长耗时任务的反馈黑箱**：后台在进行 54 表交叉比对时，界面只给出一个静态文案或无进度条的转圈，让用户无法判断是正在密集计算还是已经彻底死锁。此外，建项 120s 超时后按钮未解冻造成的弹窗死锁，让普通业务用户根本不知所措。

### 2. 逻辑性（Logical Flow）
业务逻辑链条设计非常专业严谨：监查员不能越过「研究文件核对」直接跑监查，必须先确认研究方案版本与 eCRF 指南，确保后续风险规则有据可查；同时在检出研究编号「RUX-03-002」与「R30C-RUX」不一致时，强制医学经理签注「差异不影响本次监查，继续使用」，完全符合 GCP 规范中医学监查人员对数据溯源和版本差异承担责任的管理逻辑。逻辑漏洞主要在于**前端超时与后台长任务生命周期的脱节**：前端 20 秒抛错超时，后台却依然在重度运行，导致前后端状态裂变。

### 3. 美观性（Aesthetics & Layout）
- **色彩与层级**：主界面采用冷灰与深蓝为主调，专业科技感很强，状态色（核对中、已完成、待确认）分级分明，字体间距适中，整体专业度达到「敢给公司领导演示」的水准。
- **宽屏响应**：在 1440px 与 1920px 宽屏下，卡片式布局延展自然，无留白过大或内容撕裂；
- **对齐与挤压瑕疵**：主要问题出在 1280px 分辨率下，顶部 9 栏导航由于没有响应式折叠（如溢出收拢为下拉菜单或缩小内边距），直接换行导致导航栏高度倍增，破坏了页面的精致度。
