## 三、发现清单

### F1 【数据接入向导·第3步字段识别】识别吞吐断崖式衰减，全链不可完成
- 严重度：**high**；类别：product_bug
- 证据：进度实测序列（页面「识别分片已完成 X/177」读数，2.5 秒自动刷新）：08:52 开始 0/177；09:53 22/177（≈3.2 分/片）；10:31 36/177；11:00 47/177；11:25 57/177；11:51 66/177（≈2.6 分/片）；12:12 74/177；此后会话外部挂起、浏览器保持开启，20:08 重连后读数 **77/177**——8 小时仅 +3 片。页面同时自称「核对每个阶段通常在数分钟到20分钟内推进，同一阶段超过20分钟无变化会提示停滞」，与实测不符且未见停滞提示；「预计还需约 N 分钟」在同一天内读得 439→50→86→119→138→144 分钟反复跳变，ETA 失去参考意义。
- 复现：上传 59 表 DataListing → 进入字段识别 → 按 15–25 分钟间隔读数 ≥3 小时。

### F2 【数据接入向导·失败清单】失败分片「重跑」提交后无结果反馈，失败长期不清账
- 严重度：**high**；类别：product_bug
- 证据：AE 分片 09:19 失败（invalid_ai_output），09:48 点「重跑「AE--不良事件」的失败分片」获回执「重跑请求已提交…失败分片由后台队列依次重新识别」；EC1 同样于 10:31 提交。至 20:08，失败清单仍为 3 张表（AE、EC1、LB10，均 invalid_ai_output），期间界面无任何重跑完成/再失败的状态变化。
- 复现：等任一分片失败 → 展开失败清单 → 点重跑 → 等待 ≥1 小时观察清单与反馈。

### F3 【医学监查清单页（建项后首屏）】假加载无出口

### F4 【新建项目弹窗（在医学监查模块内打开）】点「取消」跳回项目总看板根路径

## 六、界面评价

- **易用性**：三步向导（选择数据→导入概况→研究文件与字段映射确认）结构清楚，透明度是全系统最大亮点——作业队列（执行中/排队中/最早入队时间）、已等待分钟数、事件参考号、口径脚注（「表数按文件内全部工作表统计…不在此处预先剔除任何表」）都直接摆在页面上。败笔是时间口径过多且互相矛盾（「已等待约 X 分钟」「识别已进行约 0 分钟（自最近一次识别进展起计）」「预计还需约 N 分钟」三者并存且 ETA 跳变 439→50→144），加上「正在读取本次监查记录…」这类无出口假加载（F3），用户分不清该等还是该动。
- **逻辑性**：门控链条解释到位——「方案事实与规则发布」明确列出完整前置链（文件核验→第3步核对→字段映射确认）并把当前阻断标注为「完成前此阻断为预期状态」，这是规范的做法。扣分：模块内新建项目取消会把人甩回总看板根路径（F4）；重开向导必须重走文档核对（2–5 分钟/次）；失败重跑没有闭环（F2）。
- **美观性**：Inter + Noto Sans SC、14px 正文、20px 标题、全直角无圆角，整体干净克制，橙色主按钮与灰边次按钮区分明确。实际问题：顶栏「新建项目」近白底似禁用态（F9）；失败清单折叠态内容泄漏被奶油色状态条盖住（F5）是实打实的视觉缺陷；「医学监查首页」死按钮（F8）破坏可信度。
