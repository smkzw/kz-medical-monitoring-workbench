## 2. 总结论

**测试结论：FAIL（阻断于数据接入向导第 3 步：研究文档准备情况）**

**核心卡点总结**：
1. **文案承诺与底层校验逻辑冲突（OR vs AND 假出口）**：向导标题明文承诺「还需补充研究方案**或**电子病例报告表」（表示方案或 eCRF 二选一即可），而系统在方案 docx 已确认识别（`已识别`）的情况下，底层校验依旧将 `ecrf` 视为阻断性硬门禁（`required_now: true`），主按钮「请先添加所需文件」永久置灰（disabled）。
2. **PDF 场景致命死锁（R6-02 实证验证）**：专属材料中的 `RUX-03-002_eCRF填写指南_V1.0.pdf` 上传后被系统判定为内容无法提取（`document_authority_candidate_not_promotable` / 未能读取可核对内容），系统提示「请将该文件角色标记为缺失，或更换为可读取版本后重新上传」，但在当前文档准备面板上**根本没有提供任何「标记缺失」或「无此文件」的操作控件**，且没有退回重选机制，导致真实用户陷入无路可走的绝对死锁。

## 3. 发现清单

### 【发现 1】向导第3步“或/与”语义不诚实且缺失标记控件，导致全链死锁
- **页面**：医学监查 -> 数据接入向导 -> 第 3 步（处理少量疑点 / 研究文档准备情况）
- **严重度**：`critical`
- **类别**：`product_bug`
- **证据**：
  - 界面主标题：“还需补充研究方案或电子病例报告表”（使用连词“或”）。

  - 用户预期：既然方案已识别，且文案明确写明“方案或eCRF”，此时理应允许进入下一步核对字段。
  - 实际现象：底部主按钮文本显示「请先添加所需文件」，状态为 `disabled: true`。
  - 当尝试上传本研究提供的 eCRF 指南 pdf 时，报错「未能从这组文件中读取到可核对的内容...请将该文件角色标记为缺失」，但在本页面上只有「重新上传研究文件并再次核对」和「重新核对研究文件」，没有任何将 eCRF 标记为缺失的按钮或勾选项，直接掐断用户前进路径。

### 【发现 4】原生文件夹选择器路径丢失，导致误报“目录不存在”陷阱
- **页面**：数据接入向导 -> 第 1 步（选择数据）
- **严重度**：`high`
- **类别**：`ux_issue`
- **证据**：
  - 用户在第 1 步点击「选择数据文件夹」，利用系统文件选择器选中本地目标目录 `tester_staging_0927/RUX`。
  - 界面展示：“已选择‘RUX’，共 3 个文件”，且下方「开始导入」按钮被正常点亮激活。
  - 用户信心满满点击「开始导入」，界面瞬间弹红报错：“未找到该数据位置：目录不存在或路径不可访问。请核对路径后重试。”
  - 技术根因：标准 Web 浏览器安全沙箱不会将操作系统绝对路径暴露给前端 input，前端未做文件二进制切片上传，而是试图向后台传递一个空字符串 `source_path`。必须逼迫用户在下方的文本框「无法选择文件夹时，手动填写数据位置」中手敲一长串几十个字符的本地绝对路径。
  - 资深CRA体验：既然浏览器点选文件夹后无法直接导入，为什么界面要将「选择数据文件夹」做成最大的第一入口？这是极典型的欺骗性交互陷阱。
- **复现步骤**：
  1. 打开数据接入向导第 1 步；
  2. 点击「选择数据文件夹」，选择任意包含 Excel 的本地文件夹；
  3. 看到按钮变成可用，直接点击「开始导入」；
  4. 立即复现红框报错。

### 【发现 5】向导重试机制陷入无限轮询与空列表残影
- **页面**：数据接入向导 -> 第 3 步
- **严重度**：`medium`
- **类别**：`ux_issue`
- **证据**：
  - 当核对出现异常点击「重新核对研究文件」时，前端状态机进入 `analyzing` 阶段。
  - 此时前端代码试图从后端 payload 读取 `roles`，但轮询接口 `study-documents/resolve` 返回的结构中不含 `roles` 数组，导致原先展示研究方案、eCRF 等四项角色的 `<ul>` 列表被渲染成空白（`<ul></ul>`）。
  - 用户看到的是：“系统正在完成最后一次核对 / 无需操作，系统会自行处理两次判断中的差异”，而下面的文档列表全部凭空消失，且前端陷入 1.5s ~ 5s 的无限重试等待，长达数分钟没有超时熔断或进度反馈。
- **复现步骤**：
  1. 在文档核对报错时，点击「重新核对研究文件」；
  2. 观察面板列表区域瞬间变为空白，顶栏文案显示正在核对但无任何进度条或终止倒计时。

### 【发现 6】页面刷新偶发“项目服务暂不可用”假死
- **页面**：工作台全局顶栏 / 项目总看板
- **严重度**：`medium`
- **类别**：`product_bug`
- **证据**：
  - 测试过程中按 CRA 习惯刷新页面（F5 / Reload）观察后台进展时，页面多次出现顶栏显示「连接失败」、项目下拉框显示「读取失败」，看板区域展示大号警告「项目服务暂不可用：项目列表加载失败或超时（超过20秒未返回）」。

- **复现步骤**：
  1. 在监查页面进行中，执行浏览器刷新；
  2. 偶发出现「连接失败」与「项目服务暂不可用」面板。

## 4. 界面综合评价（CRA 专业视角）

### ① 易用性（Usability）
整体流程框架设计有向导式意识（分三步走：选数据 -> 看概况 -> 处理疑点），思路符合临床数据处理逻辑。但**关键操作节点充满了“反直觉陷阱”**：
1. 第 1 步明明提供了醒目的「选择数据文件夹」按钮，选完文件后也提示了“已选择3个文件”，但点击提交却直接报错“路径不存在”，逼着临床用户去手打深层文件路径，极度不友好；
2. 第 3 步提示“请将该文件标记为缺失”，但放眼整个界面，只有“重新上传”和“重新核对”，根本没有“标记缺失”的操作入口；用户像被关在密室里，系统告诉你有钥匙，但墙上根本没有门。

### ② 逻辑性（Logic & Consistency）
**语义与行为严重割裂，存在多处自相矛盾**：
1. **文案承诺 vs 校验门禁**：大标题用大字写着“还需补充研究方案**或**电子病例报告表”，中文的“或”在任何临床试验常识与公文逻辑中都代表“析取/二选一”。然而在方案已经确认为“已识别”的情况下，系统依然因为缺 eCRF 而死死封锁主按钮。
2. **前后状态脱节**：来源台账里已经清晰记录了临床方案 `RUX-03-002_临床研究方案_V1.3.docx` 经过医学经理确认沿用（R2 `已确认沿用`，2005个证据片段技术可读），但向导在刷新或切换后，前置状态无法平滑带动主流程进入字段映射，导致前后台逻辑断层。

### ③ 美观性（Aesthetics & Layout）
界面视觉风格整体采用克制的冷色调与现代卡片化排版，排版间距与字体层级较为规整。但**在动态状态与交互反馈上粗糙感明显**：
1. **内容塌陷与列表跳动**：在向导第 3 步执行异步核对时，中间区域的文档清单会突然整块消失，变成一段居中的纯文本，待状态变更后又突然弹回，视觉抖动剧烈；
2. **弹窗层级与遮挡问题**：底部固定的操作栏与页面内容偶尔出现层叠上下文穿透（例如出现 pointer-events 拦截无法点击下层按钮）；
3. **色彩语义混乱**：当文档存在格式不兼容时，通篇充斥着深红色与黄色的告警卡片，缺乏温和的操作指引提示（如建议用户“如何转换为兼容格式”或“点击此处跳过”），给非技术背景的临床人员带来极大的焦虑感。

## 5. 等待与卡点时长记录

- **第一步数据导入等待时长**：约 **165 秒**（2分45秒），界面有计时器跳动（“正在导入…已用时 X 秒”），反馈明确，资深 CRA 愿意保持耐心等待。
- **第三步方案 docx 解析与多重 AI 交叉核对时长**：
  - 队列排队及分析：约 **75 秒**
  - 独立评审（Reviewing）及裁决（Adjudicating）：约 **60 秒**
  - 分歧复核（Cross-checking）：约 **30 秒**
  - 合计单文档核查耗时约 **2.5 ～ 3 分钟**。等待期间顶部有提示文案（如“系统正在复核最后几个分歧”），但缺乏具体的百分比或细分进度。
- **第三步卡死停滞时长**：由于 PDF 报错后缺失放行控件，处于死锁状态，持续等待观察 **>45 分钟** 依然无法推进，符合等待纪律终止条件。

## 6. 一句话总结论

**“这套系统目前绝对无法由一名真实临床监查员（CRA）独立跑通——系统在向导关键路径上存在‘或/与’逻辑不符、原生文件选择器失效、PDF容错缺失及缺乏人工放行假出口四重死锁，真实用户在没有代码级介入的情况下必在数据接入向导第 3 步彻底卡死。”**
