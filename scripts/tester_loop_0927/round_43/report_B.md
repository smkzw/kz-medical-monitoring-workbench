## 三、发现清单

### F1 【critical】【product_bug】研究文件核对作业队列死锁，全链路阻塞
- **页面**：医学监查 → 数据接入向导 → 第三步「研究文件与字段映射确认」→「研究文档准备情况」
- **问题**：上传方案 docx + eCRF PDF 后，核对作业（最早入队 2026-10-13 21:31:11）始终「执行中 0 项、排队中 1 项」，2700 秒后系统判 `queue_dwell_timeout` 并移出队列；按指引显式重试后队列依旧零执行。字段确认无法完成，医学监查主链全部不可用。
- **证据**：页面状态文本「系统有 1 项核对作业在途（执行中 0 项、排队中 1 项）（最早入队 2026-10-13 21:31:11）」持续约 55 分钟；最终 alert：「失败原因：作业在队列中滞留超过 2700 秒仍未获得执行终态（队列含1个在队作业；常见于上游持续故障期间的反复重排）；已移出队列。请处理后显式重试，重试将重新计时。（queue_dwell_timeout）」；向导底部按钮「正在核对研究文件…」disabled=true；同屏横幅「先完成字段映射确认——字段核对尚未完成，确认完成前不会启动医学监查」。
- **复现**：新建仅启用医学监查的项目 → 数据接入上传 RUX DataListing.xlsx → 导入完成后补传方案 docx 与 eCRF PDF → 等待核对 → 观察作业队列滞留与 queue_dwell_timeout。

### F2 【high】【product_bug】「重新核对研究文件」宣称「真实重排/重新计时」，但两次重试均无可见生效证据
- **页面**：同 F1 的停滞警报区
- **问题**：按钮文案明确承诺「该按钮会真实重排核对作业」「重试将重新计时」。第一次点击（停滞约23分钟时）与第二次点击（queue_dwell_timeout 后）之后，界面可见状态均零变化：最早入队时间保持 21:31:11、等待计数持续累加不重置、执行/排队计数不变。用户无法确认重试是否生效，实际效果等同于无效按钮。
- **证据**：点击前后 [role=status] 文本逐字对比，均含「（最早入队 2026-10-13 21:31:11）」且「本轮已等待约 54/56 分钟」继续递增；无任何「已重排/重新计时」的确认反馈。
- **复现**：在 F1 状态下点击「重新核对研究文件」→ 观察状态区文本 2–5 分钟，无任何字段变化。

### F3 【medium】【ux_issue】sticky 页脚遮挡向导底部「重新核对研究文件」按钮，默认视口下点击无响应
- **页面**：同 F1 停滞警报区（视口高约 951px、内容高约 1172px 时）
- **问题**：`footer.monitoring-admission-actions` 为 sticky 定位（贴视口底 894–951px，z-index 2），而重试按钮位于文档流 901–933px，被页脚完全覆盖；`elementFromPoint` 命中的是 FOOTER 而非按钮，点击报「none can receive input; <footer> intercepts pointer events」。用户点击无反应且无解释，需手动滚动到页面最底部（scrollY=221）后按钮才可点。
- **证据**：DOM 实测：btnRect {top:901,bottom:933}、footerRect {top:894,bottom:951,position:sticky,zIndex:2}、topAtBtnCenter="FOOTER.monitoring-admission-actions"；滚动到底后 topAtBtnCenter 变为按钮自身，点击成功。
- **复现**：进入 F1 状态（内容略高于视口）→ 不滚动直接点「重新核对研究文件」→ 无响应；滚到页面底部 → 可点击。

### F4 【medium】【ux_issue】创建失败时后端校验错误以原始 JSON 直出并截断
- **页面**：医学监查 → 新建项目配置面板
- **问题**：项目名含特殊字符提交时，面板底部错误提示为生硬的后端 JSON（含 type/loc/msg/完整 input payload），且显示被截断，普通用户（CRA）难以阅读；校验规则本身有效，但提示层完全缺失。
- **证据**：界面显示「创建失败：[{"type":"value_error","loc":["body"],"msg":"Value error, project_name 不能包含 \\ | : * ? \" < > 这些字符；请调整后重试。","input":{"project_code":"","project_name":"MX..."」——后半截 payload 直接暴露并被截断。
- **复现**：新建项目 → 项目名称填「MX循R43B-RUX<>|」→ 其余必填完整 → 点「创建项目」。

### F5 【low】【ux_issue】选择文件后不显示实际文件名，占位文案「已选择“所选文件”」
- **页面**：数据接入向导第一步「选择数据」
- **问题**：选择文件后状态为「已选择“所选文件”，共 1 个文件」——「所选文件」是硬编码占位词而非文件名。CRA 上传前核对文件名（防止传错研究的数据）是基本动作，此处无法核对；且不支持的 PDF 能被选中并通过。对比：导入完成后概况页又能显示真实文件名（RUX-03-002_DataListing.xlsx），行为不一致。
- **证据**：[role=status] 文本「已选择“所选文件”，共 1 个文件」（选择的是 eCRF PDF 时即如此显示）。
- **复现**：向导第一步 → 点「选择单个数据文件」选任意文件 → 读状态行。

### F6 【low】【ux_issue】单文件选择被报错为「该目录存在，但其中没有可导入的数据文件」
- **页面**：数据接入向导第一步，点击「开始导入」后
- **问题**：选择单个 PDF 后报错文案以「该目录」指代用户所选的**文件**，术语与操作不匹配，第一眼会让用户以为自己误选了文件夹。错误拦截本身正确，且附事件参考号（EVT-20261013T211932-6f3e06-admission_no_data_files）与「来源台账 → 数据准入事件流水」互查指引，可追溯性好。
- **证据**：alert 全文「该目录存在，但其中没有可导入的数据文件（.csv / .xls / .xlsx / .xlsm）。…事件参考：EVT-20261013T211932-6f3e06-admission_no_data_files」。
- **复现**：向导第一步 → 选择 eCRF PDF → 点「开始导入」。

### F7 【low】【cosmetic】配置面板无方案版本/编号/日期输入，项目「方案版本：草案」与材料 V1.3 不符

## 四、界面评价

**易用性**：正常路径相当顺手——首页「新建项目」的子系统卡片一次勾选即达目标模块，配置面板字段说明写得像给真人看的（「管理代号请填在项目名称，不要填入试验药物」这种防混淆提示很专业）；三步向导每步职责清楚，「请先添加所需文件」的禁用态按钮自带原因。但异常路径的易用性崩塌：核对卡住后，用户手里只有一个被 sticky 页脚遮住、点了没反应的重试按钮（F3），重试后又没有任何反馈（F2），最后的出路文案是 2700 秒后出现的 JSON 味错误码。出差路上遇到这个局面，我大概率直接关页面开微信问运维了。

**逻辑性**：整体信息架构合理：项目→子系统→向导三步→确认闸门→监查工作区，依赖关系表述明确（「确认完成前不会启动医学监查」）；事件参考号+台账流水互查的设计对多人协作排障很有价值。扣分点：报错文案层（F4 的 JSON 直出、F6 的「该目录」术语错位）暴露了前后端之间缺一层面向用户的文案翻译；「方案版本：草案」默认值与已上传 V1.3 方案的关系没有任何界面解释（F7）；数据文件与文档上传入口分开但都在向导内，逻辑尚可接受。

**美观性**（基于截图 /tmp/r43b_top.png、/tmp/r43b_wizard_stuck.png 观察）：整体专业、克制——白底、橙色单一强调色（当前模块导航、当前步骤、警示框一以贯之）、卡片化布局对齐工整，步骤条用绿（完成）/橙（当前）区分状态一眼可读。左上 CMS logo 与左导航在深色/浅色衔接上略有生硬；左导航「安全信号与PV协同」因宽度不足折成两行（「安全信号与PV协/同」），与相邻单行项参差；顶部指标卡（未读决策/高风险开放/待交接/待审批）图标+数字的对齐良好。无花哨装饰，符合临床工具的气质。
