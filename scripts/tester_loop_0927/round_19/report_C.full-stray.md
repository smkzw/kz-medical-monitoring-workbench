## 二、总结论

**FAIL**

**卡点**：数据接入向导第 3 步（研究文件与字段映射确认）发生**死锁性前端传参缺陷**。前端在轮询 `/study-documents/resolve` 接口时未附带必需的 `batch_id` 查询参数，导致后端持续返回 HTTP 422（`mapping_resolve_batch_id_required`）。前端组件不仅未向用户呈现错误反馈，反而掩盖错误并永久显示“系统正在识别并交叉核对…”、“正在核对研究文件…”，同时将文件上传与确认按钮全部 disabled，导致用户在这一关彻底卡死，无法向下推进字段映射与任何后续步骤。

## 三、发现清单

### 【发现 1】
- **页面**：医学监查 - 数据接入向导第 3 步（研究文件与字段映射确认）
- **问题**：前端向导轮询接口漏传 `batch_id` 参数，引发 HTTP 422 并在界面导致无限假死与控件永久禁用
- **严重度**：`critical`
- **类别**：`product_bug`
- **证据**：
  - 前端向 `/api/projects/proj_user_728ebd9bd041/modules/medical-monitoring/r7/data-admissions/stg-4284df9a4e014fe18d413515cddbb038/study-documents/resolve` 发起 GET 请求时，未携带 `?batch_id=...`。
  - 后端直接返回 HTTP 422 Unprocessable Entity，响应体明确指出：
    ```json
    {
      "code": "mapping_resolve_batch_id_required",
      "message": "研究文件核对查询缺少批次参数（batch_id）。请返回向导重新进入第3步；若持续出现请刷新页面。"
    }
    ```
  - 前端组件未对 422 状态做异常捕获与告警呈现，界面文本持续保持：`系统正在识别并交叉核对…`、`系统仍在独立核对研究文件`、按钮文案显示 `正在核对研究文件…`，且相关 input 属性为 `disabled=""`，形成永久锁死。
- **复现步骤**：
  1. 新建项目「MX循R19C-MY008」并启用医学监查。
  2. 点击“开始数据接入”，在第 1 步上传 `MY008-302_DataListing.xlsx` 并点击“开始导入”。
  3. 第 2 步导入成功后，点击“下一步：让系统核对字段”进入第 3 步。
  4. 界面提示“还需补充研究方案或电子病例报告表”，上传 `MY008-302_研究方案_V1.1.docx` 与 `MY008-302_DraftCRF_V0.1.docx`。
  5. 观察界面：状态持续停在“正在核对研究文件…”，审查网络请求可见持续 422 报错，流程无法继续。

## 四、界面评价（易用性、逻辑性、美观性）

### 1. 易用性（Usability）
在数据接入的早期阶段（第 1 步与第 2 步），系统的引导性表现出色。特别是当用户直接选择包含多种格式的整个文件夹时，系统自动识别并分流了数据表与文档，并在界面给出非常清晰的提示：“已忽略 2 个非数据文件（MY008-302_DraftCRF_V0.1.docx、MY008-302_研究方案_V1.1.docx）：研究方案、eCRF 等文档请在第3步单独上传，不参与数据导入。”这大幅降低了用户的认知负荷。然而，在第 3 步出现参数缺失错误时，易用性发生断崖式下跌：系统吞噬底层 422 错误，将操作按钮永久置灰，既不提示为何受阻，也不提供手动重新上传的交互入口，让普通用户产生“系统死机”的无力感。

### 2. 逻辑性（Logical Flow）
业务闭环的门禁逻辑严谨，值得肯定。作为数据管理员，我非常认可系统在“方案事实与规则发布”中展现出的 Fail-closed 严谨态度：“当前项目医学监查来源状态未确认，读取与执行已阻断”。在数据字段未经人工或系统确实验收前，绝不虚构或假定规则运行，确保了 GxP 级别的合规底线。但其状态流转的前后端逻辑存在脱节：前端将第 2 步已生成的导入批次（batch）推进到第 3 步时，未能把 `batch_id` 正确绑定并传递给核对解析接口，导致前后端契约断裂。此外，在网络超时时粗暴地将顶层“新建项目”一并 disable，在交互逻辑上剥夺了用户的自愈与重试可能。

### 3. 美观性（Aesthetics）
界面整体遵循了现代医药专业软件的冷灰与科技蓝主色调，整体对齐严谨，排版清晰，字体层级分明。特别赞赏第 2 步“查看 59 张表的结构”展开抽屉的列表设计：采用紧凑的无衬线等宽数字、居中圆点分隔符（如 `493 行 · 37 列`）以及轻量圆角边框，即便在展示 59 张表的海量元数据时，视觉上依然整齐、呼吸感良好、毫无压迫感。不足之处在于长警告提示框的文字折叠处理（发现 4），在宽度有限的侧边抽屉中生硬截断，略显局促。
