## 核心发现摘要

1. **【发现 1】前后端契约断裂，主操作诱导点击并抛 422 错误【critical / product_bug】**  
   前端在部分表生成就绪时（如 208、224、228、252 个字段），主按钮高亮可用并提示「可采纳当前结果继续」；用户点击后，后台接口 `POST mapping-draft` 挂起长达 **74.3 秒 ~ 79.4 秒**，最终返回 HTTP 422 错误：`{"code": "mapping_draft_invalid", "detail": "字段修订内容无效。请检查填写内容后重试。请稍后重试；若持续失败，请确认字段识别已生成完成。"}`。前端捕获后退回「重新加载识别结果」，重新加载后再次高亮诱导点击，连续 3 次 100% 必现死循环。
2. **【发现 2】假性承诺文案与轮询饥饿死锁【critical / product_bug】**  
   主按钮禁用时显示 `正在生成字段识别结果…（自动刷新进度，无需手动刷新）`。但代码审计表明，前端组件内完全没有设置自动轮询定时器（无 `setInterval`），仅在 `mappingState.phase === 'idle'` 时单次触发。一旦首轮请求结束，前端长达 **206 秒（3.5 分钟以上）零网络请求**。真实用户听信文案将在屏幕前永久空等。
3. **【发现 3】后台同步长任务独占单线程事件循环，并发 API 连续超时导致整站控制台崩溃【high / product_bug】**  
   后台进行 59 表大跨度解析时，同步重计算独占事件循环 53~97 秒，导致控制台核心接口（`GET /api/projects`）超过 20 秒超时熔断（`status: 0`），导致整站控制台全屏报「连接失败/项目列表加载失败/服务暂不可用」。
4. **【发现 4】返回上一步再重入后 Attempt ID 失效，接口 422 被前端静默吞没【high / product_bug】**  
   向导中回退到第2步再前进到第3步，前端使用失效 Attempt ID 轮询 `study-documents/resolve`，后端返回 HTTP 422 `mapping_attempt_id_invalid`。前端无任何错误提示，静默死锁在「正在核对研究文档…」。
5. **【发现 5】表结构识别优秀，但跨阶段口径剧烈跳变缺乏总进度条【medium / ux_issue】**  
   第2步明确 59 张表，第3步流式跳变为 22表(148字段) -> 23表(196字段) -> 24表(228字段) -> 25表(252字段)，缺少总进度百分比（如 25/59 表）。

## 界面评价

- **易用性**：目录模式支持手动录入路径作为浏览器文件夹选择的兜底，实用性强；多文档合并上传感知平滑。但主操作按钮给出虚假的可用诱导（点亮后点击必报错）与虚假的自动刷新承诺（承诺无需手动刷新却无定时器），严重损害可用性。
- **逻辑性**：数据底层对 59 张表结构、字段类型、主键、8 张空表（header-only）与缺失值分布（如 AE.MDRAVER 缺失 8 行）的识别精度极高；但前后端业务状态机契约割裂：前端认为部分完成即可 adopt，后端强制全量就绪才允许生成 draft，逻辑打架阻断主流程。
- **美观性**：整体蓝灰医疗软件风格规范，字段按数据域归并的排版清晰；但长任务期间按钮文案从 8 字到 26 字剧烈跳动，下方错误折叠框反复挂载/卸载造成卡片视口剧烈抖动，全站接口超时挂起时缺乏优雅占位符。
