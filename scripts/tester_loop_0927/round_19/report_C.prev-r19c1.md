## 二、总结论

**FAIL**。  
**核心卡点**：第4阶段「字段映射确认」（数据接入向导第3步后半段）。  
1. **前后端状态机契约割裂，主操作诱导点击并抛 422 失败**：前端在后台部分数据表识别完成时（如 208、224、228、252 个字段），将主按钮置为高亮可用状态「采用已识别的 X 个字段并继续」，并在文案承诺「可采纳当前结果继续」；然而用户点击后，后端接口 `POST /data-admissions/{attemptId}/mapping-draft` 在长跑 74.3 ~ 79.4 秒后，以 HTTP 422 强行驳回并返回 `{"code": "mapping_draft_invalid", "detail": "字段修订内容无效。请检查填写内容后重试。请稍后重试；若持续失败，请确认字段识别已生成完成。"}`。这表明后端强校验要求 59 张表必须全量生成完成，而前端却提前诱导用户提交未就绪的 draft，产生 100% 必现的业务死锁。  
2. **假性承诺文案与轮询饥饿死锁**：在识别生成期间，主按钮显示禁用并提示 `正在生成字段识别结果…（自动刷新进度，无需手动刷新）`。但代码审计表明，前端组件内完全没有设置 mapping 的自动轮询计时器（无 `setInterval`），其触发条件硬编码为 `mappingState.phase === 'idle'`；一旦首轮调用结束，前端永久停止发送任何网络请求（实测超过 3.5 分钟 0 请求）。真实用户被文案告知"无需刷新"而在屏幕前空等，无法获得任何系统推进。  
3. **后台缺乏异步进程隔离，同步重计算拖垮整站控制台**：当后台执行大表与文档 cross-check 时，单线程事件循环被重计算任务独占达 53~97 秒，导致整站并发请求（包括控制台核心 `GET /api/projects`）超过 20 秒全部超时，导致页面全盘崩溃报「连接失败/项目列表加载失败/服务暂不可用」。

### 【发现 2】主操作按钮承诺“自动刷新进度无需手动刷新”，但前端缺失轮询机制导致用户永久挂起

- **【严重度】**：critical
- **【类别】**：product_bug / ux_issue

## 四、界面评价

### 1. 易用性（Usability）
在基础向导指引上表现良好，例如第1步支持直接填入本机目录位置作为浏览器文件夹选择的兜底机制，极大地方便了包含复杂层级文件的导入；第3步支持同时将方案和 eCRF 两个大型 docx 批量送入，且多阶段识别状态文案（"正在独立识别并交叉核对" -> "正在完成最后一次核对" -> "正在复核最后几个分歧"）具备清晰的用户感知意图。但在核心任务闭环上易用性严重受挫：最致命的是向导主操作按钮给出了**虚假的可用诱导**（明知后台仍处于 generating 却点亮采用按钮，致使用户白白承受 74 秒挂起后遭遇 422 报错），以及**虚假的自动刷新承诺**（承诺无需刷新，却缺乏定时器造成用户空等），严重违背了可用性工程的透明性与确定性原则。

### 2. 逻辑性（Logic）
数据解析层的底层逻辑十分严谨且惊艳：8 年数据管理员视角的核查发现，系统完整识别了 59 个 sheet 中的全部表结构，准确提取出 AE 的 73 列和 DM 的 24 列，对空表（header-only）如 DS、DS4、LB11、RP2 做了合理的区分和标记，且准确识别了缺失值分布（如 AE.MDRAVER 缺失 8 行）。然而，**业务状态机的契约逻辑存在严重裂痕**：前端状态定义中将 `payloadState === "needs_attention"`（部分表已就绪）当作可采纳（adopt）分支，但后端接口层却坚持要求全量候选准备完毕才允许生成 draft，导致业务前后端在"什么是可采纳的阶段"上产生逻辑打架，彻底阻断了数据流向事实层（Fact Materialization）的通道。

### 3. 美观性（Aesthetics）
界面整体视觉规范延续了专业医疗软件的克制与严谨，主色调与蓝灰基调搭配合理，信息卡片排版整齐，特别是「数据表识别摘要」对各表的字段数按数据域做归并展现时，层次分明、字体字号对比舒适。但在异常与长任务处理时的动态表现欠佳：按钮文案字数差异过大（从 8 个字到 26 个字），状态切换时按钮尺寸剧烈跳动；长达 148~252 项字段明细展开时缺乏虚拟列表滚动优化，且缺少动态进度条组件（如进度环或百分比条）；当发生全站 API 超时挂起时，看板直接弹出裸露的错误文字并打断页面整体布局，缺乏优雅的降级占位符与重试过渡态。
