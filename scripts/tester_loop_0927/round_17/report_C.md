## 二、总结论

**FAIL**。  
**核心卡点**：数据接入向导第3步（文档角色裁决与字段映射启动门禁死锁）。  
系统前端允许并引导用户将缺失的 eCRF 单选标记为「本次未提供电子病例报告表」，但后端底层规则引擎（`document_evidence.py` 及 `mapping_candidate_routes.py`）将 `protocol` 与 `ecrf` 设为不可或缺的双前置必备项（`MAPPING_REQUIRED_DOCUMENT_ROLES = frozenset({"protocol", "ecrf"})`）。用户按前端引导确认后，前端即判定向导文档准备就绪并移除了上传控件，但后端随后拒绝生成映射建议并返回 HTTP 422。前端将 422 业务错误在第3步静默吞噬（错误提示未在视口展现），仅暴露出无状态的「重新加载识别结果」按钮，用户点击反复失败；同时向导中第2步与第3步缺乏返回第1步重新选文件的通路，导致真实用户直接陷入无法自愈的永久死循环。

## 三、发现清单

### 【发现 1】向导引导标记 eCRF 缺失后触发 422 且上传入口永久消失导致死锁
- **页面**：医学监查 · 数据接入向导第3步（处理少量疑点）
- **严重度**：Critical
- **类别**：`product_bug`
- **证据**：
  1. 后端 `packages/medical_monitoring/admission/document_evidence.py` 第 25 行定义 `MAPPING_REQUIRED_DOCUMENT_ROLES = frozenset({"protocol", "ecrf"})`，第 404 行要求两角色状态必须全部为 `current`；若 eCRF 为 `missing`，`mapping_context_ready` 恒为 `False`，在生成候选时在第 494 行抛出 `DocumentEvidenceError("mapping_document_evidence_incomplete")`（HTTP 422）。
  2. 但前端 `MedicalMonitoringAdmissionWizard.jsx` 针对缺失文件展示了单选卡片：「哪份是电子病例报告表？——本次未提供电子病例报告表」，并在保存后将 `documentState.payload.ready` 设为 `true`。
  3. 前端第 299 行将上传输入框条件绑定为 `{!payload.ready && !userChoices.length}`，`ready` 一旦为 `true`，上传输入框立即被永久卸载销毁。
  4. 最终导致用户既无法推进映射（后端 422 拒绝），又无法在页面上补传 eCRF 文件，形成致命的不可逆闭锁。
- **复现步骤**：
  1. 创建项目并在第1步录入数据文件夹；
  2. 在第3步仅上传方案文档，或让系统识别到 eCRF 未提供；
  3. 在角色确认卡片中单选勾选「本次未提供电子病例报告表」，点击「保存选择并继续」；
  4. 观察系统保存后进入映射生成阶段，主按钮变成「重新加载识别结果」，点击持续失败，且页面上再无任何可上传 eCRF 的控件。

---

### 【发现 2】HTTP 422 业务错误在第3步被静默吞噬，仅暴露无状态「重新加载识别结果」按钮
- **页面**：医学监查 · 数据接入向导第3步
- **严重度**：High
- **类别**：`product_bug`
- **证据**：
  1. 后端返回 `HTTP 422: {"code":"mapping_document_evidence_incomplete","message":"研究文件未通过完整性核对：未能从这组文件中读取到可核对的内容（如全部为扫描版或文件损坏）。请更换为可读取的文件版本后重新上传。"}`。
  2. 前端 `loadMappingCandidates` 捕获异常后派发 `type: "error"`，将 `mappingState.phase` 置为 `failed`。
  3. 但在第3步的当前 DOM 中，该 `error.serverText` 未在任何醒目位置向用户渲染；用户在界面上看到的只有按钮突然跳变为「重新加载识别结果」，点击后由于入参未变再度静默失败。
  4. 只有当用户偶然点击「返回上一步」退回第2步时，第2步的页面顶部才渲染出了该 422 警告横条。第3步存在严重的「静默吞错」缺陷。
- **复现步骤**：
  1. 触发发现 1 的 422 报错状态；
  2. 观察第3步界面，确认没有任何错误文本提示；
  3. 点击「返回上一步」回退到第2步，确认该 422 错误文本突然在第2步展示。

---

### 【发现 3】向导第2步（导入概况）缺少「返回上一步」按钮，阻断用户自救路径
- **页面**：医学监查 · 数据接入向导第2步（查看导入概况）
- **严重度**：High
- **类别**：`ux_issue`
- **证据**：
  1. 向导第2步的操作区只提供了单个主操作按钮「下一步：让系统核对字段」（`button.monitoring-admission-primary`），缺少常规向导必备的「返回上一步」按钮。
  2. 当用户在第3步遇到缺失文件死锁、点击「返回上一步」退回第2步后，被困在第2步进退两难，无法返回第1步重新选择文件目录或替换数据源。
  3. 即使刷新页面，向导也直接恢复第2步或重置状态，无法优雅回退第一步修改。
- **复现步骤**：
  1. 在第1步选择数据后进入第2步；
  2. 检查底部操作区，除「下一步：让系统核对字段」外没有任何回退按钮；
  3. 从第3步点击「返回上一步」回到第2步，同样无法回退至第1步。

### 【发现 4】SPA 步骤流转与弹窗关闭后键盘焦点彻底丢失至 `document.body`
- **页面**：全系统（新建项目弹窗关闭、向导步骤 1→2→3 推进）
- **严重度**：Medium
- **类别**：`ux_issue`
- **证据**：
  1. 在新建项目弹窗内按回车提交创建后，页面重定向至 `/monitoring`，激活元素变为 `document.body`；
  2. 在向导第1步激活「开始导入」按钮后，进入第2步时原按钮卸载，激活元素重置为 `document.body`；
  3. 此时键盘用户按 `Tab` 键，焦点不是停留在新步骤的内容区或跳过链接上，而是从整个 HTML 树顶部重新开始，必须连续按 `Tab` 15~21 次，逐个遍历顶部系统品牌按钮、10个主导航模块按钮、项目下拉菜单、新建项目按钮等，才能重新到达当前向导的操作区。
- **复现步骤**：
  1. 使用纯键盘导航操作新建项目或步骤切换；
  2. 观察 `document.activeElement`，在切换瞬间立即变为 `BODY`；
  3. 按一次 `Tab` 键，观察焦点跳回左上角「返回项目总看板」品牌按钮。

### 【发现 5】未满足条件时主操作按钮使用原生 disabled 导致键盘 Tab 序列断裂穿透
- **页面**：数据接入向导第1步
- **严重度**：Medium
- **类别**：`ux_issue`
- **证据**：
  1. 第1步的「开始导入」按钮在未填入路径时使用了 `<button disabled="" aria-disabled="true">`。
  2. 按照 HTML 标准，处于 `disabled` 状态的原生按钮无法接受焦点，被浏览器移出 Tab 焦点序列。
  3. 当键盘用户聚焦在「数据位置」输入框并按下 Tab 试图探索下一步操作时，焦点并未停留在禁用按钮并给出「请先选择数据」的提示，而是直接跳出向导容器，穿透跳回网页顶部的「返回项目总看板」按钮。
  4. 实施工程师在现场培训用户时，用户会困惑为何按 Tab 会意外跳出向导。建议遵循 WAI-ARIA 规范，保留 `tabindex="0"` 与 `aria-disabled="true"`，并配以说明 tooltip。
- **复现步骤**：
  1. 打开数据接入向导第1步，清空「数据位置」输入框；
  2. 聚焦在「数据位置」输入框；
  3. 按一下 `Tab` 键，观察焦点跳出向导直接聚焦到页面最顶部的品牌按钮。

### 【发现 6】多文件选择时偶发抛出裸文字 `Failed to fetch` 且无上下文指引
- **页面**：医学监查 · 数据接入向导第3步（文档上传控件）
- **严重度**：Low
- **类别**：`ux_issue`
- **证据**：

- **复现步骤**：
  1. 进入向导第3步文档上传区；
  2. 通过文件控件一次性传入方案与 eCRF 指南两个 docx 文件；
  3. 观察页面上偶发的红色 `Failed to fetch` 警告文字。

## 四、界面评价

### 易用性（Usability）
向导整体采用了三步式渐进披露模式（选择数据 → 导入概况 → 处理疑点），步骤指示器清爽明确，并在方案代号与项目代号不一致时，设计了非常实用的「资料归属人工确认」输入框与留痕机制，使得临床实施中的非标命名有了合规自愈途径。然而，向导在**异常容错与回退机制**上的设计极度匮乏：不仅允许用户单选确认实际上后端无法豁免的缺失文件，而且确认后立刻彻底销毁上传入口，同时剥夺了第2步返回第1步的按钮，使得用户一旦误选就彻底坠入无解的死胡同。

### 逻辑性（Logic）
系统在业务严格性与界面表现层上存在明显的口径割裂。后端引擎设计极为严谨，强制要求银屑病这类包含复杂量表（PASI/BSA）与访视周期的临床试验必须同时具备临床方案与 eCRF（`MAPPING_REQUIRED_DOCUMENT_ROLES`）；但在前端交互上，却允许用户将 eCRF 标为「本次未提供」并放行，界面甚至给出「研究文件已准备好，系统会自动完成字段理解」的过度乐观反馈，随后在下一步突然返回 HTTP 422 致命阻断。前端的宽容承诺与后端的强硬校验产生自相矛盾。

### 美观性（Aesthetics）
工作台采用符合医疗合规系统特征的深蓝（#0f172a）、冷灰与白底配色体系，视觉风格端庄沉稳。状态徽标设计得当，如「已识别」采用柔和绿色背景，「可稍后添加」与「已由用户确认未提供」采用灰/橙色系区分，层级分明；数据表展开面板（`<details>/<summary>`）排版工整，行数与列数元数据对齐规范。不足之处在于错误提示的视觉层级脱节：关键的 422 错误在第3步被完全隐形，而在第2步中以鲜红色全宽警告条突兀展现；偶尔出现的裸文字「Failed to fetch」缺乏内边距与图标引导，破坏了界面的工业化质感。

## 六、对「这套系统能否由一名真实用户独立跑通」的一句话判断

> **这套系统在核心合规校验（身份绑定、跨表复核）上具备严密的防差错逻辑，但由于前端缺少必要的向导回退路径、误导性地允许标记核心文件缺失并在随后静默吞噬 422 报错，真实用户在缺少或漏选关键文档时一旦误点确认将彻底陷于闭锁死循环，无法由一名真实用户独立跑通。**
