## 2. 总结论

**总结论：FAIL（严重阻断）**

**致命卡点**：
停滞在**数据接入向导第 3 步（研究文件与字段映射确认）**。系统在识别上传的 11.5MB eCRF 填写指南 PDF 时判定其不是规范权威文件（`document_authority_candidate_not_promotable`），界面文案指导用户「可对文件角色作出裁决后重试，或将该文件角色标记为缺失」，然而**界面并未提供任何裁决角色、标记缺失、忽略文件或单选方案推进的操作控件**；当用户试图重新单独上传合规的方案 docx 时，系统又因指纹复用判定「这组文件与此前上传的内容完全一致，系统直接复用已有核对结论」而将状态锁定在失败结论中；底层的 resolve 查询还因前端缺少 `batch_id` 参数不断抛出 422 错误，前端静默吞下并向用户展示虚假的「系统正在复核最后几个分歧」，推进主按钮「请先添加所需文件」置灰不可点。真实 CRA 无法通过界面任何操作走出此死循环。

## 3. 发现清单

### 【发现 1】研究文件角色裁决缺失交互入口，导致流程死锁（CRITICAL / product_bug）
- **页面**：医学监查 · 数据接入向导第 3 步（研究文件与字段映射确认）
- **问题**：系统文本明确提示「研究文件自动核对未完成（见诊断信息）；可对文件角色作出裁决后重试，或重新上传文件」，并在诊断中指出「请将该文件角色标记为缺失，或更换为可读取版本后重新上传」。但**页面上完全没有渲染任何单选框、下拉框、复选框或裁决按钮**允许用户将该文件标记为缺失或修正角色，界面承诺的功能在 DOM 中完全缺失。
- **严重度**：Critical
- **类别**：product_bug
- **证据**：
  - 界面显示警告文本：`研究文件自动核对未完成（见诊断信息）；可对文件角色作出裁决后重试，或重新上传文件。`
  - 页面整个 wizard DOM 中经审查 `select` 为 0 个、非 file 的 `input` 为 0 个，仅有一个处于 `disabled=true` 状态的「请先添加所需文件」按钮和一个「重新核对研究文件」按钮。
- **复现步骤**：
  1. 新建项目并完成前两步数据接入；
  2. 在第3步文件上传框中同时上传 `RUX-03-002_临床研究方案_V1.3.docx` 与 `RUX-03-002_eCRF填写指南_V1.0.pdf`；

### 【发现 2】研究文件核对 resolve 轮询接口缺少 batch_id 参数，前端静默吞错并呈现虚假加载（CRITICAL / product_bug）
- **页面**：医学监查 · 数据接入向导第 3 步
- **问题**：前端向后端轮询研究文件核对结果时，请求地址为 `/api/projects/proj_user_2cedc5687438/modules/medical-monitoring/r7/data-admissions/stg-ba492187238f48e682ddca16caecf746/study-documents/resolve`，漏传了必填 Query 参数 `?batch_id=...`。后端返回 HTTP 422 及明确报错 `{"code": "mapping_resolve_batch_id_required", "message": "研究文件核对查询缺少批次参数（batch_id）。请返回向导重新进入第3步；若持续出现请刷新页面。"}`。前端不仅未在界面报错提示用户，反而静默捕获该异常，并持续向用户展示「系统正在复核最后几个分歧」、「无需操作，系统会独立核对并自行处理差异」等安抚性虚假文案，欺骗用户在界面前长时间盲目等待。
- **严重度**：Critical
- **类别**：product_bug
- **证据**：
  - 浏览器 Resource Timing 捕获连续的 `study-documents/resolve` 请求，状态为 HTTP 422。
  - 直接在前端控制台 fetch 该接口返回完整 JSON：`{"code": "mapping_resolve_batch_id_required", "message": "研究文件核对查询缺少批次参数（batch_id）。请返回向导重新进入第3步；若持续出现请刷新页面。"}`。
  - 前端界面依然显示：「系统正在复核最后几个分歧 / 无需操作，系统会独立核对并自行处理差异。」
- **复现步骤**：
  1. 上传研究文件并触发核对；
  2. 打开浏览器网络面板或审查 performance entries；
  3. 观察对 `study-documents/resolve` 的调用，缺少 `?batch_id=`，接口持续返回 422。

## 4. 界面评价（资深 CRA 现场评测）

### 易用性（Usability）
对于出差各中心、习惯了 EDC/CTMS/RTSM 直来直去操作的 CRA 来说，这套系统在**初期建项阶段的易用性令人惊喜**：新建项目流程非常清晰，多选卡片精准勾选「医学监查」后一键直达对应工作区，配置抽屉字段精炼，没有冗余表单；在数据接入第 1 步和第 2 步，对本地 18.8MB 大文件的复制与 54 张表解构的进度提示（显示精确秒数和预估时长）非常明确。然而，**易用性在第 3 步遭遇断崖式崩塌**：一旦后台判定文件存在瑕疵，系统文案明明指导用户「可对文件角色作出裁决」，界面上却根本没有提供裁决交互；同时，唯一的推进主按钮被置灰但未给出可执行的解锁路径，陷入典型的「死胡同」交互，缺乏对临床非技术用户的自愈与引导能力。

### 逻辑性（Logic）
系统在数据结构处理上的**幂等性与去重逻辑值得赞赏**：在重复选择已导入文件时，系统能精准计算 Hash 并给出「与此前导入数据内容完全一致，属重复导入——数据未翻倍」的专业反馈，符合 GxP 数据完整性要求。但是在**研究文档流转逻辑与状态机上存在明显断层**：首先，后端既然要求 `batch_id` 参数，前端轮询却未带该参数，造成接口契约脱节；其次，前端捕获到接口报错后未向用户展示真实原因，反而用「正在复核最后几个分歧」这套静态安抚文案进行逻辑伪装；最后，文件缓存指纹将「一次上传失败的集合」与「后续单文件上传」混为一谈，违反了文档管理中的版本替代逻辑。

### 美观性（Aesthetics & Visual Polish）
系统整体视觉基调专业稳重，采用康哲风格的深蓝与浅灰搭配，顶栏的研究分期标签、当前来源胶囊以及状态矩阵的网格对齐规范利落，整体质感脱离了粗糙的“程序员后台”感。向导的步骤指示器（Step 1/2/3）带有清晰的状态流转色彩，大表列表的展开/折叠样式规整，表名与行数、列数、字段缺失度（如缺失241行、日期区间）的数据可视化标签排版清晰紧凑，易读性极佳。遗憾之处在于**错误状态下的视觉降级不够优雅**：诊断信息弹框缺乏结构化排版，长段错误文本混杂在说明文字中，且关键主操作按钮在禁用状态下对比度不足，无法一眼看出是“正在计算暂时禁用”还是“前置条件缺失永久禁用”。
