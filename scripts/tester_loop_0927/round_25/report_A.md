## 三、发现清单

### F1【critical / product_bug】字段识别停滞，随后后端服务无响应，流程完全中断
- 【页面】医学监查 → 数据接入向导第3步「研究文件与字段映射确认」
- 【问题】字段识别进行到136个字段后长期停滞（页面持续显示「已识别 136 个字段，识别仍在生成中」「正在读取系统识别结果…」，约36分钟字段数无变化）；刷新页面后项目列表加载失败（「项目列表加载失败或超时（超过20秒未返回）。请点击重试；若持续失败请检查服务状态」），间隔5分钟两次点击「重新读取」均失败，最终停在「项目服务暂不可用」。用户在纯浏览器操作下无任何恢复路径。
- 【证据】轮询日志：t≈1170s 起字段数恒为136（两轮共36分钟：8.5分钟+28分钟）；刷新后页面文本「项目服务暂不可用」「项目列表读取失败（超过20秒未返回）」；两次重试后状态不变。
- 【复现步骤】新建项目（仅医学监查）→导入 DataListing.xlsx→上传研究方案+DraftCRF→完成归属人工确认与适应症差异确认→等待字段识别→观察字段数在136处停滞≥30分钟→刷新页面→项目列表读取失败→点击「重新读取」两次（间隔5分钟）。

### F2【high / product_bug】人工归属确认提交后长时间无反馈；刷新后向导文件登记状态丢失，需全部重来
- 【页面】数据接入向导第3步「研究文档准备情况」
- 【问题】点击「确认属于当前项目并继续」（附确认说明）后，界面仅显示「系统正在识别并交叉核对…」，超过9分钟无任何结果或状态变化；按界面提示（「若长时间无进展，请重新打开向导」）刷新后，研究方案与eCRF回退为「尚未添加」，必须重新上传两份docx并重新等待约18.5分钟核对。注：第二轮核对未再要求归属确认，说明后端的人工归属裁决本身已生效——丢失的是向导前端状态与已上传文件的登记状态，属于流程衔接缺陷。
- 【证据】确认后快照持续为「系统正在识别并交叉核对…」（>9分钟）；刷新后快照「研究方案 尚未添加／电子病例报告表 尚未添加」＋「最近一次研究文件核对结论：系统还无法确认资料归属……（记录于 2026-10-07T23:01:31）」仍为确认前旧结论。
- 【复现步骤】向导第3步上传两份docx→等待核对结论出现归属确认区→填写说明并点击「确认属于当前项目并继续」→等待≥9分钟观察无进展→刷新页面→重新打开向导查看「研究文档准备情况」。

### F3【medium / ux_issue】长任务缺少中间进度与预计时长，用户无法区分「慢」与「卡死」
- 【页面】向导第2/3步
- 【问题】「正在核对研究文件…」一次持续约18.5分钟，期间无任何中间产出展示；字段识别仅显示字段总数（0→12→36→76→136），无表级进度（59张表处理到第几张）、无已耗时/预计耗时。对比之下导入阶段有良好示范（「正在导入…（已用时 3 秒；大文件复制与解析可能需要数分钟）」），核对与识别阶段没有同等反馈。
- 【证据】等待期间页面唯一变化为字段计数字本体的跳变；轮询日志时间线。
- 【复现步骤】同F1/F2，观察核对与识别等待期间的界面元素变化。

### F4【low / ux_issue】方案适应症匹配过于字面，复合表述无法命中，增加人工确认负担
- 【页面】向导第3步「系统发现以下内容差异」面板
- 【问题】项目适应症填「初治阵发性睡眠性血红蛋白尿症（PNH）」，系统对研究方案docx报「文件内容：未在文件名、标题或正文中识别到预期内容（依据位置：docx:document_text）」——PNH III期研究的方案正文必然包含适应症表述，匹配器未能将「初治PNH/阵发性睡眠性血红蛋白尿症」等写法与项目字段对上。系统以人工确认（「差异不影响本次监查，继续使用」）兜底，语义上诚实（只陈述“未识别到”，未虚构差异），故不计medical_accuracy；但每份文件都要人工点确认，真实使用中负担会累积。
- 【证据】差异面板文本（当前项目/文件内容/依据位置三行对照）。
- 【复现步骤】项目适应症填写与方案正文措辞不完全一致的自拟复合表述→上传方案→等待核对→观察差异面板。

### F5【low / cosmetic】审计时间戳口径不一致，并排显示易误读

- 【问题】顶栏「最后更新」显示本地时钟（如 01:11），核对结论落款为「2026-10-07T23:01:31」，两个时间体系相差约2小时且无时区标注（无法确认服务器时区，仅报告并排显示这一现象）。对PV审计场景，结论落款时间是追溯依据，建议统一时区或标注口径。
- 【证据】两处UI文本并排可见。
- 【复现步骤】完成一次文件核对后，同时观察顶栏「最后更新」与结论落款时间。

## 四、界面评价（易用性 / 逻辑性 / 美观性）

**易用性**：引导链路对新手友好——首页空态直接教学（「从『新建项目』开始：选择要启用的子系统……」），子系统多选卡片→「前往医学监查配置」→配置面板→向导三步条（选择数据/导入概况/研究文件与字段映射确认），每一步的下一步都有明确按钮；门禁横幅「字段核对尚未完成，确认完成前不会启动医学监查」把规则前置说清。配置面板的防错文案值得表扬（「管理代号请填在这里，不要填入试验药物」）。扣分项：长任务无进度与预计时长（F3），确认提交后无阶段性反馈，用户只能干等或刷新，而刷新恰恰触发F2的状态丢失。

**逻辑性**：状态机整体一致——「确认前不会生成可用于监查的数据；确认后也只保存字段对应关系」明确了数据生效点；归属人工确认会「写入项目工作区的裁决档案（identity_overrides，含操作人与时间）」，有审计留痕意识；识别口径透明（「系统不会把代码对照表、名册页等辅助表静默排除在识别之外」「表数按文件内的全部工作表统计」）。最大的逻辑断点在F2：已提交并声称留痕的确认，与向导前端状态在刷新后脱节，用户被迫重复整个核对流程。

**美观性**：诚实声明——本测试者为文本界面操作，未做像素级视觉检查（仅存档1张截图且无法目视核验），且后端不可用后页面只剩错误态，1440/1920宽屏表现未测（本轮视口1728×963）。基于DOM结构与文案层级的观察：区块层级清晰（顶栏→项目上下文条→模块页头→向导卡片），信息密度适中，文案严谨不浮夸（如「分期未知（待核实，不作为已核实事实）」这一诚实选项、「通知中心尚未开放」的直白标注）；错误页给出超时阈值与可执行动作而非笼统报错。「敢不敢给领导演示」的视觉结论本轮无法给出，仅认可其表达层面的专业感。
