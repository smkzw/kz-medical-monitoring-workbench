## 二、总结论

### 结论：FAIL（不通过）

**卡点描述**：
1. **主阻断**：第3步「研究文件与字段映射确认」遭遇不可逆 UI 死胡同。由于初次仅上传方案并勾选「本次未提供电子病例报告表」，后端拒绝在缺少 eCRF 证据下生成字段映射（返回 422 `mapping_document_evidence_incomplete`）。但前端在用户提交选择后彻底移除了文件上传组件，文案承诺的「如需更换，可在保存后重新上传文件并重新核对」完全落空，用户无任何界面途径重新上传 eCRF 文件，重试按钮仅能死循环重放 422 错误。
2. **伴随次级阻断（严重性能/架构级问题）**：后台执行文档交叉分析期间，FastAPI 服务的 `/api/projects` 接口因资源竞争/锁竞争延迟飙升至 43~50 秒，直接击穿前端硬编码的 20 秒超时限制，导致整个系统触发「项目服务暂不可用」全屏阻断。因 `selectedProjectId` 丢失，顶部所有模块标签全被禁用置灰，用户被完全锁死。

## 三、发现清单

### 【发现 1】
- **页面**：数据接入向导 · 第3步「研究文件与字段映射确认」
- **问题**：eCRF 标记未提供后映射生成触发 422 报错，且前端文件上传入口被彻底销毁，形成不可自救的死胡同
- **严重度**：critical
- **类别**：product_bug
- **证据**：
  在文档角色确认中，用户选择「本次未提供电子病例报告表」并点击「保存选择并继续」后，系统调用 `startDataAdmissionMappingCandidates` 接口，后端返回 HTTP 422：
  ```json
  {
    "code": "mapping_document_evidence_incomplete",
    "message": "研究文件未通过完整性核对：未能从这组文件中读取到可核对的内容（如全部为扫描版或文件损坏）。请更换为可读取的文件版本后重新上传。"
  }
  ```
  此时前端界面将原本的文件上传组件彻底销毁，页面只剩下「重新加载识别结果」按钮。点击该按钮只会重新调用同一接口并反复报 422 错误。即便用户此时手头有 `MG-K10-CSU-001_eCRF填写指南_V1.0.docx`，界面也无任何上传、更换或重置入口，整个向导卡死在此状态。
- **复现步骤**：
  1. 新建项目并完成第1步与第2步数据导入；
  2. 在第3步仅上传 `MG-K10-CSU-001_临床研究方案_V1.3.docx`；
  3. 等待核对完成后，界面弹出「哪份是电子病例报告表？」，勾选单选项「本次未提供电子病例报告表」，点击「保存选择并继续」；
  4. 观察系统抛出 422 错误，界面所有文件上传入口消失，死循环报错。

### 【发现 2】
- **页面**：数据接入向导 · 第3步「研究文件与字段映射确认」
- **问题**：缺少配对文档被前端错误归咎为「扫描版或文件损坏」，存在对研究材料的不实指控（语义不诚实）
- **严重度**：high
- **类别**：medical_accuracy
- **证据**：
  当后端因缺少 eCRF 证据链返回 `mapping_document_evidence_incomplete` 时，界面红字提示显示：
  > 「研究文件未通过完整性核对：未能从这组文件中读取到可核对的内容（如全部为扫描版或文件损坏）。请更换为可读取的文件版本后重新上传。」
  
  实际上传的方案文件为合法、规范的 Word docx 文档，且此前已被系统成功识别为「研究方案：已识别」。系统真正的阻断原因是「eCRF 未提供导致字段无法映射」，但前端却将错误归因于「文件是扫描版或文件损坏」。在临床试验稽查中，对申办方/机构的研究文件做此种虚假归因极不严谨，存在严重的专业信誉风险。
- **复现步骤**：
  同发现 1，观察出现 422 错误后的提示文案。

### 【发现 3】
- **页面**：系统全局 / 项目总看板
- **问题**：后台分析作业期间 `/api/projects` 耗时飙升至 50s 击穿前端 20s 超时门限，导致全局「项目服务暂不可用」锁死（R30-01 严重复发）
- **严重度**：critical
- **类别**：product_bug
- **证据**：
  当系统在后台运行文档分析与核对作业时，实测前端请求 `/api/projects` 的耗时由常态的 4ms 飙升至 **43,350ms ~ 49,723ms**。而前端代码对该请求硬编码了 20,000ms（20秒）的客户端 AbortController 超时。由于请求耗时远超 20 秒，前端每次请求均强制 abort 并展示错误全屏：
  > 「项目总看板：项目服务暂不可用 —— 项目列表加载失败或超时（超过20秒未返回）。请点击重试；若持续失败请检查服务状态。」
  
  由于此时未能获取到当前项目数据，顶部全局导航栏的所有模块按键（「医学监查」、「入排审核」等）全部置灰禁用，用户被彻底阻隔在系统之外，既无法进入工作台也无法操作。直至后台作业完全结束、接口耗时回落至 17.9s（低于 20s）后，点击「重新读取」才得以恢复。
- **复现步骤**：
  1. 上传研究文件并触发后台双核对/分析作业；
  2. 在后台作业活跃期间（入队约 1~5 分钟内），刷新页面或在新标签页打开 `http://localhost:5178/monitoring?project_id=...`；
  3. 观察前端在精确等待 20 秒后报错中断，全站导航锁死。

## 五、界面评价

### 1. 易用性（Usability）
在主干顺畅时向导性良好，每一步骤均有明确的承接提示。但防错容错机制存在致命死穴：在第3步一旦做出不可撤回的文档选择（标记 eCRF 缺失），原本的文件选择器会被无情销毁，用户无法「后悔」或补充文件。提示文案承诺「可在保存后重新上传文件并重新核对」，但在界面上却找不到任何上传按钮。这种「文案承诺存在，界面入口蒸发」的设计给初次使用的用户造成极大挫败感。

### 2. 逻辑性（Logical Flow）
系统的内在业务逻辑存在两处严重的口径割裂：
第一，文档准入逻辑允许用户选择「本次未提供电子病例报告表」，但在下一步字段映射引擎中，却又将 eCRF 视作必须的证据链，直接返回 422 报错拒绝继续。既然 eCRF 是映射的不可或缺前提，前端就不应允许用户轻易提交「未提供」，或在未提供时直接提示风险，而非在后台静默抛错。
第二，后端 `/api/projects` 在有后台任务时常态耗时 40~50 秒，而前端超时却强设为 20 秒，前后端 SLA 设定自相矛盾，导致正常运行的系统因客户端过早超时而直接崩溃全屏。

### 3. 美观性（Aesthetics & Visuals）
界面整体遵循了医疗专业系统的沉稳风格，色彩搭配克制（蓝灰底色配高对比度文字）。卡片化布局、步骤条（第1步/第2步/第3步）以及表结构清单的收折设计规范工整，字体排版和间距对齐表现良好。但在异常状态下，多处重叠的警告卡片（如数据接入向导内部出现警告的同时向导外部又挂着同样的警告）破坏了视觉层级，信息冗余明显。
