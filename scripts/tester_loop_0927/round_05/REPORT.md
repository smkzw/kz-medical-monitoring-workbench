## 五、复盘与策略

### 根因归类

1. **R3-01 家族（映射确认不收敛）仍是全链唯一战略锁**，机制清单增至五种（见第三节）。它同时消耗真人路径（B/C）与自动化路径（预置脚本 13:40 被 422 挡住）。cf80887 的终态失败上报＋幂等重排队是对症方向，但 **≤15 分钟验收标尺下 B 的 159 分钟差距仍以十倍计**，修复深度有待 R6 检验。
2. **后端就绪与界面就绪之间的状态断裂（R5-03 家族）**：同一项目，台账说可用、抽屉说阻断、顶栏说未登记、告警说打不开——四处口径互斥。这是本轮开考位失败的直接原因，也解释了 R3-12/R1-13/R5-06/R5-07 一串「元数据与状态脱节」类发现：**各模块各自读各自的状态源，没有单一事实源**。
3. **预置通道的设计教训**：走与人相同的 UI 管线做预置，会把人遇到的所有门（角色裁决、确认题、收敛慢）都再撞一遍（84 分钟 API 硬推才通）。正确做法是**后端直写状态**（直接写入「文档已识别＋映射已确认＋事实已就绪」的项目状态），跳过向导管线。
4. **通道侧五轮来首次全绿**：无报告覆盖、无路径失败、无空转（A 位 runner 首次空输出后自动同会话恢复成功——工具修复见效）；唯一残留问题是通道侧「自动会话续接要求」把 A 的会话提前掐断（未达停止线），需要在规程上明确通道不得先于测试纪律收束。
5. **诚实性机制在自我修正**：分诊更正自己的 R4-03 假设、修复侧验收留痕如实记录「新发现待下批」、测试者 A 主动声明自己的结果不算停滞证据——这套文化是本循环五轮下来最稳的资产。

### 停滞与升级

- 满 5 轮：R1-01、R1-05、R1-07～10、R1-13、R1-15（8 条）；满 4 轮：R2-02、R2-04、R2-06～09、R2-12（7 条）；满 3 轮：R3-02～13（12 条）；满 2 轮：R4-01～06（6 条）。合计 33 条停滞，其中 R1＋R2 共 15 条按工作流规则处于正式升级区。
- **但停滞的性质已经变了**：这 33 条全部处于「修复已落地、复测未做」状态（批量冲刺 4c0ea2b 覆盖了全部存量）。当前的问题不再是「没人修」，而是「没人验」。四轮的升级请求已被所有者用行动回应（8201064）；本轮的升级请求相应转为：**授权「修复即自验」的收口规则**——修复方在冲刺内已完成验收留痕（9f09074），建议规则化为：low/cosmetic 类以修复方冒烟自验＋抽查即可关闭，medium/high 类必须独立复测，避免 34 条待复测把后续每轮的测试位全部吃掉。
