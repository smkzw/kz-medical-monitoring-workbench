## 二、发现清单

### D-01【critical / medical_accuracy】差异面板虚构文件内容，并标注伪造的依据位置
- **页面**：医学监查 → 数据接入向导第三步「需要您核对文件内容 / 系统发现以下内容差异」
- **问题**：研究方案条目声称「文件内容：COVID-19 / NM-139 / NM-198 / PNH-2-01 / PNH-3-02，依据位置：docx:document_text」。经我对三份上传材料做全量核查（docx 解包后全部 XML 部件 + xlsx 全部 XML 部件 grep）：**NM-139、NM-198 在任何一份文件中出现次数为 0**；COVID-19 仅作为排除标准用语出现（「活动性全身细菌、病毒（包括COVID-19）或真菌感染史」），不是研究标识。系统把不存在的内容当作"从文件提取的证据"展示并要求医学经理签核——这正是"把不知道伪装成结论"的语义不诚实，且签核记录会被留档。
- **证据**：面板原文（见旅程 10:30 快照）；核查命令与结果：`unzip` 两个 docx 后对 `**/*.xml` grep `NM-139|NM-198` 均为 0 hits；xlsx 全部 XML 部件 `NM-139/NM-198/COVID` 均为 0 hits；方案 `word/document.xml` 中 `COVID` 3 hits 且全部位于排除标准句。
- **复现步骤**：新建项目（自动代码与方案编号不同）→ 上传本套研究方案与 CRF → 等待差异面板出现 → 查看研究方案条目的「文件内容」清单。

### D-02【high / medical_accuracy】适应症核对把"未精确匹配"谎报为"未在正文中识别到"
- **页面**：同上差异面板，研究方案条目「适应症」小项
- **问题**：面板声称「文件内容：未在文件名、标题或正文中识别到预期内容」。事实：方案标题页即为「……在既往未接受过补体抑制剂治疗的**阵发性睡眠性血红蛋白尿症**患者中评价 MY008211A 片……」，全文该词出现 21 次。我的项目适应症填的是「阵发性睡眠性血红蛋白尿症（初治PNH）」——即便因括号补充语导致精确匹配失败，如实的表述应是"未匹配到与项目适应症字段一致的表述"，而非"正文未识别到"。该不实陈述使用户被迫对一个并不存在的差异签署「差异不影响本次监查，继续使用」。
- **证据**：面板原文；`word/document.xml` 提取纯文本后 `睡眠性血红蛋白` 21 hits、`阵发` 22 hits，首个上下文即标题句。
- **复现步骤**：同 D-01。

### D-03【high / product_bug】字段自动识别 4.5 小时未完成，主链不可达
- **页面**：数据接入向导第三步「系统已自动识别 N 个字段 / 已识别 N 张数据表」
- **问题**：59 表 / 3557 行的清单，字段识别从 10:33 跑到 15:07（4h34m）仅到 49 表 / 1349 字段，确认按钮始终禁用。进度虽然可见且单调递增（约 5 字段/分钟），但既无总量参照（不显示 49/59），也无预计完成时间。"假定只有两小时空闲"的情境下，本系统在任何有意义的时间预算内都走不完接入阶段；等待期间页面还发生过一次向导面板自动收起（约 10:59），需要用户自己重新打开并两次点击才能回到进度视图。

### D-04【medium / product_bug】固定页脚遮挡「数据位置」输入框，录入被拦截
- **页面**：数据接入向导第一步「无法选择文件夹时，手动填写数据位置」
- **问题**：视口高 649px 时（输入框 y≈558–592，页脚占底部），`page.fill` 连续两次报「`<footer>` intercepts pointer events」，`scrollIntoView` 后依然被拦。自动化与矮窗口真实用户同样受阻；我最终以脚本直填值+派发事件绕过。
- **证据**：两次 fill 超时报错原文；`getBoundingClientRect` 输出 `{y:558.77, h:34}`，`innerHeight:649`。
- **复现步骤**：窗口高度 ≤650px 打开向导第一步，尝试点击/输入「数据位置」。

### D-05【medium / ux_issue】核对进行中的上传会丢：刷新/面板收起后文件回到「尚未添加」
- **页面**：数据接入向导第三步「研究文档准备情况」
- **问题**：10:24:45 第一次上传两份 docx 后系统显示「正在核对研究文件…」；10:25:48 我整页刷新一次（系统自己提示"整理在后台进行时，可以离开页面，稍后再查看"），10:26:11 重开向导后两文件均回到「尚未添加」，首次上传凭空丢失，必须重新上传（10:26:25 第二次上传才留存）。约 10:59 还发生过一次无人操作的面板自动收起，同样要求用户手动找回视图。
- **证据**：三次快照串（上传后"正在核对"→刷新后"尚未添加"→二次上传后正常）。
- **复现步骤**：上传 docx 后立即刷新页面，重开向导第三步。

### D-06【low / ux_issue】空项目误报「暂时无法安全打开此项目」
- **页面**：医学监查首页（checklist 视图）顶部 alert
- **问题**：新建项目落地后立即出现「当前内容暂不可用：暂时无法安全打开此项目，请保留原项目并联系支持」，点「重新读取」不消失；数据导入后自行消失。对刚建好的空项目这是误导性噪音，且"联系支持"的指引无中生有。
- **证据**：10:21–10:25 期间四张连续快照均含该 alert。
- **复现步骤**：新建项目后立即观察医学监查首页。

### D-07【low / ux_issue】字段全列表面渲染过重，页面近乎不可交互
- **页面**：向导第三步「查看全部字段的识别结果」展开区
- **问题**：展开后一次性渲染上千条「表 · 变量 · 类型」条目，两次 CDP `Page.captureScreenshot` 均超时失败。真实用户在该状态下的滚动/点击将明显卡顿。
- **证据**：15:06、15:07 两次截图报 `CdpRequestTimeoutError: Page.captureScreenshot`；快照单次输出达 170–180KB。
- **复现步骤**：识别进行中展开「查看全部字段的识别结果」并截图/滚动。

## 四、正面观察（非发现）

- 门禁人工放行链路真实可用：差异确认后两份文件即转「已识别」，未出现 R1 描述的放行失效。
- 导入概况诚实：如实展示 1 文件 · 59 表 · 3557 行，未见美化。
- 首页热力图区写明「仅在后端返回真实风险矩阵后展示；当前不使用固定示例值替代」——这类"没有数据就说没有"的表述符合语义诚实要求。
- 文件夹选择器在自动化会话不可用属环境限制（webkitdirectory 输入框 `setInputFiles` 后 `files` 保持为空），界面自带的「手动填写数据位置」回退路径按设计可用，不计为产品缺陷。

## 五、一句话判断

**这套系统当前不能由一名真实用户独立跑通**：建项、上传、人工放行都没问题，但 59 表清单的字段识别跑了 4.5 小时以上仍未结束，任何真实医学监查员的时间预算都会在半路耗尽；更要紧的是，它在要求人签核的差异面板里编造了文件中不存在的标识（NM-139/NM-198），签核凭据本身不可信。
