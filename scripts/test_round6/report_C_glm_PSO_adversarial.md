## 3. 对抗样本专章（任务重点2）★

### 3.1 对抗样本构造
- 源文件：`CMS-D001-PSO-201_eCRF填写指南_V1.0.docx`（37,937B）
- 对抗件：字节级复制，改名 `PSO-201_临床研究方案V2.0.docx`——**内容是eCRF填写指南，文件名冒充研究方案V2.0**

### 3.2 系统如何对待冒充方案（如实作答）

**答：系统不读内容判定角色，只看文件名/元数据做候选提名，最终把裁决权交给人工，且不做任何内容一致性校验。**证据链：

1. **候选提名无内容验证**：单独上传对抗件后，裁决面板把 `PSO-201_临床研究方案V2.0.docx` 同时列为 protocol 角色候选（「这是protocol文件：PSO-201_临床研究方案V2.0.docx」）——一个正文满篇「eCRF字段说明」的文件被系统提名为研究方案候选，**系统未给出任何「内容疑似不是方案」的提示**
2. **双角色同时提名**：同一文件在同一面板中同时是 ecrf 角色和 protocol 角色的候选——系统对「一个文件只能是一种文档」无内容层面的判断
3. **人工裁决完全放行**：面板标题明示「医学判断以您为准」，即系统设计上接受「用户指鹿为马」；本轮实测把真eCRF指南裁决为protocol角色提交，下游唯一反应是另一个**机制性**诊断码（见3.3），**没有出现任何基于内容的质疑**
4. **对比观测（真实方案上传A项目）**：真方案在A项目同样先被要求人工裁决，未因「内容是真方案」而免裁决——进一步证明裁决面板与内容无关

**结论（CFDI视角）**：文件角色确认环节是**纯人工背书**环节。若真实场景中CRA误选或恶意指派，系统第二道防线（内容校验）不存在；「冒名方案」一旦被人工确认，将直接以「研究方案」身份进入监查依据库，被后续跨表核对引用时无任何告警。**P0风险**。

### 3.3 顺带发现：三个未公开的裁决管线规则（P0可用性/一致性缺陷）

通过B项目系统化探测（构造各种裁决组合+6分钟级轮询）确认：

| 探测 | 结果 | 系统反馈 |
|---|---|---|
| 同一文件同时裁决为 protocol+ecrf | **提交按钮禁用**，tooltip「请先为每个角色作出选择」 | 错误提示误导（实际规则是「一文件一角色」，tooltip说的是另一回事） |
| ecrf=对抗件，protocol=缺失 | 按钮可用，提交被拒 | 诊断码1 |
| 仅上传真指南，裁决为 protocol | 提交被拒 | **诊断码2: `document_authority_candidate_role_collision`** |
| 仅上传真指南，裁决为「protocol缺失」 | 提交被拒 | 诊断码1 |
| protocol=缺失 循环提交4次+6分钟等待 | 面板无任何变化 | 同码 |

**核心矛盾**：这些规则均未在UI上向用户披露（无规则说明、无冲突高亮、无可构造解提示）。B项目截至报告时点仍无法完成文档注册。结合A项目的同码死锁，**文档裁决→注册管线在当前版本对所有「触发人工裁决」的场景都可能不可通过**——这本身比对抗样本问题更严重。

### 3.4 对抗样本最终定级

- **无内容级反欺骗能力**：P0（若生产环境按此逻辑运行）
- **裁决管线死锁**：P0（阻断监查主链路）
- 「重新读取」按钮对裁决面板无效（点击后面板原样保留）：P2

### 5.1 隔离性观察（数据层）

- **核对结果层隔离无法验证**：两项目均未到达核对阶段

### 5.2 交错操作发现的重大问题：**异研究文件静默混入**（P1）

T3中数据接入指向了共享目录`/tmp/test_materials`（含另一研究的`MG-K10-CSU-001`材料）。系统识别结果同时呈现：
- CMS-D001-PSO-201 的10张表（478行）+ **MG-K10-CSU-001 的10张表（含UAS荨麻疹评分表，473行）**
- **系统未发出任何「同一数据接入中存在两个不同研究/不同文件命名体系」的警告**

虽然每张表标注了来源文件名，但「表名同为DM/MH/AE」的两套数据并列呈现，医学监查中极易误用（CSU的AE混入PSO的受试者池）。对比B项目（专用目录）识别为1文件10表，确认混入源是目录指向而非系统错误。**建议**：导入时按文件名前缀/项目代号做来源一致性校验并强制人工确认。

### 5.3 交错暴露的稳定性问题
长会话（约60min+）后GUI元素定位开始失真（footer拦截、元素匹配0），刷新后恢复。双项目交错操作（频繁切换）是否加速该现象未做定量对比——本轮样本不足以定级，记录待观察。

## 7. 反过拟合章节（防「为通过本轮测试而存在的实现」）

**问题**：本轮测试大量时间消耗在文档裁决管线的三个诊断码上。评估者必须回答：这些失败是「真实缺陷」还是「测试方法导致的表象」？

**证据支持「真实缺陷」的观察**：
1. 操作均为UI正常路径（无API绕行、无非预期输入）；上传的文件格式合法（.docx，与A项目第一次上传成功解析的文件相同）
2. 同一操作在不同项目、不同文件组合、不同会话状态下**确定性复现**（A: 5次；B: 6+次），等待时间最长6.6分钟，远超正常AI核对耗时（成功场景<90s）
3. 失败发生在**前端轮询后端**的架构下——诊断码由后端生成（`resolve`接口 60-140ms 快速返回失败态），说明是服务端注册逻辑主动拒绝，不是前端渲染bug
4. 每次提交后系统都「重新开始两轮核对」（文案自述），但核对结果恒为「无法自动判定」——如果AI真的在重读文件，不应每次都得出同样的不可判定结论，除非判定逻辑本身有缺陷或输入有系统无法消解的状态残留

**证据支持「测试环境表象」的可能**：
1. 后端AI队列接口（`/api/.../ai/queue`）持续返回401大小（401B固定长度、无payload），**独立AI通道可能未鉴权/未连通**——若文档核对依赖该AI，则死锁是「AI后端未配置」的下游表现，生产环境配置AI后可能消失
2. 项目标题栏显示「AI 设置 · zhipu-coding-plan · glm-5.3-flash 可运行」，与queue 401矛盾——存在配置不一致
3. 无法排除：裁决管线对「同一文件多角色候选」场景的校验规则设计为「必须一个文件对应一个角色且必须覆盖所有必需角色」，而当前测试恰好永远差一个文件（A: eCRF被判非必需；B: protocol被锁），形成「永远差一步」的病态组合

**结论**：文档管线的死锁**在当前部署状态下是真实且确定性的**，但其根因可能是后端AI依赖未就绪（环境问题）而非前端/管线设计缺陷。**给开发的定位建议**：优先检查 ai/queue 鉴权链与 document authority 注册服务的事务状态机。**给测试的同学**：复现时务必用「单独上传一个合法研究方案」作为起点，若复现 `registration_validation_blocked` 即与本报告同源。

**防止本轮结论被过拟合的三个要求**：
1. 不得以「测试方法不当」为由关闭§3.2对抗样本发现——该发现基于系统**正向展示的行为**（候选提名、双角色并列、「医学判断以您为准」），与管线死锁无关，任何修复版本中都必须重新验证「系统是否在候选提名前做内容预检」
2. 「诚实性加分项」（§4）不能抵消P0——诚实展示失败与失败本身是两个维度
3. 修复验证必须覆盖：A路径（正常材料全链到监查结果）+ B路径（对抗样本拦截或显式内容告警）+ 混入场景（§5.2）三条独立链路
