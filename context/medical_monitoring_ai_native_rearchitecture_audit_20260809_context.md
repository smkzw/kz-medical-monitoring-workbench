## 5. 当前判断

现有工程不是空白原型，已经积累了风险身份、来源证据、批次、映射、规则、AI 候选、日常运行、Patient Profile、Subject Timeline、CAS、审计和多级汇总等可复用资产；但它尚不是一个 AI 原生医学监查系统。主要原因是：

- 产品骨架由既有 RUX/MG-K10/MY009 适配器与 Profile/Timeline/漏报能力向外拼接；
- 控制流分散在巨型 `main.py`、巨型 `App.jsx`、多 SQLite 仓储和大量局部合同中；
- 规则、AI、医学风险、处置与聚合存在多个相邻权威面；
- 系统按功能切片演进，未先定义统一的医学监查任务图、状态图和 Agent 交付物；
- 测试投入大量用于身份/hash/shape/fail-closed 微合同，真实用户流程和医学科学性证据不足。

Graph engineering 适合该系统，但推荐的是“确定性状态图 + 有界专业 Agent + 独立 QC + 人工医学门控”，而不是七个 Agent 自由对话或让统筹 Agent 单独决定正式医疗结论。

## 6A. 已确认设计决策

### D1：正式医学权威采用受控自治（用户选择 C，2026-08-09）

- 高置信度、可由确定性证据与规则重放验证的低/中风险，可以自动进入正式风险记录。
- 高风险、证据冲突、低置信度、超出已批准规则能力、会改变重要医学结论或需要对外输出的事项，必须进入人工医学复核。
- 用户可在任一后续阶段监查中新增最初未定义的特殊风险评判条件。
- 用户可用自然语言描述条件；AI 负责拆解为结构化规则候选，包括适用范围、输入字段、时间窗、阈值、逻辑、例外、风险等级、证据要求和不确定性。
- 新规则必须先展示可读解释、字段/数据依赖、影响范围和模拟结果，由用户确认后形成不可变版本并激活；AI 不得静默改写已激活规则。
- 自动形成的正式风险仍须保留来源事实、规则版本、运行版本、置信度、自动确认原因和可撤销/复核状态。
- 既往签署的医学判断不得被新规则静默重写。新规则如何处理历史数据，留待下一项决策。

### D2：新增规则的历史作用范围按激活实例选择（用户选择 C，2026-08-09）

- 每次激活新规则或新规则版本时，用户在以下三种范围中选择：
  1. 全历史回溯：覆盖保留的历史来源修订和快照；
  2. 当前数据快照：只对激活时选定的数据截止版本运行；
  3. 仅未来数据：只处理激活点之后进入的新来源修订。
- AI 必须根据规则涉及的受试者安全、数据可靠性、潜在系统性问题、监查模式、数据可得性和计算代价给出推荐及理由，但不能代替用户选择作用范围。
- `evaluation_scope`、数据截止时间、基线/来源修订和推荐理由写入不可变 `rule_activation` 记录；更改范围必须创建新的激活版本。
- 全历史回溯产生的命中作为当前 run 的“回溯性发现”，同时展示事件发生时间、规则激活时间和风险发现时间；不得改写既往已签署报告、处置或基线。
- 当前快照只依据所选快照的当前事实状态，不把已被后续修订替代的旧值重新当作当前事实。
- 仅未来数据以激活时的来源边界作为水位线，后续每批增量按同一规则版本执行。

### D3：顶层任务采用研究级 Monitoring Run，并独立区分全量/增量（用户选择 A 并补充，2026-08-09）

- 一个顶层任务的基本身份为：`研究项目 × 医学监查业务模式 × 数据截止版本 × 执行基础`。
- `execution_basis=full`：基于选定数据截止版本，对该研究适用范围内的事实、风险、Profile、Timeline、中心/项目聚合和报告进行全量构建或重算。
- `execution_basis=incremental`：必须绑定一个既有、允许作为基线的 `baseline_run_id`，只处理新增、修改、撤回的数据以及由这些变化影响的规则、风险、受试者、中心、项目聚合和报告部分。
- “业务模式”与“执行基础”是独立维度：
  - 日常监查可以首次全量，之后增量；
  - 锁库前可以先做全量，再对 query 修订进行多轮增量；
  - 锁库后—CFDI 核查前通常先固定总量全量构建，若正式数据版本发生受控修订，再以明确基线做增量重算。
- 受试者、中心、风险域和专业 Agent 是 Run 内可独立重试、恢复、跳过或并行的 `work unit`，不是新的顶层 Run。
- 每个 Run 必须冻结 `project/study`、业务模式、`execution_basis`、数据截止时间、来源版本、知识包、映射、规则、graph 版本及基线身份。
- 哪个完成 Run 可以被提升为增量基线，留待下一项决策。

### D4：数据基线与医学决策基线分离；增量来自两次全量 listing 快照差异（用户选择 A 并补充，2026-08-09）

- 数据来源的实际形态是定期导出的全量 data listing，而不是只包含新增行的增量文件。
- 日常增量：比较“本次全量 listing 快照”和“上一次已接受的全量 listing 快照”，识别期间新录入、修改、撤回、重新出现和未变化记录。
- 锁库/时间锁定后的增量：比较锁定前或上一轮已接受全量快照与数据修改后的新全量快照，识别 query/修订导致的变化。
- `execution_basis=incremental` 表示计算与医学影响传播方式，不表示输入文件只包含增量。
- 每个全量快照必须不可变、内容寻址，并记录导出/截止时间、来源文件、结构画像、映射版本和完整性范围。
- 增量比较至少分三层：
  1. 记录级：新增、删除/缺失、重新出现；
  2. 字段级：旧值、新值、变化字段、空值变化；
  3. 临床语义级：时间关系、严重度、因果性、给药/处置、趋势、风险和报告影响。
- 来源、映射、标准事实和流程 QC 通过后，自动形成新的数据基线；不要求所有医学风险已关闭。
- 风险、处置、Query/PD 和报告签署属于独立的医学决策版本，未完成事项随下一 Run 结转。
- 新快照中缺少旧记录不能直接解释为事实删除或风险解除；必须先区分真实数据删除、导出范围变化、表结构变化和来源缺失。
- 正式报告或医学结论仍绑定当时的数据基线与医学决策快照，后续增量不得回写既往签署版本。

### D5：共用核心图并使用三种模式专属子图（用户选择 C，2026-08-09）

- 三种医学监查模式共用以下核心图：来源登记与验证、Study Knowledge Pack、全量快照与差异、字段映射、标准事实、规则/AI 风险发现、统一风险账本、Patient Profile、Subject Timeline 和独立 QC。
- 日常监查专属子图：新增/修改/撤回影响传播、风险变化分诊、少量待决事项、增量摘要和新数据基线提升。
- 锁库前专属子图：当前全量重算、query/修订多轮增量、未关闭风险、关键数据一致性和锁库阻断/关闭门。
- 锁库后—CFDI 核查前专属子图：固定总量、受试者/中心/项目三级汇总、全量报告、风险集中呈现和现场自查 checklist；仅受控数据修订可触发增量分支。
- 核心 artifact 在模式间共享引用，不复制成三套事实或风险权威；模式子图只生成各自的任务状态、验收结果和输出投影。
- 每个模式有独立完成判据，但必须引用同一版本化事实、风险身份和医学决策链。

### D6：资料冲突采用按问题类型划分的权威矩阵（用户选择 B，2026-08-09）

- 不建立一条跨所有资料类型的简单全局优先级。每类资料只对其职责范围内的主张具有权威性。
- 基础权威矩阵：
  - 研究要求、入排、访视、给药和方案程序：当前生效且已批准的研究方案及修订；
  - 已录入数据状态：当前已接受的全量 data listing 快照、来源元数据及其差异/审计；listing 证明“系统记录了什么”，不自动证明临床真实世界事实；
  - 药物安全、已知风险和参考安全信息：当前适用且已批准的 IB、RSI 和安全管理资料；
  - 项目执行与监查要求：已批准的监查计划、数据管理计划、统计/安全计划和正式项目决定；
  - CRO 医学监查报告：待核查的主张和总结，不作为原始事实权威；
  - 外部监管指南、文献和同类药物证据：解释、风险提示和建议依据，不自动覆盖项目批准文件。
- 矩阵按 `claim_type + effective_time + scope + approval_state` 解析，尤其要处理方案修订生效时间、版本适用人群和项目阶段。
- 冲突不静默裁决。系统创建版本化 `source_conflict` artifact，包含双方主张、来源定位、冲突类型、受影响节点、AI 的 3–5 个处理方案、推荐理由和不确定性。
- 只暂停依赖该冲突的节点；不相关的 Agent/子图继续运行。
- 用户裁决创建不可变 `source_resolution`，后续新来源或版本变化使原裁决进入重新确认状态，而不是覆盖历史。
- 项目可对权威矩阵增加经批准的局部覆盖，但不能改变 listing、CRO 报告或外部文献的基础证据性质。

### D7：七类 Agent 由 Graph Controller 条件调度（用户选择 B，2026-08-09）

- 每个 Monitoring Run 必经：
  - Agent ⑦ 的规划建议与代码 Graph Controller；
  - Agent ② 的当前全量快照处理，以及全量构建或与基线的差异计算；
  - Agent ④ 对适用风险域的整理与影响传播；
  - Agent ⑥ 对本次 Run 的独立 QC。
- Agent ① 每次执行轻量知识/控制点版本就绪检查；仅在方案、修订、IB/RSI、项目计划、外部证据、规则来源或知识包版本变化时深度重跑。
- Agent ③ 在全量 Run 中覆盖全部适用受试者；在增量 Run 中只重建受变更事实/风险/指标影响的受试者、Profile、Timeline、中心和上层投影。
- Agent ⑤ 仅在上传 CRO 医学监查报告、需要审阅既有报告或本次模式要求生成/复核报告时运行。
- Agent ④ 内部按 AE/MH、CM/IP、PD/Query/访视、疗效、安全/实验室、多表交叉和中心/项目聚合等受影响域分片，并可按受试者/中心并行。
- 条件调度由依赖和影响图决定，LLM 只能提出建议，不能跳过 graph policy 中的强制节点或 QC。
- 每个未运行节点必须产生 `skip_or_reuse_decision`：原因、依赖指纹、未变化证据、复用 artifact、适用范围和作出决定的 controller 版本。
- `skipped`、`reused`、`not_applicable`、`blocked` 和 `passed` 是不同状态，界面与审计中不得混用。
- 知识/规则变化可使看似未变化的数据重新进入风险计算；是否回溯按对应规则激活的 `evaluation_scope` 执行。

### D8：系统自动建立的低/中风险在后续快照不再命中时自动关闭（用户选择 B，2026-08-09）

- 适用对象仅为系统依据已批准规则/能力自动建立、且当前等级为低或中的风险。
- 下一次已接受的全量 listing 快照中该风险不再命中时，系统自动关闭，不要求逐条医学确认。
- 自动关闭前必须通过：
  - 本次全量快照技术可读、范围与完整性校验；
  - 旧记录与新记录的身份匹配或可信消失判断；
  - 排除导出范围变化、表结构变化、文件漏行和来源缺失；
  - 风险未被人工提升为高风险、未转入强制人工处置类型。
- 自动关闭创建追加式 `risk_transition`，记录旧/新证据、关闭原因、触发规则版本、数据快照、Run、时间和系统身份；不得删除原风险或覆盖历史。
- 风险后来重新命中时：若仍是同一临床事件/事实身份，则重开原 `risk_instance`；若是新的临床事件，则在同一 `risk_key` 下创建新实例。
- 高风险、SAE/AESI、人工确认或人工升级的风险，以及已进入强制人工处置链的风险，不因不再命中而自动关闭。
- 已签署报告只显示当时状态；后续自动关闭作为新状态进入当前看板和后续报告，不回写旧报告。

### D9：医学监查只生成结构化 Query 草稿；疑似 PD 通过 Query 核实（用户修订 A，2026-08-09）

- 医学监查系统不负责正式报送、分级、登记或关闭 PD。
- 系统可以：
  - 读取已存在的 PD listing/记录并与方案、给药、访视和其他数据核查一致性；
  - 识别潜在方案偏离线索；
  - 把潜在 PD 线索写入 Query 草稿，要求有权责任方核实是否构成 PD。
- 系统不得把“潜在 PD”自动转成正式 PD 结论；内部可使用 `potential_protocol_deviation` 标签路由 Query 和风险，但该标签不等于 PD 状态。
- Query 草稿采用中文原生的三分句结构：
  1. `basis`（依据）：方案条款、医学判断标准、数据逻辑或前后关系；
  2. `finding`（发现）：当前参与者/中心的具体事实、日期、数值、药物或矛盾；
  3. `action`（行动项）：请核实、说明、补充、更正或评估的明确问题。
- 展示文本可合并为一句或两句自然中文，但结构化存储必须保留三段，且每段可追溯到来源。
- 用户给定示例模式：
  - 医学合理性：`ALT轻度升高临床意义有限` + `目前参与者ALT仅轻度升高且相关记录为NCS` + `请核实AE判定理由是否充分`；最终文字必须依据实际字段和值生成，不得把 NCS 错当作数值阈值。
  - 疑似 PD：`研究方案规定xxx药为禁用药` + `参与者YYDD-YYDD服用a药且包含xxx成分` + `请核实是否为PD`。
- 每条 Query 草稿还应绑定：风险/事实身份、方案/数据来源位置、参与者、时间窗、问题类别、置信度、生成规则/模型和版本。
- Query 草稿可由系统自动生成并进入内部待办；用户可以编辑、合并、撤回或批准。向 EDC、CRO、中心或其他外部系统正式发送前必须由用户确认。

### D10：Query 回复与关闭不在工作台形成闭环（用户选择 B，2026-08-09）

- 医学监查工作台的 Query 职责止于：自动生成结构化草稿、内部审核/编辑/合并/撤回/批准，以及导出可供用户复制或录入外部系统的 Query 交付物。
- 工作台不直接发送 Query，不与 EDC、CRO 或研究中心双向同步，也不把“已导出”表述为“已发送”。
- Query 的回复接收、充分性评价、追问、正式状态和关闭继续由外部业务系统及其责任流程管理；工作台不建立虚假的 `sent/responded/resolved` 外部状态。
- Query 导出记录只保留内部可审计信息：草稿版本、批准版本、导出时间、导出人/系统身份、导出格式、关联风险/事实和来源版本。它不证明外部系统已接收或执行。
- 后续全量 listing 快照发生修订时，工作台仍依据新旧快照和风险规则重新评估事实与风险；不得把数据变化擅自归因为某条 Query 的回复或处置。
- D8 的低/中自动风险关闭继续只由下一次已接受全量快照及完整性/身份校验驱动，不依赖工作台不存在的 Query 回复状态。
- 若未来确需 Query 双向集成，应作为独立版本的外部系统集成能力重新设计、验证和授权，不预埋为当前完成条件。

### D11：默认入口采用中高风险全量优先的风险行动驾驶舱（用户选择并修订 A，2026-08-09）

- 一次 Monitoring Run 完成后，用户进入研究的默认入口是风险行动驾驶舱，不是研究统计总览或项目—中心—受试者目录。
- 首屏优先呈现全部高风险和中风险项，不设“仅显示 3–5 项”的硬上限；不得因为信息简洁而截断、抽样或隐藏仍需用户关注的中高风险。
- 高风险始终置顶；中风险按紧迫度、临床影响、是否新增/升级、证据确定性和影响受试者/中心范围排序。相同风险可按医学主题或中心形成可展开风险簇，但每条风险身份和证据仍可单独访问。
- 低风险默认以数量、趋势和主题摘要折叠展示，用户可一键展开、筛选和搜索；低风险不是删除或忽略。
- 驾驶舱同时显示 Run 完整性/QC、风险新增/升级/持续/下降/自动关闭变化、受试者/中心热点，以及每条中高风险的建议动作。
- 每条风险可直接下钻到项目—中心—受试者的相关层级，并进一步进入 Profile、Timeline、原始事实、来源定位和 Query 草稿；下钻后应保留返回时的筛选与排序上下文。
- 研究分析总览和层级对象目录仍作为一级可切换视图存在，但不是默认落点。
- Planning Agent 可以为真正需要用户决策的分叉提供 3–5 个建议选项；该“3–5 个选项”不适用于风险列表数量。

### D12：知识采用分层、版本化复用（用户选择 A，2026-08-09）

- 知识体系至少分为四层：
  1. 通用医学层：疾病自然史、适应症、诊疗路径、临床终点、共性安全与疗效判断方法；
  2. 药物/同类机制层：作用机制、剂量与暴露、预期疗效趋势、已知/潜在安全风险、相互作用及同类药物证据；
  3. 项目 `Study Knowledge Pack`：当前有效方案/修订、IB/RSI、监查/数据/统计/安全计划、访视/给药/禁限用药/终点/重点风险和正式项目裁决；
  4. 项目激活规则层：由系统或用户自然语言定义并经确认激活的项目特异规则、适用范围、例外和版本。
- 通用层和药物层可以跨项目复用；项目层和激活规则层按研究隔离。项目可引用上层知识，但经批准的项目文件在其权威范围内优先，不能被通用知识静默覆盖。
- 每条知识主张必须保留来源、定位、证据类型、适用人群/阶段、有效时间、版本、置信度和已知不确定性；推断与正式项目要求分开存储和展示。
- 每个 Monitoring Run 冻结四层知识的确切版本/内容哈希。后续更新不回写历史 Run，保证风险、Query、Profile、Timeline 和报告可重放。
- 发现新方案/IB/外部证据或知识更新时，系统先产生影响分析：受影响规则、风险域、受试者、中心、既往结论和推荐升级方式；用户确认后才建立新的知识包版本。
- 新版本默认用于后续 Run；是否回溯当前快照、全历史或仅未来，沿用 D2 的 `evaluation_scope` 决策与审计机制。
- 复用不能导致项目过拟合或跨项目污染：标准事实与规则接口保持项目无关，项目 adapter 只处理来源结构和获批项目特异内容；知识能力必须在不同适应症、药物和 listing 结构上验证。

### D13：产品主形态为本地单用户应用（用户选择 B；D20 进一步取消商业化目标，2026-08-09）

- 面向用户本人专业使用的主产品形态是安装在单台工作站上的本地单用户应用，而不是客户内网多用户服务器或中心化多租户 SaaS。
- 核心能力在本机可独立完成：项目资料登记、全量快照与差异计算、Graph Controller、风险账本、Profile/Timeline、看板、Query 草稿、审计、备份与恢复；不把中央服务可用性作为核心工作流前提。
- 产品可以采用本地后端加浏览器/桌面壳的实现，但必须封装为用户可理解的本地应用生命周期，不能要求用户手工管理开发服务器、端口、数据库进程或命令行。
- 项目数据、artifact、运行状态、知识包、规则、审计记录和导出物默认存放在明确的本地应用数据域，并具备项目级导入/导出、校验、备份、恢复和升级迁移能力。
- 首版不以多人协作、中心账号目录、租户隔离、共享任务锁或服务器并发为完成条件；正式的外部协作仍通过受控交付物完成。
- 单用户不等于无身份、无审计或可覆盖历史。系统仍需区分本地操作人、AI/系统 principal、自动与人工动作，并对批准、规则激活、基线提升、导出和正式报告保留追加式记录。
- 专业使用验收需覆盖安装、首次启动、升级、回滚/恢复、备份、项目迁移、故障重启和卸载后数据处置，而不只验证开发态 localhost 页面。
- 领域模型和存储边界应避免把单用户假设写死到医学事实和 artifact schema，以保留未来演进到私有化多用户部署的迁移路径，但不为未来形态提前堆叠当前无用复杂度。

### D14：AI 推理采用外部 AI 能力优先，但具体模型/API/harness 完全由用户配置（用户选择 C，并在 D18 补充修订，2026-08-09）

- 本地应用负责来源文件、不可变快照、标准事实、确定性规则、Graph Controller、检查点、风险/决策状态、审计、界面和导出；这些正式业务状态不托管在任何模型供应商的会话中。
- 资料解构、复杂医学推理、风险候选、知识分析、Profile/Timeline 叙事、Query 草稿和报告审阅等 AI 节点默认调用用户配置的外部 AI 能力；“外部”既可为直接模型 API，也可为用户已有的 Agent harness/CLI/native session。
- 产品提供统一 `AI Capability Adapter`，支持通过适配器接入用户自行配置的 API，或 Codex、Kimi Code、Grok Build、OMP、Hermes、Reasonix、CodeBuddy CLI 等 harness。列举这些工具表示适配目标，不表示未验证即可宣称兼容或成为内置依赖。
- 具体 provider、model、selector、reasoning/effort、凭据、命令、harness 会话方式、超时和可选 fallback 均由用户配置；产品不得替用户挑选模型、发明路由或静默更换未声明的执行工具。
- 每个节点只声明所需能力和结构化输出合同；Adapter 在启动前检查用户配置是否满足可用性、上下文、工具、格式和权限要求，并将实际执行配置冻结到 Run manifest。
- 用户未配置合格能力、配置不可用或所有用户声明的 fallback 失败时，节点进入 `blocked_model_unavailable` 并保留检查点；不得自行寻找其他模型或用未验收能力形成正式风险、Query 或报告结论。
- 断网或云端故障时，用户仍可查看既有项目、事实、风险、Profile/Timeline、审计和导出物，并运行不依赖 AI 的确定性功能；AI 必需节点可排队后恢复，不伪装为完整成功。
- 模型输出继续作为可追溯候选或受控自动化输入；正式事实、状态转换和医学门仍由 artifact schema、代码状态机、证据规则与已确认权限决定。
- API 密钥存放于本地受保护凭据存储；harness 凭据和 session 由其自身受支持机制管理，不复制到业务账本。实际 adapter、模型、版本、输入 artifact、输出、耗时、重试、成本和终止状态均可审计，但供应商/harness session 不作为业务恢复权威。

### D15：身份仅记录本机用户名，关键动作不重认证（用户选择 C，2026-08-09）

- 应用启动时读取当前操作系统账户名及本地设备/安装实例身份，作为 `human_local_user` 的显示与审计来源；不建立应用内账号密码体系。
- 日常动作及规则激活、风险确认、基线提升、Query/报告导出等关键动作均不要求再次输入密码或调用 Touch ID；使用清晰的影响摘要和单击确认完成。
- 单击确认仍须记录：本机用户名、设备/安装实例、时间、动作、目标 artifact/版本、变更前后状态、确认界面版本及可选备注；系统/Agent 自动动作使用不同 principal，不得冒充人工确认。
- 该机制只能证明“当前操作系统会话在该设备上执行了动作”，不能证明执行人完成了独立身份复核，也不能防止已解锁共享设备上的代操作。
- 因此当前产品不得把此类确认表述为受监管电子签名、身份再认证或 21 CFR Part 11 等价签署。若交付物需要正式签名，应在系统外按组织现行流程完成；工作台只保存导出版本和交付记录。
- 若未来客户要求合规电子签名、多用户角色或职责分离，必须作为独立能力增加身份生命周期、认证、签名含义、凭证管理和验证，不把当前单击确认直接升级命名。

### D16：采用可检测篡改的追加式业务审计账本（用户选择 A，2026-08-09）

- 审计分为两条不同生命周期：
  - 业务审计账本长期保存并随项目备份/迁移；
  - 技术调试与性能日志按容量和期限轮转，不承担医学事实或决策证明。
- 业务事件只追加，不原地编辑或删除。错误更正、撤回、重开和恢复均创建新事件，并引用被更正/替代的事件或 artifact。
- 每个业务事件至少包含：事件 ID、UTC/本地时间、principal、设备/安装实例、动作、项目/Run/Node、对象及前后版本/哈希、来源/知识/规则/模型/skill/prompt 版本、结果、原因、关联证据和上一审计事件哈希。
- 来源导入、快照接受、映射与事实变化、节点开始/完成/阻断/恢复、AI 调用清单、风险建立/升级/降级/关闭/重开、规则激活、人工确认、基线提升、Query/报告导出、备份恢复和迁移均进入业务账本。
- 使用项目级哈希链、Merkle/签名清单或等效机制，使删除、插入、改写和链断裂可被验证工具检测；备份、导出和恢复后必须重新验证完整性。
- 本地单用户可接触文件，因此该能力准确表述为 `tamper-evident`（篡改可检测），不承诺物理或管理员层面的绝对不可篡改。
- 模型审计优先保存完整输出 artifact、输入 artifact 引用、prompt/skill 模板版本及内容哈希；不得把密钥写入账本。大体积来源不重复复制到事件中，以可解析引用和内容哈希保持可追溯与存储效率。
- 审计链增强历史完整性，但不提升 D15 的身份强度，仍不能被宣传为电子签名。

### D17：单次权威运行在后台执行，展示真实精确进度，完成前不发布本次结果（用户选择并修订 B，2026-08-09）

- 每次 Monitoring Run 只执行一条正式全量或增量分析路径，不先生成抽样、低成本或低规则覆盖的快速风险预览。
- 工作流启动后默认在后台运行。用户无需停留在进度页，可继续查看上一已接受基线、其他项目页面和既有结果；随时返回查看本次 Run。
- 在执行前由 Planning Agent 与 Graph Controller 完成可执行清单展开，生成版本化 `execution_manifest`，列明阶段、节点、受试者/中心/风险域 work unit、依赖、复用/不适用项和强制 QC。
- 进度条基于该清单的真实状态计算，显示精确的 `已完成 / 总节点`、百分比、正在运行、等待、复用、跳过、不适用、阻断和失败数量；百分比表示节点完成比例，不伪装为精确剩余时间。
- 阶段和节点均可展开到具体 work unit，使总数与详情逐项对得上。若运行中确需新增节点，必须创建新的 manifest revision、说明原因并显式更新分母；不得静默跳变或用动画模拟进度。
- 进度区下方持续滚动显示当前正在进行的用户可理解工作，如“正在解析 AE 表”“正在核查受试者 0102 的 AE–CM 时间关系”“正在进行安全性风险 QC”，并显示节点、对象、状态、开始时间和耗时。
- 工作播报是结构化执行事件，不展示模型隐含推理、原始 chain-of-thought、密钥或无意义 token 日志；用户可展开查看来源与技术审计。
- 已完成节点可以显示完成状态和证据数量，但本次 Run 的风险、看板、Profile/Timeline 更新和正式导出仅在全部强制节点与最终 QC 通过后统一发布，避免用户把局部结果误认为完整结论。
- 阻断或需要用户决策时，后台任务保留检查点，并在全局任务入口和系统通知中显示具体阻断节点与所需动作；完成后提供本地通知和清晰的运行摘要。
- 应用窗口切换不影响运行；若应用进程或设备中断，已提交检查点用于下次启动后恢复，不能把中断任务标为成功。

### D18：默认医学质量优先；执行能力由用户自行配置（用户选择 A 并补充，2026-08-09）

- 所有适用于本次研究、监查模式和数据变化的风险域、受试者/中心 work unit、证据核查和强制 QC 必须完整执行；不得为了节省模型费用或缩短等待而跳过、抽样或延后应做的医学检查。
- 性能与成本优化只能使用不降低已验证医学覆盖和质量的手段：增量影响传播、已验证 artifact 复用、确定性缓存、批处理、受控并行、避免重复上下文和结构化压缩。
- 时间、调用次数、token/费用（若 adapter 可提供）和失败重试透明展示，但预算超限不会自动切换模型、削减风险域或发布不完整结果；应暂停并向用户说明。
- “质量优先”约束的是检查覆盖、能力验收、证据链和 QC，不意味着产品内置或替用户指定某个最昂贵模型。
- 用户自行配置直接 API 或 harness 能力，包括 Codex、Kimi Code、Grok Build、OMP、Hermes、Reasonix、CodeBuddy CLI 等；Graph Controller 仅按用户保存的执行映射调用相应能力。
- 每次 Run 冻结 `execution_profile_version` 和每个节点的实际 adapter/model/harness 记录，以便审计与重放；运行中改变配置需形成显式 revision，并只影响尚未开始或用户明确重跑的节点。

### D19：执行配置采用全局默认并允许按 Agent/能力和项目覆盖（用户选择 A，2026-08-09）

- 用户建立版本化 `ExecutionProfile`，其中包含已配置的 API/harness adapter、凭据引用、provider/model/selector/effort 或 harness 命令/session 方式、超时、并发和用户显式 fallback。
- 配置层级为：
  1. 全局默认 binding，覆盖普通 AI 节点；
  2. 按 Agent/能力类别覆盖，如资料解构、医学风险、Profile/Timeline、报告审阅和独立 QC；
  3. 项目级覆盖，用于特定研究的特殊模型、harness 或限制；
  4. Run 启动时生成只读 `effective_execution_profile` 快照。
- 常规用户只需配置一次全局默认；按能力和项目覆盖均为可选。启动 Run 时展示有效映射摘要，不要求逐 Agent 重复选择。
- 优先级仅解析用户保存的配置：项目覆盖 > 全局能力覆盖 > 全局默认。Graph Controller 和 Agent 无权自行改选 adapter、model 或 harness。
- fallback 必须由用户在对应 binding 中显式排序；每个候选均需通过该能力的连接、权限、上下文、结构化输出和质量资格预检。
- 凭据以本地安全引用保存，不随不含凭据的 profile 导出；项目迁移时导出配置结构和需求，但目标设备需重新绑定凭据并预检。
- Run 开始后冻结 profile 版本与解析结果。配置修改默认只作用于后续 Run；当前 Run 如需切换，必须由用户创建 execution revision，并记录受影响且尚未开始/需重跑的节点。
- 进度、审计和结果必须显示实际执行的 adapter/model/harness，而不是只显示抽象 Agent 名称。

### D20：不以商业化为目标；既有项目交付物作为基座并引入多模型风险分析（用户修订 B，2026-08-09）

- 当前目标调整为供用户本人/内部专业工作使用的高质量本地医学监查系统，不再要求达到对外商业化销售、监管电子签名、商业验证 dossier 或多用户企业部署标准。
- MG-K10、芦可替尼 AD 等项目已有的 Patient Profile、Subject Timeline、风险清单、AE/MH 漏报、checklist 和监查报告作为 `reference_baseline`，用于迁移保真、回归对照、已知风险召回和界面/输出比较。
- 既有交付物不是不可质疑的绝对金标准：它们可能存在遗漏、历史判断偏差、版本差异或只覆盖部分风险域。系统不得为了“匹配基座”压制有来源证据的新发现。
- 多模型风险分析对同一项目来源独立形成可追溯候选，结果至少分为：
  - 与基座一致的已知发现；
  - 基座未包含但有充分来源证据的新增发现；
  - 与基座冲突或模型间不一致、需要进一步核查的发现；
  - 经反证支持应排除的疑似误报。
- 每条结果保留模型/harness、执行配置、来源事实、规则/知识版本、风险分级、置信度、支持与反对证据；多模型一致性是信号，不等于医学真值。
- 对没有成熟 Profile/Timeline/风险成品的 MY008/MY009 等项目，以原始方案、IB、listing 和项目资料为来源基座，由多模型机制建立初始风险参考集，而不是伪造既有标准答案。
- 完成门改为：真实项目来源可追溯、既有能力无损迁移、多模型分析可解释、关键风险不因架构重构丢失、专业用户可高效使用、系统可恢复和审计；不再生成或声称商业化认证结论。

### D21：多模型风险分析采用同题、隔离上下文、独立并行后汇总（用户选择 A，2026-08-09）

- 对同一风险分析包，同时分发给两个或多个由用户 ExecutionProfile 配置的模型/API/harness；每个执行者使用独立上下文，不读取其他模型的候选、理由、置信度或中间过程。
- 各模型接收相同版本的标准事实、来源定位、Study Knowledge Pack、规则、适用风险域和结构化输出合同；输入包及内容哈希冻结，避免因输入不一致把差异误判为模型分歧。
- 每个模型独立输出风险候选，至少包括：风险类型、项目/中心/受试者、事实身份、时间窗、等级建议、支持证据、反证、临床理由、Query 建议、置信度和未决问题。
- 汇总前不允许某模型以 reviewer 身份修改另一个模型的原始输出。原始候选作为不可变 artifact 保留，归并器只创建新的关系和汇总结论。
- 结果通过 canonical `risk_key / risk_instance`、事实身份、时间窗和语义相似度去重聚类，形成：多模型共同发现、单模型独有发现、分级/理由冲突、相互否定和共同未发现但基座已有等类别。
- 多数同意或全体一致只形成 `agreement_signal`，不能自动等同于医学真值；单模型发现也不能因缺少多数支持而丢弃，只能进入证据核查和后续裁决。
- 独立并行是风险分析的基础形态；领域专长仍可通过 Agent/能力 binding 指定，但不能用完全不重叠的分工替代对关键风险包的独立交叉分析。
- 每个模型任务均是 execution manifest 中可见的 work unit，分别显示进度、实际 adapter/harness、完成状态和证据数量；汇总节点只在声明的独立任务完成或明确阻断后运行。

### D22：所有独立模型从既有 reference baseline 出发进行审阅（用户选择 B，2026-08-09）

- 对存在既有 Profile、Timeline、风险清单、漏报、checklist 或报告的项目，所有独立模型在初次风险分析时均可读取同一冻结版本的 `reference_baseline`，不设置盲审发现组。
- 基座与原始方案、IB、listing、知识包和规则一同作为输入；模型不能只摘要或复述基座，必须回到原始来源逐条核验。
- 每个基座条目要求输出独立处置：`confirmed`（证据支持）、`partially_supported`（部分支持/需修订）、`unsupported`（当前来源不支持）、`outdated`（与当前版本不一致）、`insufficient_evidence`（证据不足）或 `not_applicable`。
- 每个风险域还必须执行 `baseline_gap_search`，主动检查基座未覆盖的受试者、中心、表、时间窗和风险类型，并输出有来源证据的新增候选；不得因“基座没有”就降低或丢弃。
- 若基座与当前来源快照、方案/IB 版本不匹配，应先形成 `baseline_version_conflict`，把版本差异与医学分歧区分开来。
- 不同模型虽然都看到基座，但仍使用隔离上下文，不能看到其他模型如何评价基座；其核验、补充和反证结果分别保留。
- 对没有衍生交付物的项目，以冻结的原始项目资料清单作为 `source_reference_baseline`；所有模型从同一来源清单独立建立初始候选，不伪造不存在的历史风险答案。
- 该选择接受基座锚定风险；缓解措施是强制来源逐条定位、基座条目反证、gap search、模型独立性和后续分歧裁决，而不是声称消除了锚定。

### D23：模型分歧采用确定性核对、独立裁决、用户处置三级机制（用户选择 A，2026-08-09）

- 第一级为代码/规则驱动的 `evidence_verifier`：核对项目/批次/受试者/中心身份、来源定位、版本、日期、单位、记录匹配、规则条件和 artifact 完整性，先消除重复、错配、过期基座和可确定的事实错误。
- 第二级为用户 ExecutionProfile 中单独配置的 `adjudication_binding`。裁决执行者使用新的隔离上下文，只接收原始模型 artifacts、reference baseline、来源证据、反证、规则/知识版本和裁决 schema，不接收某个 worker 的隐含推理。
- 裁决节点不得修改原始模型输出，只能创建追加式 `adjudication_record`，把每个聚类标记为：
  - `merged_supported`：可合并且来源支持；
  - `distinct_supported`：应保留为不同风险；
  - `rejected_by_evidence`：被明确反证排除；
  - `version_mismatch`：由基座/来源版本差异造成；
  - `needs_user_attention`：仍有医学分歧、证据不足或高风险影响，需要在看板中重点呈现。
- 裁决必须逐项说明采用/不采用的来源、冲突点、分级理由和剩余不确定性；模型数量与多数意见只能作为辅助信号。
- 清晰的重复、身份错配、版本差异和来源反证可由前两级解决。符合 D1 自动化条件的低/中风险可继续进入受控自动状态；高风险、重要医学结论、低置信度或裁决后仍冲突的中高风险在看板中重点呈现。
- 高风险候选无论模型是否一致、裁决是否支持，都不能仅由裁决模型自动关闭或从风险驾驶舱中消失。
- 裁决节点不可用时保留全部原始结果并阻断发布，不自动退化为多数票，也不让任一生产模型兼任裁决者。
- 确定性核对、裁决调用、裁决记录和用户实际发生的确认/导出动作均进入 execution manifest、进度与追加式审计。

### D24：曾选择异常处置队列，但由 D25 修订为看板优先、无强制待办（用户选择 A 后补充修订，2026-08-09）

- D24 初步选择了 exception-only review，以减少逐条复核噪声。
- 用户随后明确：医学监查子系统主要是用于查看风险、查阅项目/中心/个例信息和定位数据源头的看板，不应围绕待办、清空队列或任务交互设计。
- 因此不建设独立的“异常处置队列”作为主工作面；其中有价值的并排证据、模型分歧、基座对照、Query 草稿和来源下钻能力保留在风险详情/证据 inspector 中。
- 高风险、未解决中风险、低置信度和冲突项通过排序、颜色、标识、筛选和摘要突出，而不是转化为必须点击完成的任务。

### D25：AI 与 QC 完成后直接发布看板；分析状态与可选人工决定内部区分，但不显示“人工复核未完成”（用户选择并修订 A，2026-08-09）

- 所有强制 Agent、确定性核查、独立裁决和最终 QC 通过后，Run 进入 `analysis_complete`，本次风险、看板、Profile 和 Timeline 直接成为可查看的新版本。
- 界面不显示“人工复核未完成”横幅，不要求用户清空待办，也不以 `review_complete` 作为查看本次结果的门槛。
- 系统内部仍区分：AI/裁决分析状态、风险证据状态，以及用户实际发生的确认、备注、Query 批准或导出等 `user_decision`；不存在用户动作时保持“未发生人工决定”，而不是生成一个全局未完成任务。
- 用户主要行为是浏览、搜索、筛选和下钻：从项目风险到中心、受试者、Profile、Timeline、标准事实、原始 listing 行、方案/IB 条款和模型/裁决证据。
- 高风险、模型/基座冲突、证据不足和低置信度在看板中以醒目但非任务化的状态呈现；可按这些状态筛选，不能隐藏或要求用户逐条点选才能继续。
- 用户主动修改风险、添加备注、激活规则、批准/编辑 Query 或导出特定结果时，才创建相应交互与追加式审计；这些动作不构成日常浏览的强制流程。
- Query 向外部系统使用前仍需用户主动批准/导出，正式报告若需要人工确认也在导出动作处完成；这不转化为全局待办中心。
- 该设计保留“分析事实”和“人工决定”的权威分离，但产品表面是信息看板和证据导航器，而不是工作流工单系统。

### D26：风险详情采用分栏证据 Inspector，并深链到完整 Profile/Timeline（用户选择并补充 A，2026-08-09）

- 桌面端风险驾驶舱采用主从分栏：左侧保留当前风险列表/风险簇及筛选排序，右侧为所选风险的 evidence inspector；切换相邻风险无需离开看板。
- Inspector 至少展示：风险摘要与等级、基座条目、各独立模型候选、裁决、支持/反对证据、标准事实、原始 listing 定位、方案/IB/知识条款、关联 Query 草稿和变更历史。
- Inspector 内的受试者、Profile 和 Timeline 入口必须是可复制/可恢复的深链接，绑定 `project_id + run_id + snapshot_id + site_id + subject_id + risk_instance_id + view + anchor + return_context`。
- 点击 Profile/Timeline 后进入该受试者在同一 Run/快照下的完整原始 Profile 或完整原始 Timeline 视图，不是为风险详情另造的裁剪副本；相关事件、日期或指标可高亮并自动滚动定位，但完整上下文保持可浏览。
- “原始 Profile/Timeline”指本系统为该 Run 生成并保存的完整受试者级 artifact 和 audience-facing 视图；其中的每个事实仍可继续下钻到原始 listing 行/单元格和方案/IB 条款。
- 跳转前保存风险列表筛选、排序、分组、滚动位置、选中风险和 Inspector 展开状态；返回时精确恢复，避免用户重新寻找原风险。
- 跳转和返回必须验证项目、Run、快照、中心、受试者与风险身份。任何身份不一致或目标 artifact 缺失都 fail-closed，并提供可理解的修复路径，不能展示相邻受试者数据。
- Inspector 可折叠/调整宽度；大屏优先并排阅读，窄屏可退化为全屏详情，但导航和 return context 合同保持不变。
- Profile、Timeline 和风险 Inspector 共用同一 canonical facts/risk authority，只做不同投影，不复制成三套可漂移数据。

### D27：Profile 与 Timeline 进入统一 Subject Workspace，并共享受试者时间骨架（用户选择并补充 A，2026-08-09）

- 受试者级采用统一 `Subject Workspace`，共用项目/Run/快照、中心、受试者身份、治疗组/阶段、风险摘要和返回上下文；`Patient Profile` 与 `Subject Timeline` 为两个一级页签，各自保留完整视图和适合自身任务的信息结构。
- 两个页签不复制时间逻辑，而是共享 canonical `Subject Temporal Spine`，至少包含：实际日期/时间、研究日、名义访视、实际访视发生、计划/非计划访视、筛选/基线/治疗/随访阶段、首次/末次给药和关键数据截止点。
- 每个事件/观察通过稳定 `subject_timepoint_id` 或时间区间绑定到该骨架；Profile 的实验室、生命体征、疗效、给药和风险趋势，以及 Timeline 的 AE/MH/CM/IP/PD/访视事件均使用同一坐标换算和 visit identity。
- 共享轴不意味着强行把所有事件归入访视。AE 起止、合并用药、非计划检查、住院和部分日期事件仍按真实/不确定时间定位；名义访视作为覆盖层或锚点，不能替代实际日期。
- 两页共享时间导航器：当前时间窗、缩放、访视/研究日/日期切换、治疗阶段背景带和选中锚点。Profile 中选择某次访视/异常点，Timeline 同步高亮相同时间窗与相关事件；Timeline 选择事件，Profile 同步定位相关指标和摘要。
- 深链接可直接指定 `view=profile|timeline`、时间轴模式、访视/日期/事件 anchor 和缩放范围；切换页签保留时间窗、受试者和高亮上下文。
- Profile 仍以分领域医学摘要、趋势图和结构化表格为主；Timeline 仍以历时事件关系、持续时间、重叠与序列为主。共享时间骨架提升一致性，不把两者压缩成一个过载页面。
- 部分日期、冲突日期和访视归属不确定性必须显式展示，并在两个页签保持相同语义；不能在 Profile 与 Timeline 分别推断出不同时间。

### D28：Subject Temporal Spine 默认以实际日期为主轴（用户选择 A，2026-08-09）

- Profile 与 Timeline 默认使用连续实际日期/时间横轴；名义访视、实际访视、筛选/治疗/随访阶段、首次/末次给药和数据截止点作为同轴标记、背景带或覆盖层。
- 实际日期来自 canonical fact 的原始/标准化日期证据；不得用名义访视日期替换缺失实际日期，也不得为视觉整齐把访视间事件吸附到最近访视。
- 名义访视与实际发生日期同时存在时，显示计划—实际偏移；非计划访视使用不同但克制的标识，仍落在真实日期位置。
- 时间导航器支持一键切换 `calendar_date` 与 `study_day`。研究日的锚点和计算规则由项目知识包定义，通常以首次给药或方案指定 Day 1 为零点；未给药/锚点缺失时不得伪造研究日。
- 切换轴模式只改变坐标投影，不改变事件身份、排序、来源或风险结论；当前时间窗、选中事件和关联指标在两种模式间保持对应。
- 长随访使用缩放、brush/minimap、预设时间窗和“跳到异常/访视/给药”导航，不能通过不透明的断轴隐藏空白期或改变事件距离。
- 部分日期显示为不确定时间区间/精度带，冲突日期显示冲突标记；在 Profile 与 Timeline 中使用同一位置与视觉语义。
- 深链接保存轴模式、起止范围和 anchor；从风险 Inspector 进入时默认仍为实际日期轴，并自动定位相关事实。
- 跨受试者/中心比较可按分析目的切换研究日或访视对齐，但这不改变单受试者页面默认实际日期轴。

### D29：中心级默认入口为中心风险图谱（用户选择 A，2026-08-09）

- 进入某中心后，默认先展示该中心的风险图谱，而不是纯统计首页或单纯受试者目录；全部高风险和中风险可见，低风险默认聚合可展开。
- 首屏由以下联动区域组成：风险等级/领域热图、当前与前次 Run 的风险变化、重复/系统性风险簇、热点受试者、关键数据完整性信号，以及中心相对项目总体的对照摘要。
- 风险领域至少覆盖 AE/MH、CM/IP、方案/访视/Query、疗效、安全/实验室、多表交叉和数据质量；项目不适用域明确显示 `not_applicable`，不能与零风险混淆。
- 单个受试者偶发风险与多个受试者重复出现的中心模式分开呈现。系统性风险簇显示涉及人数、占中心受试者比例、时间范围、共同来源/流程特征及模型/规则证据。
- 点击热图单元或风险簇，进入保留中心过滤的风险列表和分栏 Inspector；点击热点受试者，进入完整 Subject Workspace，并可从 Profile/Timeline 返回同一中心上下文。
- 中心受试者目录和统计总览仍在同页一级可切换视图中，提供受试者数、暴露、访视、数据完整性和各风险域数量/比例，但不抢占默认风险入口。
- 中心与项目对照必须同时展示原始数量、适当分母/暴露调整指标和数据覆盖情况；小样本、随访长度差异、缺失/导出范围变化必须提示，不能简单按风险数量给中心贴高低质量标签。
- 颜色用于医学风险等级与变化，不用于把中心做惩罚性排行榜；中心排序依据可见、可切换、可解释。
- 中心图谱、项目图谱、风险 Inspector 和 Subject Workspace 共用相同 risk/fact/site/subject identities，所有下钻可定位到原始数据来源。

### D30：中心对照同时展示绝对数量与分母/暴露调整指标（用户选择 A，2026-08-09）

- 每项中心风险指标同时显示至少两类值：实际受影响受试者数/事件数，以及按明确、临床合理分母计算的比例或率；不得仅以其中一种替代另一种。
- 分母按指标语义确定并明示：受试者层风险通常使用可评估受试者数；访视/程序风险可使用应发生访视或程序数；事件/暴露风险仅在合理时使用人时、治疗暴露期或给药机会数。
- 同一指标必须说明分子定义、分母定义、数据截止、排除规则、单位和计算版本；分母为零、未知或覆盖不足时显示 `not_evaluable`，不能显示 0%。
- 小样本中心、短随访、不同暴露长度、不同招募阶段和缺失/导出范围变化显示明显提示；可显示区间估计或不稳定标识，但不制造虚假精度。
- 默认表格/图形同时提供“受影响人数”“事件数”“比例/率”“数据覆盖”列；用户可按任一列排序，并能看见当前排序依据。
- 点击任一数量或比率可展开其完整分子与分母集合，定位到对应中心、受试者、事件、访视和来源记录；聚合值必须可解释重建。
- 不生成无法分解的综合中心风险分数。若未来需要综合指数，必须展示组成、权重、适用性和敏感性，并作为独立设计决策。
- 项目级中心比较使用同一指标合同，保证中心页和项目页的数字一致；缓存/增量更新不得产生两个口径。

### D31：项目级驾驶舱默认“变化优先＋当前全量”（用户选择 A，2026-08-09）

- 项目级风险驾驶舱首层回答“本次相对所选基线发生了什么”，显示新增、升级、持续、降级、自动/证据关闭、重开和不再可评估的风险数量、领域、中心与受试者分布。
- 同一页面始终保留当前全部高风险和中风险清单/风险簇/热点；低风险默认聚合可展开。不能因默认突出增量而隐藏长期持续但仍重要的存量风险。
- 每条风险变化绑定 `from_run/baseline_snapshot → to_run/current_snapshot`、旧/新风险状态、旧/新证据和变化原因。
- 变化原因至少区分：
  - 新录入/修订/撤回的 listing 数据；
  - 方案、IB、知识包或规则版本变化；
  - mapping/canonical fact 修订；
  - 多模型/裁决执行配置或结果变化；
  - 用户主动决定；
  - 来源范围/完整性变化导致不可比较。
- 临床/数据变化与分析管线变化分开展示，不能把模型、prompt 或规则改变造成的风险差异描述为受试者状况变化。
- 风险变化摘要、中心热图、受试者热点和当前全量列表联动；点击任一变化类别可过滤到风险 Inspector，并继续下钻中心和 Subject Workspace。
- 当前全量可按风险域、等级、中心、受试者、基座/模型一致性、来源和状态筛选；默认中高风险全量顺序仍遵循 D11。
- 第一次全量 Run 无可用基线时显示“初始全量”，不伪造新增/解除；后续可选择其他兼容 Run 做历史对照，但不是日常默认入口。
- 已解除/关闭风险只出现在变化摘要与历史轨迹中，不冒充当前开放风险；重开风险同时显示此前关闭原因与本次新证据。
- 项目、中心和受试者页面使用同一风险变化合同，保证上下钻取的新增/持续/解除口径一致。

### D32：分析执行者数量不设最低值（用户选择 C，2026-08-09）

- 系统支持一个或多个由用户 ExecutionProfile 配置的独立风险分析执行者，但不把“至少两个模型”设为 Run 启动、完成或看板发布的硬门。
- Graph Controller 按各风险域实际解析出的 `analysis_bindings` 数量创建 work units；一个执行者和多个执行者都可以完成相同的风险域覆盖、来源证据、结构化候选和最终 QC。
- `ensemble_size=1` 时不生成 `agreement_signal`、多数/少数、模型分歧率或“多模型共识”等表述；只展示该次实际分析来源、证据和裁决/基座关系。
- `ensemble_size>=2` 时才执行 D21 的同题独立并行、模型间聚类、一致性与分歧分析；原始结果继续各自保留。
- 模型数量不直接等同于证据质量或风险置信度。无论数量多少，每条结论仍按来源直接性、规则/知识适用性、反证和 QC 评价。
- 用户可以按全局、能力或项目配置不同数量；有效数量和实际 adapter/harness 在 Run manifest、进度详情和审计中准确记录，但不在主看板显示为“配置不足”待办。
- 质量优先仍要求所有适用风险域和强制 QC 完整执行；“不设模型数量下限”不能被解释为允许跳过医学域。
- D23 的独立裁决只在存在模型间、模型—基座或模型—证据冲突且达到裁决条件时运行；分析执行者数量本身不触发或免除裁决。
- 若用户未配置任何可用分析能力，则相关 AI 风险域仍因没有执行者而阻断；`零个执行者` 不属于本决策允许的完成状态。

### D33：外部医学监查报告采用主张—来源逐条核查（用户选择 A，2026-08-09）

- Agent ⑤ 仅在用户上传 CRO/外部医学监查报告或明确需要审阅报告时启动；原报告按文件哈希、版本、日期、作者/来源、声称的数据截止和适用项目冻结为不可变 `external_report_source`。
- 外部报告只提供待验证主张，不成为事实、风险或医学结论权威。系统先抽取报告结构和原子主张，包括对象、时间窗、分母、数值、趋势、风险、等级、因果性、中心/受试者、建议与结论。
- 每条主张建立 `report_claim`，逐项链接并核对：方案/修订、IB/RSI、当前/相关 listing 快照、canonical facts、风险账本、Profile/Timeline、中心/项目指标、reference baseline 和前次报告。
- 主张核查状态至少包括：`supported`、`partially_supported`、`unsupported`、`outdated_or_wrong_cutoff`、`overstated`、`understated`、`internally_inconsistent`、`not_evaluable`。
- 报告遗漏检查从系统当前风险和变化反向出发，识别应在报告范围内但未覆盖的高/中风险、关键个例/中心模式、疗效/安全趋势、数据局限和前次未解决事项；同时区分真正遗漏与报告范围外事项。
- 对前后报告比较时，区分数据更新、风险真实变化、报告表述变化和分析方法/版本变化；不得仅按文字差异判断医学结论改变。
- 每个问题输出：报告原文定位、问题类型、系统事实/风险、支持与反对证据、影响等级、建议修改方向和可直接使用的中文修订建议；不得只给笼统“建议核实”。
- 报告中系统未识别的新风险作为候选进入相同 evidence verifier/风险分析链，不能因来自 CRO 报告就自动采用或自动拒绝。
- 报告审阅结果以看板/矩阵方式查看，可从主张直接下钻受试者 Profile/Timeline、中心图谱、风险 Inspector 和原始 listing；不建设必须逐条完成的审阅待办。
- Agent ⑤ 可以使用用户配置的一个或多个分析执行者；多模型数量语义遵循 D32，冲突处理遵循 D23，最终 QC 独立于报告分析执行者。
- 报告审阅不原地改写上传原件，也不直接改变风险状态。

### D34：报告审阅默认生成问题矩阵、带批注副本和可选清洁修订稿（用户选择 A，2026-08-09）

- `report_review_matrix` 是报告审阅的结构化权威产物。每个 `review_issue_id` 绑定报告/claim 定位、问题类型、风险/事实、正反证据、影响、建议和状态。
- 上传的 CRO/外部报告原件始终不可变；任何批注或修订都生成内容寻址的派生版本，绑定原件哈希、审阅 Run、数据截止、知识/规则/模型版本和生成时间。
- 带批注副本尽量保留原报告版式、页码、表格和文字，仅以评论、批注锚点或等效标记关联 `review_issue_id`；不在用户不知情时直接改正文。
- 对无法可靠写入原格式批注的输入（如扫描 PDF 或受限格式），生成视觉定位清楚的批注副本/旁注报告，并保留页码、段落、表格/单元格或图形定位；不能伪称已在原件内批注。
- 清洁修订稿为可选派生产物，只在用户主动选择时生成；它把已确定的修订建议整合为连续、中文原生的报告草稿，但保持 `DRAFT` 身份，不冒充 CRO 已接受版本或人工签署版本。
- 清洁修订稿不能静默解决 `not_evaluable`、来源冲突或高风险医学分歧；这些位置保留明确占位/说明或采用经裁决的安全表述。
- 问题矩阵、批注副本和清洁修订稿共享同一 issue IDs、来源引用和版本；在看板点击问题可打开报告定位，也可下钻风险、中心、Subject Workspace 和原始 listing。
- 用户重新上传修订后的报告时创建新 `external_report_source`，系统比较哪些 issue 已解决、部分解决、未解决或引入新问题；不覆盖上一轮矩阵和派生文件。
- 导出前运行格式/内容/身份 QC，核对项目、报告版本、数据截止、issue 数、批注锚点、引用和派生文件哈希；失败不得显示为完整交付。
- 三件套的生成、下载/导出和后续版本比较进入追加式审计；原文件、批注副本和清洁稿在 UI 中有不可混淆的标签。

### D35：三种监查模式采用模式化组合输出（用户选择 A，2026-08-09）

- 三种模式始终生成同一权威看板体系：项目风险变化＋当前全量、中心风险图谱、Subject Workspace、风险 Inspector、来源与审计；模式只决定默认摘要、报告和 checklist 组合，不复制事实/风险。
- 日常医学监查默认输出：
  - 当前全量快照相对数据基线的增量变化摘要；
  - 新增/升级/持续/降级/关闭/重开风险及影响受试者/中心；
  - 当前完整中高风险看板；
  - 新生成或受变化影响的结构化 Query 草稿；
  - 数据/知识/规则/模型变化对结论的影响说明。
- 日常模式不机械生成冗长全量报告；用户仍可从当前看板按需导出选定风险、受试者、中心或项目摘要。
- 锁库前医学监查默认输出：
  - 当前全量风险与关键数据一致性；
  - 已发生多轮 Query/数据修订的前后影响；
  - 高/中风险、未有充分数据支持的关键项和锁库前核查点；
  - Query 草稿/修订包、受影响个例/中心清单和锁库检查包；
  - 每轮修订均引用相应全量 listing 快照和基线。
- 锁库后—CFDI 核查前默认输出：
  - 绑定固定数据总量/受控修订版本的全量项目医学监查报告；
  - 每个中心风险汇总与中心级数据导航；
  - 受试者级风险摘要、完整 Profile/Timeline 入口和可按需导出的个例材料；
  - 项目/中心/受试者风险 checklist 与现场自查材料；
  - 数据截止、来源覆盖、未评估项和版本身份说明。
- 模式输出均由 canonical facts/risk/decision artifacts 投影生成；相同数字、风险状态和来源在看板、摘要、报告、Query 与 checklist 中必须一致。
- Agent ⑤ 在需要生成/审阅报告的模式下按条件运行；外部报告审阅三件套与系统自产监查报告是不同 artifact 类型，UI 与导出不得混淆。
- 所有输出默认中文原生、重点优先、可追溯，保留项目/Run/快照/知识/规则/执行配置和生成版本；无用户主动动作不对外发送。
- 用户可在任一模式按需生成其他模式的某种派生材料，但不得因此改变该 Run 的业务模式身份或完成判据。

### D36：AE/MH 漏报纳入统一风险、Profile、Timeline 与三级聚合（用户新增硬需求，2026-08-09）

- 既有 AE/MH 漏报能力不再作为外部旁路页面或独立工具交付，而是 Agent ④ 的核心 `AE/MH under-reporting` 风险子图，并进入统一 risk/fact/evidence 状态机。
- 系统区分至少四类对象：
  - listing 中已记录的 AE；
  - listing 中已记录的 MH；
  - `potential_unreported_ae` 风险候选；
  - `potential_unreported_mh` 风险候选。
- 漏报候选不是正式 AE/MH 事实。模型、规则、Profile、Timeline、统计和导出均不得把候选计入“已报告 AE/MH”数量；只有后续 listing 新增相应记录并完成身份匹配后，才建立“候选—正式记录”关系。
- 候选证据可来自症状/诊断、实验室/检查异常、住院/急诊、手术/操作、合并用药适应证、停药/减量/处理、死亡/严重事件线索、访视叙述、既往疾病时间关系及跨表矛盾；每条证据必须定位到来源记录。
- AE 与 MH 的候选分类依据事件相对研究起点/知情同意/筛选/首次给药的时间、既往存在性、恶化/新发、方案定义和项目规则；无法可靠区分时标记 `ae_mh_classification_uncertain`，不强行归类。
- 每条漏报候选绑定受试者、中心、时间窗、触发信号、支持/反对证据、严重性/临床影响、模型/规则版本和置信度，并进入与其他风险一致的新增、持续、关闭、重开和来源变更生命周期。
- 当后续全量 listing 补录匹配 AE/MH、证据被明确反证或来源范围修复后，低/中候选可按 D8 规则自动关闭；关闭事件保留旧/新证据和匹配身份。高风险或严重事件线索不能仅因一条表记录消失而自动关闭。
- 漏报候选自动生成 D9 三段式 Query 草稿：依据＋发现＋行动项，例如请核实相关症状/处理是否需补充 AE 或 MH；不得直接宣称已构成未报告 AE/MH。
- 项目级显示漏报风险当前全量、相对基线变化、涉及中心/受试者和主要触发来源；中心级识别重复漏报模式并同时显示绝对量、分母和数据覆盖；所有聚合可下钻单个候选。
- 受试者层必须能够从漏报风险打开 Profile/Timeline 和原始来源。Profile 负责展示候选的医学解释、关联指标/用药/检查及是否已有相应 AE/MH；Timeline 负责把候选放在真实日期轴上，与已记录 AE/MH、CM/IP、访视和处置的时间关系对照。
- 视觉上必须区分“已记录事实”和“潜在漏报候选”，例如实线/实心与虚线/描边、事实色与候选警示色，并提供清晰图例；候选不能用与正式 AE/MH 相同的事件样式。
- 既有 MG-K10 等漏报结果作为 reference baseline 进入 D20/D22 的基座核验；多模型数量、独立分析、基座对照、裁决和 QC 分别遵循 D21-D23、D32。
- 风险 Inspector 与原始来源深链均为强制能力。

### D37：AE/MH 漏报候选在 Profile 与 Timeline 同时默认呈现（用户选择 A，2026-08-09）

- 同一个漏报候选使用唯一 `risk_instance_id/candidate_id`，在 Profile、Timeline、风险 Inspector、中心和项目聚合中只引用、不复制；统计、状态和审计均只计算一次。
- Profile 增加“潜在 AE/MH 漏报”医学解释区，并在相关实验室、检查、CM、IP 处置、住院/操作和风险摘要旁显示轻量关联标记；每项说明触发线索、已记录 AE/MH 对照、正反证据、分类不确定性和 Query 草稿。
- Timeline 增加可开关的“潜在漏报候选”覆盖层/泳道，按 D28 实际日期轴展示候选时间点或不确定区间，并与正式 AE/MH、CM/IP、访视、检查、住院和处置关系并列。
- 已记录 AE/MH 使用事实样式，漏报候选使用虚线/描边/候选图标与清晰图例；颜色同时受风险等级约束，但不能仅依赖颜色区分事实与候选。
- 在 Profile 选择候选时，Timeline 同步定位并高亮其时间窗与关联事件；在 Timeline 选择候选时，Profile 同步打开对应解释区和相关指标。两个页签切换保持选中候选和时间范围。
- 候选详情显示“当前 listing 中未找到匹配 AE/MH 记录”或已匹配状态，并提供到 AE/MH 表、触发来源行、风险 Inspector 和 Query 草稿的链接；不得只展示模型摘要。
- 当后续快照补录匹配 AE/MH 时，事实事件以正式样式进入 Profile/Timeline，原候选显示为已解决历史并链接新记录；不能删除原候选或把候选原始时间静默改成补录日期。
- 高/中候选默认可见，低风险候选可在 Profile 摘要折叠、Timeline 覆盖层筛选中控制，但始终可检索；严重事件线索无论置信度都不得因折叠默认而不可发现。
- Profile 与 Timeline 对候选的名称、等级、状态、日期精度和来源计数必须一致；任何投影不一致由 QC 阻断本次 Subject Workspace 发布。

### D38：专业使用完成验收覆盖全部五个真实项目（用户选择 A，2026-08-09）

- 最终专业使用完成门同时覆盖以下五个真实项目，而不是只在一个主项目或三个代表性项目上通过：
  1. MG-K10-SAR；
  2. 芦可替尼 AD；
  3. MY008-3-02；
  4. MY008-3-01；
  5. MY009-UC-2-01。
- 每个项目至少完成一次真实全量 Run：来源/版本、Study Knowledge Pack、listing 结构与 mapping、canonical facts、适用风险域、AE/MH 漏报、项目/中心/受试者看板、Subject Workspace、风险 Inspector、模式输出和独立 QC 全链可追溯。
- MG-K10 与芦可替尼 AD 重点验证既有 Profile、Timeline、漏报和风险基座无损迁移，同时允许证据支持的基座外新增发现。
- MY008-3-01 与 MY008-3-02 重点验证没有既有衍生成品时从原始项目资料建立知识、事实、风险、Profile/Timeline 和中心/项目视图，并验证同类药物/适应症下不同研究不会身份串扰或硬编码复用。
- MY009-UC-2-01 重点验证不同适应症、不同 listing 结构及小数据量条件下的适用性、`not_evaluable`、小样本提示和不过拟合。
- 只有项目内存在两个可确认、范围兼容的真实全量 listing 快照时，才把增量 Run 纳入该项目真实验收；没有真实双快照时不以人为拆分或 synthetic diff 冒充真实增量通过。
- 存在可用外部医学监查报告的项目执行 D33-D34 报告审阅；不存在报告的项目标记 `not_applicable`，不伪造输入。
- 每个项目记录数据规模、表/字段画像、运行清单、实际 ExecutionProfile、耗时/调用、结果与基座差异、来源可追溯、界面验收和已知局限；跨项目汇总用于证明泛化，不把一个项目特例写进公共内核。
- 验收读取真实项目资料，但不修改原始项目文件；所有系统 artifacts 和测试输出写入隔离应用/验收目录。
- 五项目完成门不要求同时并发运行；可串行分阶段验证，但最终必须形成统一 coverage matrix，任何项目缺失都不能声称“五项目专业使用完成”。

### D39：五项目、双角色、连续两轮无任何开放 P0-P4（用户选择 A，2026-08-09）

- 最终专业使用完成采用最严格缺陷门：五个真实项目分别由工程师视角和资深医学监察员视角完成连续两轮验收，任何真实 P0、P1、P2、P3 或 P4 均不得保持开放。
- 最终验收前冻结缺陷等级定义、角色任务合同、ExecutionProfile、项目/来源版本、浏览器/应用版本和验收矩阵；不得在失败后通过放宽等级或删减范围制造“零缺陷”。
- 资深医学监察员角色必须通过真实 audience-facing UI/Playwright 从零操作，评价流程、医学准确性、漏报/误报、风险分级、证据充分性、中文易读性、图表逻辑、美学一致性、Profile/Timeline、中心/项目下钻和来源定位；不能只调用 API 或查看后端结果。
- 工程师角色覆盖安装/启动、项目导入、执行配置、全量/真实增量、Graph 进度、检查点、失败/重启恢复、幂等、审计链、备份迁移、导出、性能、错误处理和数据身份；涉及用户界面的结论仍需真实 UI 证据。
- 每轮使用不同但等价覆盖的 prompt/任务路径，并按项目实际资料变化角色关注点；同一角色的轮次为独立会话，避免记忆前一轮答案。
- 每个项目×角色只有连续两轮均无开放缺陷才通过。任何后续修订使受影响范围的 clean streak 失效，至少重跑该传播范围及其共享合同/相邻回归；不能沿用修订前的第二轮通过。
- “无开放缺陷”允许经证据证明为重复、非问题、范围外或测试环境问题的条目关闭，但必须保留原报告、裁决理由和复验证据；不允许以“已知问题/以后处理”保留 P4 仍宣称完成。
- 医学验收既检查 reference baseline 召回，也检查基座外新增发现的来源支持、基座错误/过时识别、模型分歧与裁决、AE/MH 漏报，以及未命中案例/反证，防止只优化已知答案。
- 最终 coverage matrix 至少按项目、角色、轮次、监查模式、全量/真实增量、风险域、看板层级、报告/Query、恢复/审计、实际执行配置和缺陷状态记录证据定位。
- 该严格门服务于用户本人的专业使用质量，不构成商业化、法规认证或电子签名声明。
